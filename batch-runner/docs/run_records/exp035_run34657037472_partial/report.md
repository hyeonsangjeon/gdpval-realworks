### 채점 비용 범위

판정 모델 `azure:gpt-5.6-sol`은 `models_deliberately_not_priced`에 있어서
**하나의 금액을 쓸 수 없습니다.** Azure 공표 요금(`standard_global`)의 짧은
문맥 요율을 하한, 긴 문맥 요율을 상한으로 삼은 **범위**만 쓸 수 있습니다.

| 구분 | 문제 | 채점 항목 | 범위 |
|---|---|---|---|
| 기준 실행이 실제로 측정한 것 | 89 | 4,247 | $206.48 – $361.44 |
| 기준 실행에서 0회였던 것 | 9 | 419 | +$20.37 – +$35.66 (측정 아님, 환산) |
| **합계** | **98** | **4,666** | **$226.85 – $397.10** |

4구간 시점의 값은 70문제·3,321항목·$157.67–$276.13이었습니다. **이 범위는
구간에 매인 값이라** 릴레이가 구간을 더할 때마다 움직입니다. 앞 구간 값을
인용하지 말고 그때마다 다시 재야 합니다.

빠진 것 둘은 **둘 다 실제 청구액을 올리는 쪽**입니다: 캐시 쓰기 토큰은
어디에도 기록되지 않고, 시각·음성 호출 사용량은 문제별 판정 칸에 들어가지
않습니다.

**이 범위는 위의 $76.7194와 별개입니다.** 하나는 문제를 푸는 값이고 하나는
채점하는 값입니다.

### 채점을 시작할 수 있는가

아직 아닙니다. 채점기는 채워진 parquet와 `inference_provenance.json`을
입력으로 삼는데, 둘 다 **마지막 구간의 4단계와 7단계**가 만듭니다. 중간
구간은 그 단계를 돌지 않습니다.

다행인 것은 이 계보가 `DRY_RUN_INPUT: false`로 돌고 있다는 점입니다. 마지막
구간이 2a단계를 `success`로 끝내면 3~7단계가 전부 돌고, parquet와 출처
파일이 생깁니다. **남은 실패 경로는 하나뿐입니다** — 마지막 구간의 2a단계가
감시견이 아닌 이유로 `success`가 아니게 끝나는 경우입니다. 그러면 3~7단계가
전부 건너뛰어지고 결과물은 `workspace/upload/`에만 남습니다.

## 숫자를 어떻게 확인했나

이 기록은 손으로 만들지 않았습니다.
`batch-runner/scripts/build_partial_run_record.py`가 아티팩트에서 생성합니다.

```
python scripts/build_partial_run_record.py \
    /tmp/relay/34657037472/artifact/batch-results-34657037472 \
    --run-id 34657037472 \
    --output-dir docs/run_records/exp035_run34657037472_partial \
    --log /tmp/relay/leg3_job.clean.log \
    --log /tmp/relay/34631861765/raw.log \
    --log /tmp/relay/34657037472/raw.log \
    --ledger /tmp/relay/34603033098/workspace/cost_ledger_condition_a.sqlite3 \
    --ledger /tmp/relay/34631861765/artifact/.../cost_ledger_condition_a.sqlite3
```

`--ledger`에는 **앞 구간 것만** 넣습니다. 이 구간 자신의 원장은 아티팩트
안에 있습니다. `--log`는 **계보 B의 세 구간 것을 모두** 넣어야 합니다 —
실패 46개의 제공자 문구가 세 로그에 흩어져 있기 때문입니다. 빠뜨리면 그
줄에 `message_source: "not_available"`이 붙습니다. **이 기록에는 그 표시가
붙은 줄이 0개**이고, 실패 46개가 전부 제공자 문구를 갖고 있습니다.

숫자는 서로 독립된 출처에서 따로 세어 맞췄습니다:

| 출처 | 무엇을 말해주나 |
|---|---|
| 실행 로그 (계보 B 세 구간) | 문제별 재시도 사다리와 결말, 제공자 문구 |
| 원장 `cost_calls` (96 + 74 + 98행) | 턴 수, 토큰, 재시도 분류, 정산 여부 |
| 체크포인트 `step2_inference_progress_condition_a.json` | 220개 전부의 최종 상태 |
| 아티팩트 파일 시스템 | 실제로 남은 결과물 371개 |
| 채점기 선택 단계 (직접 실행) | 판정에 닿는 98개 / 막히는 6개 |
| 실행 단계 상태 (Actions API) | 이어받기가 실제로 일어났는지 |

맞아떨어진 것:

- 체크포인트 성공 **104개** = 결과물 폴더 **104개** = 매니페스트 문제 **104개**
- 파일 없는 성공 0개, 파일 남긴 실패 0개
- 원장 268행 = 문제별 `calls` 합계 268

- 이 구간 원장의 48문제 = 이 구간이 **새로** 푼 48문제와 정확히 일치

기록이고, 회차 숫자는 그 파일이 정본입니다.

## 왜 `results/`가 아니라 여기에 있나

`batch-runner/results/` 아래는 **대시보드에 발행되는 실험** 자리입니다.
중단된 실행을 거기 두면 발행에 필요한 `report_data.json`이 없어 빌드가 서고,
폴더 이름을 바꿔도 `short_id`가 충돌합니다. 끝나지 않은 실행의 보존 기록은
`docs/run_records/` 아래에 둡니다.
