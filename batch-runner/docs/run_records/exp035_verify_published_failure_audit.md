# exp035 — 발행 검증 9개 실패의 원인 분류

채점은 9개 조각 전부 성공했고, 발행 검증은 9개 전부 실패했습니다. 돈은 이미
나갔고 결과는 `origin/main`에 올라가 있는데, 그 위에 빨간 표시가 붙어 있는
상태였습니다.

**다시 채점하지 않았습니다.** 아래는 전부 이미 있는 증거를 다시 읽은 것입니다.

- 9개 실행의 커밋: `937074280752ed2893b94bca95e74e09faa1bd1a`
- 채점기 지문: `src_fd0db9d9d78d6d54`
- 증거가 있는 곳: 각 실행이 올린 `published-verification-<run>-1.json` 딸림파일

## 먼저 — 실패가 몇 종류인가

9개 실행이 **전부 똑같이** 두 가지에서 걸렸습니다. 조각마다 다른 문제가 난
것이 아닙니다.

| 조각 | 실행 번호 | 걸린 검사 |
|--:|---|---|
| 0 | 34703017924 | 원장(`task_coverage`), 집계 |
| 1 | 34703225139 | 원장(`task_coverage`), 집계 |
| 2 | 34703228952 | 원장(`task_coverage`, `usage_containment`), 집계 |
| 3 | 34703233070 | 원장(`task_coverage`), 집계 |
| 4 | 34703237744 | 원장(`task_coverage`), 집계 |
| 5 | 34703242971 | 원장(`task_coverage`), 집계 |
| 6 | 34703248954 | 원장(`task_coverage`), 집계 |
| 7 | 34703254151 | 원장(`task_coverage`), 집계 |
| 8 | 34703258988 | 원장(`task_coverage`, `usage_containment`), 집계 |

통과한 검사도 적어 둡니다. 9개 전부 **발행 확인·payload·스키마 검사는
통과**했습니다. 파일이 깨졌거나 없어서 실패한 것이 아닙니다.

딸림파일에는 **실패한 검사만** 기록됩니다. 그래서 나머지 검사가 통과했는지는
딸림파일로 알 수 없고, 원장 검증기를 9개 조각에 직접 돌려서 따로 확인했습니다.
조각마다 12개씩, 합쳐서 108개입니다.

| 검사 | 결과 |
|---|---|
| `sidecar` `identity` `no_double_billing` `all_calls_settled` | 9개 전부 통과 |
| `usage_reconciles` `cost_reconciles` `components_reconcile` | 9개 전부 통과 |
| `price_table` `partial_cause` `legacy_counters` | 9개 전부 통과 |
| `usage_containment` | **조각 2, 8 실패** (원인 3) |
| `task_coverage` | 발행 당시 9개 전부 실패 → 고친 뒤 9개 전부 통과 (원인 2) |

`identity`와 `no_double_billing`이 108개 중 하나도 안 걸렸다는 것이, 신원이
겹쳤거나 같은 호출이 두 번 청구됐을 가능성에 대한 답입니다.

그래서 원인은 셋입니다. 두 개는 검사 쪽 결함이고, 하나는 진짜 발견입니다.

### 병합본도 한 번 검사됐습니다 — 다만 빈손으로 통과했습니다

조각 4의 실행(34703237744)은 조각 파일과 **병합 채점본** 두 개를 검사했습니다.
병합본 쪽 결과는 이렇습니다.

> `…__v2.2.json` declares no cost_ledger; nothing to reconcile against

통과이긴 하지만 **맞춰 볼 대상이 없어서 통과한 것**입니다. 병합본은 파일
이름이 259바이트라 딸림 원장 이름이 `NAME_MAX`를 넘어 만들어지지 못했고,
그래서 원장을 가리키는 칸이 비어 있습니다. 이 통과를 "병합본의 비용이
확인됐다"로 읽으면 안 됩니다. 조각 9개의 원장이 실제 증거입니다.

## 원인 1 — 집계가 채점 파일을 한 개도 안 읽고 죽었습니다 (9개 전부)

검증 작업이 `npm run aggregate`를 부르는데, 그 작업에는 Node를 깔아 주는
단계가 없었습니다. `node_modules`가 없는 나무에서 명령을 부른 셈입니다.

여덟 개 스크립트 중 **첫 번째**에서 끝났습니다.

```
Cannot find package 'yaml' imported from scripts/aggregate-tests.mjs
```

`aggregate-grades.mjs`까지 가지도 못했습니다. 즉 이 실패는 **exp035 채점
결과에 대해 아무것도 말하지 않습니다.** 발행된 나무가 거부된 것처럼
보고되지만, 거부한 쪽이 그 나무를 읽은 적이 없습니다.

> **이 오류가 어디 있는지 주의해야 합니다.** 딸림파일
> `published-verification-*.json`의 집계 항목 `output_tail`에만 있고,
> **작업 로그에는 없습니다.** `gh run view --log`로 찾으면 한 건도 안 나와서
> 이 설명이 틀린 줄 알게 됩니다. 실제로 그렇게 한 번 헛짚었습니다.

고친 자리: `.github/workflows/grade-run.yml`의 `verify-published` 작업에
`actions/setup-node`와 `npm ci`를 검증 단계 **앞에** 넣었습니다. 버전은
`deploy.yml`과 같은 것으로 맞췄습니다. 이 검사가 답하려는 질문이 "대시보드
빌드가 이 커밋을 받아들이는가"이므로, 대시보드가 쓰는 것과 다른 걸 돌리면
다른 질문에 답하게 됩니다.

## 원인 2 — 0원과 증거 없음을 구별하지 못했습니다 (9개 전부)

옛 검사는 이렇게 말했습니다.

> 9 graded tasks have no call in the ledger, so they appear to have been graded for free

조각별로 9, 6, 6, 9, 6, 10, 9, 12, 11개씩 지목했습니다. **합이 78입니다.**

그런데 exp035에서 판정자를 한 번도 못 부른 과제가 정확히 78개입니다. 지목된
78개와 0호출 78개를 맞춰 봤더니 **한 개도 다르지 않았습니다**(양쪽 차집합 0).

| | 수 |
|---|--:|
| 옛 검사가 "공짜로 채점됐다"고 지목 | 78 |
| 판정 호출이 실제로 0인 과제 | 78 |
| 두 집합의 차이 | **0** |

**즉 이 검사는 증거가 없는 자리를 찾은 것이 아니라, 값이 진짜 0인 자리를 찾아
놓고 수상하다고 한 것입니다.** 78개는 판정자를 부르기 전에 멈췄고(파일을 못
낸 70개 + 선택기가 거절한 8개), 부르지 않았으니 0원이 맞는 값입니다.

고친 자리: `batch-runner/scripts/verify_cost_ledger.py`. 과제마다 세 군데를
맞춰 보고, 세 부류를 **따로 이름 붙여** 셉니다.

- 비용이 붙은 과제
- 실패했지만 0원으로 청구된 과제 — 공짜가 아니라 계산에 들어간 것
- 판정자에 도달하지 못해 값이 진짜 0인 과제

조용히 통과시키지 않았습니다. 그러면 검사를 꺼 버린 것과 결과가 같아집니다.
0원이라고 판단한 과제를 검사 결과에 이름으로 남기고, 그 수를 시험이 셉니다.

### 검사를 약하게 만들지 않았다는 근거

고친 검사가 **더 엄격해졌는지**를 확인하려고 실패 사례 시험 5개를 새로
넣었습니다. 전부 "이런 건 여전히 잡혀야 한다"는 쪽입니다.

- 못 보여 주는 호출을 했다고 주장하는 과제
- 호출 수를 0으로 적어 호출을 숨긴 과제
- 호출 수를 실제보다 적게 적은 과제
- 호출이 없는데 청구액이 있는 과제
- 자기 신고 두 개가 서로 다른 과제

그리고 발행 당시 커밋의 검증기를 그대로 꺼내(`git show 937074…`) 같은 9개
조각에 돌려 전후를 비교했습니다.

| | `task_coverage` | `usage_containment` |
|---|---|---|
| 발행 당시 검증기 | **9개 전부 실패** | 2개 실패 |
| 고친 검증기 | **9개 전부 통과** | 2개 실패 (그대로) |

## 원인 3 — 오디오 사용량 (조각 2, 8) — 이건 진짜입니다

조각 2와 8은 **지금도 실패인 채로 둡니다.**

```
조각 2: 30 calls … ({'audio_input_tokens': 8999, 'audio_output_tokens': 0})
조각 8:  8 calls … ({'audio_input_tokens': 2400, 'audio_output_tokens': 0})
```

38건, 11,399토큰. 과제 3개가 오디오를 보냈는데 영수증이 그 칸을 담지
못합니다. 원장에는 찍혀 있고, 합산 함수가 안 읽고, 발행 스키마가 안 받습니다.
막고 있는 것은 발행 스키마입니다. 자세한 것은
[`exp035_grading_coverage_220.md`](exp035_grading_coverage_220.md)에 적었습니다.

**다시 채점해도 안 고쳐집니다.** 스키마에 오디오 칸이 생겨야 하고, 그러면
이미 발행된 영수증 21벌을 다시 검사해야 합니다. 채점기 지문이 걸린 영역이라
이번 복구에서는 건드리지 않고 다음 작업으로 답니다.

## 사용자가 물은 다섯 가지 가능성에 대한 답

| 가능성 | 해당하는가 | 근거 |
|---|---|---|
| 증거가 진짜 없다 | **아니오** | 9개 전부 payload·스키마 검사 통과. 조각 9개와 원장 9개가 커밋돼 있음 |
| 조각 범위 문제 | **아니오** | 9개 조각의 과제 220개가 겹침 0, 빠짐 0 |
| 0호출 규칙 처리 | **예 — 9개 전부** | 원인 2. 지목된 78개가 0호출 78개와 완전히 일치 |
| 중복 신원 | **아니오** | 과제 번호 220개가 전부 서로 다름. `identity`·`no_double_billing` 검사가 9개 조각 전부 통과 |
| 양식 사용량 누락 | **예 — 조각 2, 8** | 원인 3. 진짜 발견이라 고치지 않고 남김 |
| 검증기·집계 결함 | **예 — 둘 다** | 원인 1(집계), 원인 2(검증기) |

## 유료 재개가 필요한가 — 아니오

- 0호출 78개는 다시 채점해도 같은 자리에서 멈춥니다. 풀이 단계에서 파일이
  없었던 것이지 채점이 실패한 것이 아닙니다.
- 오디오 빈칸은 채점기가 아니라 스키마 문제라 다시 채점해도 그대로입니다.
- 두 결함 모두 검사 쪽에 있고, 이미 있는 파일로 고칠 수 있습니다.

**실패한 9개 작업을 다시 돌리는 것도 답이 아닙니다.** `verify-published`는
`main`이 아니라 **발행 당시 커밋을 꺼내서** 그 커밋의 워크플로와 검증기로
돌립니다. 다시 돌리면 고치기 전 코드가 다시 실행됩니다. 돈은 안 들지만
결과도 같습니다.

## 이 문서가 주장하지 않는 것

- 채점 결과가 옳다고 주장하지 않습니다. 여기서 본 것은 **검증이 왜
  실패했는가**까지입니다.
- 0호출 78개가 점수를 잘 받았으리라고 주장하지 않습니다. 0호출은 0점으로
  두고 220 분모에 그대로 넣었습니다.
- 조각 2, 8의 실패를 해결했다고 주장하지 않습니다. 남겨 뒀습니다.
