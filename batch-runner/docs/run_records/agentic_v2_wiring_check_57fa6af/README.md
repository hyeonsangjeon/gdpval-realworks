# 격리 백엔드 배선 점검 — 실제 호스트, 모델 없음

승인서를 하나 내밀면 러너가 고정된 가짜 백엔드 대신 **진짜 격리 백엔드**를 고르고,
그 백엔드의 `exec_run`이 실제로 게스트를 띄워 명령을 돌리고, 바깥에서 넣어 준 파일을
게스트 안에서 읽고, 게스트가 쓴 파일이 호스트로 돌아오고, 끝나면 기계가 사라지는지를
한 번에 확인한 기록입니다.

**모델은 한 번도 부르지 않았습니다.** `model_calls: 0`, `paid_runs: 0`.

실행일 2026-09-16. 소스 head `57fa6af`. 호스트 `gdpval-devhost-vm`(커널
6.17.0-1022-azure, 8 vCPU). 이미지 `ghcr.io/hyeonsangjeon/gdpval-sandbox`
(`sha256:ee6ef798…`). 22개 사례 전부 통과.

재실행 방법은 `batch-runner/scripts/run_agentic_v2_wiring_check.py`에 있습니다.

## 1. 이 기록이 답하는 질문

"격리 백엔드가 러너의 입장 심사에 실제로 이어져 있는가, 아니면 시험용 대역에만
이어져 있는가."

이 질문이 먼저 풀려야 하는 이유는, 이 백엔드 위에서 돈을 쓰는 실행을 하기 전에
**그 실행이 어디서 벌어지는지**가 정해져 있어야 하기 때문입니다. 대역 위에서 통과한
시험은 대역에 대해서만 말합니다.

분모는 아래 22개 사례 목록 자체이고, 단위는 사례별 통과/거절입니다.

## 3. 이 기록이 말하지 않는 것

- **운영 준비 상태가 아닙니다.** 여기서 확인한 것은 배선이고, 배선이 이어져 있다는
  것과 유료 실행을 돌려도 된다는 것은 다른 말입니다.
- **모델 품질에 대해 아무 말도 하지 않습니다.** 모델을 부르지 않았습니다.
- **반복 흔들림을 재지 않았습니다.** 각 사례는 1회 관측입니다. 통과/거절이 갈리는
  종류의 점검이라 반복 폭을 재는 설계가 아닙니다.
- **비용은 미측정이고 0이 아닙니다.** 모델 호출과 유료 실행은 0이지만, 이 점검이
  쓴 가상 머신 전원 시간에 대한 요금은 이 기기에서 조회할 수 없습니다.

## 4. 왜 사례 12와 20의 문구가 저 모양인가

처음 판에서는 이 두 사례가 "게스트가 정지 확인됐는가"를 물었고, 실제로는 아무것도
남기지 않은 실행에서 거절이 났습니다. 명령을 마치고 마감 안에 스스로 끝난 게스트에는
신호를 보낼 일이 없고, 신호를 안 보냈으니 확인할 것도 없기 때문입니다.

호스트가 남았는지를 판정하는 `the_host_was_left_running`은 "신호를 보냈는데도
살아 있었다"에만 걸리도록 쓰여 있습니다. 그래서 질문을 고쳤습니다. 호스트가 남지
않았어야 하고, 게스트는 실제로 끝나는 두 경로 중 하나로 설명돼야 합니다. 신호가
나갔고 확인됐거나, 신호가 필요 없었고 실행이 그것이 돌지 않는 것을 봤거나입니다.
**신호가 나갔는데 확인되지 않은 경우는 여전히 거절입니다.**

이 기록에 남은 통과 22건은 고친 뒤의 것이고, 고치기 전 20/22 판은 호스트의
`wiring-check-dbb7cb6.json`에 그대로 남겨 뒀습니다.
