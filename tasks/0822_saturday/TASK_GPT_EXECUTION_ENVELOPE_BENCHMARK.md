# 같은 GPT 모델의 실행 환경별 성능 비교

- 작성일: 2026-08-25
- 상태: 5개 작업 사전 점검 준비 완료. 실제 비교 실험은 아직 시작하지 않았습니다.
  2026-08-28 소유자가 매월 제공되는 Azure 크레딧 사용과 미확정 소리 채점 비용의
  실측을 승인했으므로 비용 추정은 기록만 하고 실행을 막지 않습니다. 현재 남은 것은
  Azure 연결과 입력 파일 등 비용 외 실행 조건입니다. 최신 결정은 13.27장에 있습니다.
- 관련 GitHub Project: hyeonsangjeon/projects/5 — 카드 "같은 GPT 모델의 실행 환경별 성능 비교"

## 1. 이 문서가 답하는 질문

GDPVal 벤치마크는 지금까지 "어떤 모델이 더 잘하는가"를 측정해 왔습니다. 이
문서는 다른 질문을 다룹니다.

> **모델을 하나로 고정했을 때, 그 모델이 작업하는 장소를 바꾸면 성적이 달라지는가?**

같은 모델에게 같은 지시문과 같은 입력 파일을 주더라도, 코드를 어디서 실행하느냐에
따라 결과물이 달라질 수 있습니다. 서버에 설치된 라이브러리가 다르거나, 실행 시간
제한이 다르거나, 모델이 자기 결과를 다시 볼 수 있는지 여부가 다르기 때문입니다.
이 문서는 그 차이를 측정하기 위해 **실험을 시작하기 전에 고정해야 하는 조건**을
정의합니다.

이 문서는 특정 GPT 버전을 지정하지 않습니다. 실험을 시작하는 사람이 그때 사용할
모델 하나를 고르고, 그 선택을 아래 3장의 형식으로 적어 두면 됩니다. 나중에 다른
GPT 모델로 같은 실험을 반복할 때도 이 문서를 고칠 필요가 없습니다.

### 이 문서를 읽는 데 필요한 사전 지식

없습니다. 별도 용어 목록을 찾아볼 필요가 없도록, 줄임말과 내부에서만 통하는
표현을 쓰지 않았습니다. 코드에 있는 이름을 인용할 때는 바로 앞에서 그 이름이 무슨
일을 하는지 먼저 설명합니다.

"지금 실험을 시작해도 되는가"를 판정하는 검사 도구와 자동 테스트를 추가했습니다.

## 3. 고정 모델 실행 조건

### 3.1 무엇인가

**고정 모델 실행 조건**은 다섯 실행 환경 전부에서 글자 하나까지 똑같이 유지해야
하는 항목의 묶음입니다. 이 조건이 한 곳이라도 달라지면, 측정된 성적 차이가 실행
환경 때문인지 조건이 달라져서인지 구분할 수 없게 됩니다.

코드에서 이 묶음을 다루는 이름은 `model_run_conditions`이며,
`batch-runner/core/execution_environment_readiness.py`의
`ModelRunConditions`가 그 형식을 정의하고 검사합니다.

### 3.1.1 두 비교에서 엄격함이 다른 부분

열다섯 항목 중 열한 개는 **두 비교 모두에서** 똑같아야 합니다. 서비스, 배포 이름,
실제 응답 모델, 호출 규격 버전, 두 지시문 원문, 작업 목록, 입력 파일 버전, 최대
텍스트 양, 작업별 최대 실행 시간, 그리고 자동 모델 전환 금지입니다. 이것이
달라지면 어느 비교를 하든 같은 질문에 답하는 것이 아닙니다.

나머지 네 개 — 자기 검토 허용 여부와 횟수, 재시도 허용 사유와 최대 횟수 — 는
비교 종류에 따라 다릅니다.

- **첫 번째 비교(6.1)**: 네 항목 모두 다섯 환경에서 똑같아야 하고, 자기 검토는
  꺼져 있어야 합니다. 실행 환경만 바뀌어야 하기 때문입니다.
- **두 번째 비교(6.2)**: 네 항목이 환경마다 달라도 됩니다. 각 도구가 원래 하던
  방식이 바로 측정 대상이기 때문입니다.

검사 도구에 어느 비교인지 알려 주면 그에 맞는 엄격함을 적용합니다. 알려 주지
않으면 더 엄격한 첫 번째 비교 기준으로 검사합니다.

### 3.2 포함할 항목

실험을 시작하기 전에 아래 열다섯 항목을 모두 적어야 합니다. 하나라도 비어 있으면
검사 도구가 실행을 막습니다.

| 적어야 할 내용 | 코드에서 쓰는 이름 | 설명 |
|---|---|---|
| 모델을 제공하는 서비스 | `provider` | 예: Azure AI Foundry를 통해 제공되는지, OpenAI에서 직접 제공되는지 |
| Azure AI Foundry 배포 이름 | `deployment` | 관리자가 Azure AI Foundry에 만들어 둔 배포의 이름 |
| 실제 응답을 생성한 모델 이름과 버전 | `resolved_model` | 서비스가 응답과 함께 돌려준 값. 배포 이름 뒤에 어떤 모델이 실제로 연결돼 있었는지 |
| Azure AI Foundry 호출 규격 버전 | `api_version` | 호출에 사용한 요청 규격의 버전 |
| 시스템 지시문 원문 | `system_instruction` | 요약하지 않고 원문 그대로 |
| 사용자 또는 작업 지시문 원문 | `task_instruction` | 요약하지 않고 원문 그대로 |
| 실행할 작업의 고정 목록 | `task_ids` | 실행 전에 정해 둔 작업 번호 목록. 순서까지 고정 |
| 입력 파일의 정확한 버전 | `input_file_versions` | 파일 경로마다 내용 지문(SHA-256)을 함께 기록 |
| 모델이 생성할 수 있는 최대 텍스트 양 | `max_output_tokens` | 0보다 커야 함 |
| 작업별 최대 실행 시간 | `per_task_timeout_seconds` | 0보다 커야 함 |
| 자기 검토 허용 여부 | `self_review_enabled` | 6.2절의 두 번째 재시도 종류를 허용할지 |
| 자기 검토 최대 횟수 | `self_review_max_attempts` | 허용하지 않으면 반드시 0 |
| 재시도 허용 사유 | `retry_reasons_allowed` | 6장의 세 가지 중에서만 고를 수 있음 |
| 재시도 최대 횟수 | `retry_max_attempts` | |
| 자동 모델 전환 금지 | `automatic_model_switch_allowed` | 반드시 거짓. 참이면 검사 도구가 실행을 막음 |

### 3.3 자동 모델 전환을 금지하는 이유

모델 호출이 실패했을 때 다른 모델이나 다른 배포로 조용히 바꿔서 다시 시도하면,
성적표에는 성공으로 남지만 실제로는 다른 모델이 푼 작업이 섞입니다. 그러면 비교
자체가 무너집니다.

이 저장소에는 추론 단계에 자동 전환 기능이 없습니다. 대안 배포 목록을 받는 곳은
`batch-runner/core/azure_ai_clients.py` 806행의
`narrative_route_workloads` 하나뿐이며, 이는 실험 결과 요약문을 쓰는 단계에만
쓰입니다. 비교 실험 자체에는 영향을 주지 않지만, 실험 보고서를 만들 때도 대안
배포를 비워 두는 편이 안전합니다.

## 4. 비교할 다섯 실행 환경

| 번호 | 이 문서에서 부르는 이름 | 무엇을 하는 곳인가 |
|---|---|---|
| 1 | 서버 운영체제의 별도 Python 프로세스 | 모델이 Python 코드를 쓰고, 배치 실행기가 그 코드를 서버 운영체제에서 별도 프로세스로 실행합니다 |
| 2 | Docker 컨테이너 | 모델이 Python 코드를 쓰고, 배치 실행기가 고정된 이미지로 만든 Docker 컨테이너 안에서 실행합니다 |
| 3 | Azure Code Interpreter | Azure AI Foundry가 모델의 Python 코드를 대신 실행합니다. 실행 장소는 Azure가 만들고 관리하는 컨테이너입니다 |
| 4 | Agentic Sandbox V2 | 모델이 도구를 고르고, 결과를 읽고, 다음 행동을 정하는 과정을 반복하는 것이 목표인 실행 방식입니다 |
| 5 | Codex 기본 에이전트 | Codex가 스스로 도구를 고르고, 명령을 실행하고, 결과를 검토하고, 재시도까지 직접 처리합니다 |

## 5. 다섯 실행 환경의 현재 상태

각 환경을 아래 다섯 상태 중 하나로 분류했습니다. 추측이 아니라 이 저장소의 코드나
공식 제품 문서를 근거로 판단했습니다.

- **현재 실제 실험 실행 가능**
- **모델을 호출하지 않는 구조 검사만 가능**
- **현재 저장소에 구현되지 않음**
- **필요한 조건이 충족되지 않아 실행이 차단됨**
- **근거가 부족해 판단할 수 없음**

### 5.1 요약표

| 실행 환경 | 현재 상태 | 한 줄 근거 |
|---|---|---|
| 1. 서버 운영체제의 별도 Python 프로세스 | 현재 실제 실험 실행 가능 | 실험 설정 파일 24개가 이미 이 방식을 쓰고 있고, 220개 작업 전체 실행 기록이 남아 있음 |
| 2. Docker 컨테이너 | 조건부로 실행 가능. 조건이 빠지면 차단 | 컨테이너가 없을 때 조용히 서버 운영체제로 넘어가는 경로가 있어, 이를 막는 설정이 반드시 필요함 |
| 3. Azure Code Interpreter | 필요한 조건이 충족되지 않아 실행이 차단됨 | 코드는 있지만 지정된 Azure 연결 설정이 없으면 시작 자체를 거부함 |
| 4. Agentic Sandbox V2 | 모델을 호출하지 않는 구조 검사만 가능 | 명령 실행 도구가 닫혀 있고, 모델을 호출하는 반복 실행이 아예 없음 |
| 5. Codex 기본 에이전트 | 현재 저장소에 구현되지 않음 | GDPVal 작업을 Codex로 실행하는 코드가 저장소 어디에도 없음 |

### 5.2 서버 운영체제의 별도 Python 프로세스 — 현재 실제 실험 실행 가능

**근거**

- 작업을 실행 방식별로 나눠 보내는 부분인
  `batch-runner/core/executor.py` 154행이
  `subprocess`라는 이름의 실행 방식을 받아
  `batch-runner/core/subprocess_runner.py`의
  `SubprocessRunner`에게 넘깁니다.
- 실험 설정 파일 24개가 이 방식을 쓰고 있습니다. 예:
  `batch-runner/experiments/exp003_GPT52Chat_baseline_runner_exec.yaml`의
  `execution.mode` 값이 `subprocess`입니다.
- 이 방식으로 220개 작업 전체를 실행하고 채점까지 마친 기록이
  `data/grades`에 남아 있습니다.

**주의할 점**

작업 하나의 기본 제한 시간은 570초, 메모리 상한은 5GB입니다
(`batch-runner/core/config.py` 113행).
이 값은 환경 변수로 바뀔 수 있으므로, 비교 실험에서는 3장의 고정 모델 실행 조건에
실제 사용값을 적어야 합니다.

### 5.3 Docker 컨테이너 — 조건이 갖춰지면 실행 가능, 아니면 차단

**근거**

- `batch-runner/core/executor.py` 165행이
  `sandbox`라는 이름의 실행 방식을
  `batch-runner/core/sandbox_runner.py`의
  `SandboxRunner`에게 넘깁니다.
- 컨테이너 이미지 이름의 기본값은 `gdpval-sandbox:latest`이며, 이미지를 만드는
  자동 작업은
  `.github/workflows/build-sandbox-image.yml`에
  있습니다.

**반드시 걸어야 하는 조건**

실행할 곳을 고르는 부분인
`batch-runner/core/sandbox_runner.py` 1039행의
`_execute`는, 컨테이너 사용 설정이 `auto`일 때 Docker가 없거나 이미지가 없으면
**경고만 출력하고 서버 운영체제에서 그대로 실행합니다.** 비교 실험에서 이 일이
벌어지면 2번 환경의 성적이 사실은 1번 환경의 성적이 되어 버립니다.

따라서 비교 실험에서는 컨테이너 사용 설정을 반드시 `always`로 둡니다. 그러면
Docker나 이미지가 없을 때 작업이 조용히 넘어가지 않고 실패로 기록됩니다. 이미
운영 중인 설정 파일
`batch-runner/experiments/exp026_sandbox_skills_multimodal.yaml` 260행도
같은 이유로 `always`를 쓰고 있습니다.

**현재 판정**

- 설정이 `always`이고 Docker와 이미지가 모두 있으면 → 현재 실제 실험 실행 가능
- 설정이 `always`가 아니면 → 필요한 조건이 충족되지 않아 실행이 차단됨
- Docker나 이미지를 확인하지 않았으면 → 근거가 부족해 판단할 수 없음

검사 도구는 이 세 가지를 실제로 확인해서 판정합니다. 확인하지 않은 항목을 "괜찮을
것"으로 추정하지 않습니다.

### 5.4 Azure Code Interpreter — 필요한 조건이 충족되지 않아 실행이 차단됨

**저장소 근거**

- `batch-runner/core/executor.py` 143행이
  `code_interpreter`라는 이름의 실행 방식을
  `batch-runner/core/code_interpreter.py`의
  `CodeInterpreterRunner`에게 넘깁니다.
- 추론을 실행하는
  `batch-runner/step2_run_inference.py` 124행의
  `_require_code_interpreter_route_profile`은, Azure 연결 방식을 지정하는 설정값이
  지정된 값이 아니면 실행을 거부합니다. 이 설정이 없는 상태에서는 시작할 수
  없습니다.
- 모델 제공 서비스가 Azure가 아니면 실험 설정 검사 단계에서 거부됩니다
  (`batch-runner/core/experiment_config.py` 519행).
- 실험 설정 파일 5개가 이 방식을 지정하고 있습니다. 즉 코드가 없어서 막힌 것이
  아니라, 연결 설정과 승인이 없어서 막힌 것입니다. 다만 이 방식으로 220개 작업
  전체를 실행하고 채점까지 마친 기록은 아직 없습니다.

**공식 제품 문서 근거**

- Microsoft 문서는 이 도구를 "모델이 Python 코드를 실행할 수 있는, 서비스가 관리하는
  격리된 실행 환경"으로 설명합니다.
  (learn.microsoft.com/azure/foundry/openai/how-to/responses,
  learn.microsoft.com/azure/foundry/agents/how-to/tools/code-interpreter)
- 같은 문서에 따르면 실행 환경은 20분 동안 쓰지 않으면 사라지고, 요금은 분 단위로
  부과되며 최소 5분이 청구됩니다. 요청 하나에 파일 50개까지 넣을 수 있고, 실행
  환경 하나가 보관할 수 있는 파일은 입력과 출력을 합쳐 1,000개까지입니다.
- **문서에 없는 것**: 이 실행 환경 안에서 바깥 네트워크에 접속할 수 있는지는 Microsoft
  문서에 나와 있지 않습니다. 따라서 "네트워크가 차단돼 있다"고 적으면 안 됩니다.
  8장의 기록 항목에서는 이 부분을 "공식 문서에 명시 없음"으로 남깁니다.

**차단을 푸는 방법**

Azure 연결 설정을 지정된 값으로 맞추고, 유료 실행 승인을 받으면 됩니다. 검사
도구가 그때 자동으로 "현재 실제 실험 실행 가능"으로 판정을 바꿉니다. 사람이 문서를
고칠 필요가 없습니다.

### 5.5 Agentic Sandbox V2 — 모델을 호출하지 않는 구조 검사만 가능

이 환경은 **아직 실험에 쓸 수 없습니다.** 목표는 모델이 도구를 고르고 결과를 읽고
다음 행동을 정하는 과정을 반복하는 것이지만, 현재 있는 것은 그 과정의 뼈대뿐입니다.
모델은 한 번도 호출되지 않습니다.

**막혀 있는 세 곳**

1. **명령을 실행하는 도구가 닫혀 있습니다.**
   `batch-runner/core/agentic_v2_fixture_backend.py` 197행의
   `exec_run`은, 시험용으로 만든 한 가지 예시 명령을 빼면 모든 명령에 대해
   "이 기능은 사용할 수 없음"(`capability_unavailable`)이라고 답합니다. 즉 실제
   프로그램을 돌릴 수 없습니다.

2. **모델이 도구 결과를 보고 다음 행동을 정하는 반복 실행이 없습니다.**
   `batch-runner/core/agentic_v2_runner.py`는
   미리 적어 둔 호출 목록을 순서대로 재생할 뿐입니다. 모델에게 무엇을 물어보는
   코드가 없습니다.

3. **실제 실험 사용이 승인되지 않았습니다.** 두 곳에서 각각 막습니다.
   - 추론 실행 단계
     `batch-runner/step2_run_inference.py` 135행의
     `_require_runnable_execution_mode`가 이 실행 방식을 아예 거부합니다.
   - 작업 분배 단계
     `batch-runner/core/executor.py` 571행은
     "이 실행은 유료 모델 호출을 하지 않는다"고 명시하지 않으면 준비 자체를
     거부하고, 모델 접속 정보가 함께 넘어오면 그것도 거부합니다.

**이 상태를 어떻게 다뤄야 하는가**

- 이 환경의 성적을 다른 환경과 같은 표에 넣지 않습니다. 아직 성적이 없습니다.
- 위 세 가지 차단을 우회하지 않습니다. 검사 도구가 세 곳을 실제로 실행해 보고,
  하나라도 열려 있으면 문제로 보고합니다.
- 이 환경이 준비되지 않았다고 해서 다른 실행 환경으로 대체하지 않습니다. 준비가 안
  된 상태 그대로 기록하고 넘어갑니다.

### 5.6 Codex 기본 에이전트 — 현재 저장소에 구현되지 않음

**저장소 근거**

- GDPVal 작업을 Codex로 실행하는 코드가 없습니다. 실행 방식 이름을 모아 둔 목록
  (`batch-runner/core/executor.py` 36행)에 해당 항목이 없습니다.
- 저장소에서 Codex를 언급하는 파일은 여럿 있지만, **실행되는 코드는 하나도
  없습니다.** 언급은 코드 검토용 안내 문서 `.github/agents/first-reviewer.md`와
  `tasks/` 아래 지난 작업 기록 문서들에 있으며, 모두 사람이 읽는 글입니다.

**공식 제품 문서에서 확인된 것과 확인되지 않은 것**

| 항목 | 확인 결과 |
|---|---|
| Codex가 스스로 도구를 고르고 명령을 실행하는 방식 | 공식 문서에 있음. 실행 권한 범위와 승인 방식을 설정으로 고를 수 있음 (learn.chatgpt.com/docs/agent-approvals-security) |
| 승인 질문 없이 자동으로 돌리는 방법 | 명령줄 도구에 한해 공식 문서에 있음 |
| 외부 벤치마크 작업 묶음을 넣고 결과 파일을 받는 공식 자동화 경로 | **공식 문서에서 확인되지 않음** |
| Azure AI Foundry 배포로 Codex의 자체 실행 방식을 쓰는 방법 | **공식 문서에서 확인되지 않음** |

마지막 항목이 특히 중요합니다. 3장의 고정 모델 실행 조건은 다섯 환경이 **같은
배포 이름**을 써야 한다고 요구합니다. 그런데 Codex의 자체 실행 방식을 Azure AI
Foundry 배포로 돌릴 수 있다는 내용이 Microsoft 문서에도 OpenAI 문서에도 없습니다.
Azure 모델 목록에 이름에 codex가 들어간 모델이 있고 Azure의 에이전트 서비스에서
쓸 수 있지만, 그것은 **Azure가 만든 에이전트 기능이 그 모델을 쓰는 것**이지 Codex
제품의 자체 실행 방식이 아닙니다.

**결론**

- 저장소 구현 상태로는 "현재 저장소에 구현되지 않음"입니다.
- 설령 구현하더라도, 같은 배포를 공유할 수 있다는 근거가 확인되기 전에는 3장의
  고정 조건을 만족시킬 수 없습니다. 이 부분은 "근거 부족"으로 남겨 둡니다.
- 지원되지 않는다고 해서 이 자리를 다른 실행 환경으로 채우지 않습니다. 5개 환경 중
  1개는 비어 있는 채로 보고합니다.

## 6. 두 가지 비교 방법

두 비교는 서로 다른 질문에 답합니다. **두 결과를 하나의 점수로 합치지 않습니다.**

### 6.1 첫 번째 비교 — 같은 코드를 옮겨서 실행

**하는 일**: 모델이 한 번 만든 Python 코드를 그대로 가져다가, 실행 환경만 바꿔 다시
실행합니다. 코드는 한 글자도 고치지 않습니다.

**답하는 질문**: 실행 환경 자체가 결과에 얼마나 영향을 주는가. 설치된 라이브러리
차이, 실행 시간 제한 차이, 파일 접근 방식 차이가 결과물을 어떻게 바꾸는가.

**이 비교에서 고정하는 것**: 모델은 코드를 만들 때 한 번만 호출됩니다. 그 뒤로는
모델을 부르지 않습니다. 자기 검토도 재시도도 하지 않습니다. 그래야 차이가 실행
환경 때문이라고 말할 수 있습니다.

**코드에서 쓰는 이름**: `same_generated_code_rerun`

### 6.2 두 번째 비교 — 각 도구의 기본 기능을 그대로 사용

**하는 일**: 각 실행 도구가 원래 제공하는 기능을 모두 켜 둡니다. 코드 생성, 도구
선택, 자기 검토, 재시도, 결과 확인을 그 도구가 하던 방식대로 하게 둡니다. 다른
도구와 맞추려고 기능을 억지로 끄지 않습니다.

**답하는 질문**: 실행 도구 전체가 성능에 얼마나 영향을 주는가. 사용자가 실제로
그 도구를 쓸 때 어떤 성적이 나오는가.

**주의**: 이 비교에서는 모델 호출 횟수가 도구마다 다릅니다. 그래서 비용도 다릅니다.
그것이 이 비교의 측정 대상이므로 문제가 아니지만, 8장의 기록 항목에 호출 횟수와
비용을 반드시 남겨야 합니다.

**코드에서 쓰는 이름**: `tool_built_in_features`

### 6.3 두 비교를 섞지 않는 방법

두 비교는 각각 별도의 결과표를 씁니다. 각 결과표에는 자기가 어느 비교의 것인지
적혀 있어야 합니다. 검사 도구의 `check_comparisons_are_scored_apart`가 두 결과표가
모두 있는지, 각 표에 붙은 이름이 맞는지 확인합니다. 표가 하나뿐이거나 이름이
바뀌어 있으면 문제로 보고합니다.

## 7. 재시도 세 종류

같은 작업을 다시 실행한 경우, 이유를 반드시 세 종류로 나눠서 셉니다. 하나로 합쳐
세면 "모델이 똑똑해서 고쳤다"와 "네트워크가 끊겨서 다시 했다"를 구분할 수 없습니다.

### 7.1 모델 판단과 무관한 문제로 다시 실행한 경우

네트워크 오류, 서버 오류, 시간 초과처럼 모델이 결정하지 않은 이유로 다시 실행한
경우입니다. 모델은 이런 재시도가 있었는지 알지도 못합니다.

- 코드에서 쓰는 이름: `infrastructure_error`
- 현재 구현: 실험 설정의 `execution.max_retries` 값이 이 횟수를 정합니다. 기본값은
  3입니다 (`batch-runner/step2_run_inference.py` 2717행).

### 7.2 모델이 결과를 스스로 검토하고 고치려고 다시 시도한 경우

모델이 자기가 만든 결과물을 다 만든 뒤에 다시 보고, 부족하다고 판단해서 새 답을
만든 경우입니다.

- 코드에서 쓰는 이름: `model_self_review`
- 현재 구현: 실험 설정의 `qa` 항목을 켜면 동작합니다. 기본 허용 횟수는 2입니다
  (`batch-runner/step2_run_inference.py` 2909행).
  1번과 2번 환경에서 실제로 쓰이고 있습니다.

### 7.3 모델과 도구가 주고받는 중에 내부적으로 오류를 복구한 경우

모델이 아직 "다 했다"고 말하기 전에, 도구 실행이 실패하자 모델이 스스로 방향을
바꿔 복구한 경우입니다. 바깥에서 보면 재시도가 아니라 한 번의 실행처럼 보입니다.

- 코드에서 쓰는 이름: `tool_loop_internal_recovery`
- 현재 구현: 3번 환경(Azure Code Interpreter)과 5번 환경(Codex)에서 이런 일이 일어날
  수 있습니다. 다만 그 횟수를 바깥에서 정확히 셀 수 있는지는 실험 전에 확인해야
  합니다. 셀 수 없으면 "측정 불가"로 기록하고, 셀 수 있는 것처럼 적지 않습니다.

### 7.4 자기 검토 효과를 따로 보는 방법

첫 번째 비교(6.1)는 자기 검토를 끕니다. 두 번째 비교(6.2)는 켭니다. 같은 실행
환경에서 두 결과를 나란히 놓으면 자기 검토가 얼마나 기여했는지 보입니다. 여기에
7.1부터 7.3까지의 횟수를 나눠 기록해 두면, 성적이 오른 이유가 자기 검토인지 단순히
여러 번 시도해서인지 구분할 수 있습니다.

## 8. 모든 실행에서 공통으로 남길 기록

실행 환경이 무엇이든 아래 항목을 모두 남깁니다. 나중에 다른 사람이 결과를 다시

| 기록할 내용 | 코드에서 쓰는 이름 |
|---|---|
| 사용한 모델과 배포 환경 | `model_and_deployment` |
| 시스템 지시문 | `system_instruction` |
| 작업 지시문 | `task_instruction` |
| 작업 목록 | `task_ids` |
| 입력 파일 버전 | `input_file_versions` |
| 실행한 코드 버전 | `executed_code_version` |
| 실행 시작 시각 | `started_at` |
| 실행 종료 시각 | `finished_at` |
| 전체 소요 시간 | `total_seconds` |
| 모델 호출 횟수 | `model_call_count` |
| 도구 실행 횟수 | `tool_run_count` |
| 재시도 횟수 (7장의 세 종류를 각각) | `retry_counts_by_reason` |
| 생성한 파일 | `produced_files` |
| 파일 검사 결과 | `produced_file_check_results` |

의도된 것입니다.

**기존 기록과의 관계**: 이 저장소는 이미 실행 시간, 모델 호출 횟수, 도구 실행 횟수,
자기 검토 횟수를 남기고 있습니다
(`batch-runner/step2_run_inference.py` 544행).
비교 실험에서 새로 추가해야 하는 것은 7장의 세 종류로 나눈 재시도 횟수와, 실행 환경
격리 조건입니다.

## 9. 실행 규모 세 단계

실제 실행 전에 각 단계의 조건을 확정합니다. 확정하지 않은 채로 시작하면, 결과가
나쁠 때 기준을 뒤늦게 바꾸고 싶은 유혹이 생깁니다.

| 단계 | 작업 수 | 코드에서 쓰는 이름 |
|---|---|---|
| 사전 점검 | 5 | `advance_check` |
| 예비 실험 | 30 | `trial_run` |
| 전체 실험 | 220 | `full_run` |

### 9.1 각 단계에서 실행 전에 적어야 할 여덟 가지

| 적어야 할 내용 | 코드에서 쓰는 이름 |
|---|---|
| 사용할 작업 목록 | `task_ids` |
| 작업 선택 방법 | `task_selection_method` |
| 성공 판단 기준 | `success_criteria` |
| 실행을 중단할 조건 | `stop_conditions` |
| 다음 단계로 넘어갈 조건 | `advance_conditions` |
| 예상 최대 비용 | `maximum_expected_cost` |
| 허용할 재시도 사유 | `allowed_retry_reasons` |
| 허용할 자기 검토 횟수 | `allowed_self_review_attempts` |

검사 도구의 `check_run_size_plan`이 세 단계 모두에 대해 여덟 항목이 채워졌는지,
작업 수가 5·30·220과 맞는지, 같은 작업이 중복되지 않았는지 확인합니다.

### 9.2 단계별 권장 내용

아래는 실행하는 사람이 채워 넣을 때 참고할 기본 형태입니다. 실제 값은 실험을
시작하는 사람이 그때 정하고, 정한 뒤에는 바꾸지 않습니다.

**사전 점검 (5개 작업)**

- 목적: 다섯 환경이 같은 조건으로 실제로 켜지는지만 확인합니다. 성적을 보지
  않습니다.
- 작업 선택 방법: 결과물 형식이 서로 다른 5개를 고릅니다. 예를 들어 스프레드시트,
  문서, 발표자료, 그림, 글만 있는 작업을 하나씩 고르면 형식별 문제를 빨리 찾을 수
  있습니다. 고른 목록과 고른 이유를 실행 전에 적습니다.
- 성공 판단 기준: 실행 가능한 모든 환경에서 5개 작업이 오류 없이 끝나고, 3장의
  고정 조건이 환경마다 똑같이 기록됩니다.
- 중단 조건: 10장 참고.
- 다음 단계로 넘어갈 조건: 위 성공 기준을 모두 만족하고, 8장의 기록 항목이 빠짐없이
  남았을 때.

**예비 실험 (30개 작업)**

- 목적: 환경 사이에 실제로 차이가 있는지 처음으로 봅니다.
- 작업 선택 방법: 전체 220개에서 분야별 비율을 유지하면서 30개를 고릅니다. 무작위로
  고르는 경우 고정된 난수 씨앗값을 함께 적어, 나중에 같은 목록을 다시 만들 수 있게
  합니다.
- 성공 판단 기준: 실행 가능한 환경 전부가 30개를 끝내고, 채점까지 마칩니다.
- 다음 단계로 넘어갈 조건: 위 기준을 만족하고, 예상 비용이 전체 실험에서 감당

- 작업 선택 방법: 전체 220개를 순서까지 고정해서 씁니다.
- 성공 판단 기준: 실행 가능한 환경 전부가 220개를 끝냅니다.
- 다음 단계로 넘어갈 조건: 없습니다. 마지막 단계입니다.

## 10. 실행을 중단해야 하는 조건

아래 중 하나라도 해당하면 **즉시 멈추고, 무엇이 부족한지 기록합니다.** 다른 실행
환경으로 바꿔서 계속하지 않습니다.

1. 어떤 환경에서든 실제 응답을 만든 모델 이름이나 배포 이름이 다른 환경과 다를 때
2. 지시문, 작업 목록, 입력 파일 지문 중 하나라도 환경 사이에 다를 때
3. 자동 모델 전환이 켜져 있을 때
4. Docker 컨테이너 환경에서 컨테이너를 못 쓰게 됐는데 서버 운영체제에서 대신
   실행되고 있을 때
5. Agentic Sandbox V2의 세 가지 차단(5.5 참고) 중 하나라도 우회된 흔적이 있을 때
6. 유료 실행 승인 없이 유료 모델 호출이 일어나려 할 때
7. 8장의 기록 항목 중 하나라도 남지 않을 때
8. 실제 비용이 해당 단계에 적어 둔 예상 최대 비용을 넘었을 때
9. 구현 상태나 필수 조건을 확인할 수 없을 때 — 이때는 "괜찮을 것"으로 넘기지 않고
   "근거가 부족해 판단할 수 없음"으로 기록하고 멈춥니다

## 11. 실행 가능 여부 검사 도구

### 11.1 무엇인가

실제 모델을 한 번도 부르지 않고, 돈을 한 푼도 쓰지 않고, "지금 비교 실험을 시작해도
되는가"를 판정하는 도구입니다.

- 판정 논리:
  `batch-runner/core/execution_environment_readiness.py`
- 명령줄 실행:
  `batch-runner/scripts/check_execution_environment_readiness.py`
- 자동 테스트:
  `batch-runner/tests/test_execution_environment_readiness.py`
- 이 계획서를 정말 읽을 수 있는지에 대한 자동 테스트:
  `batch-runner/tests/test_the_free_check_reads_the_plan_it_guards.py`
  (위 테스트는 자기가 만든 계획서로만 돌려 봅니다. 커밋된 계획서에 대고
  돌려 보는 것은 이쪽입니다 — 13.29 참고)

### 11.2 어떻게 실행하는가

```bash
cd batch-runner

# 이 저장소와 이 컴퓨터의 상태만 보고 판정
python scripts/check_execution_environment_readiness.py

# 실험 계획 파일까지 함께 검사
python scripts/check_execution_environment_readiness.py --plan 계획파일.yaml

# 다른 프로그램이 읽을 수 있는 형태로 출력
python scripts/check_execution_environment_readiness.py --json
```

**비교할 환경이 전부 지금 시작할 수 있고 문제도 없을 때만** 종료 코드가 0입니다.
환경 하나라도 차단돼 있거나 문제가 하나라도 있으면 1을 돌려주므로, 자동 작업에
그대로 연결해도 안전합니다.

비교할 환경은 계획 파일에 고정 조건을 적어 둔 환경들입니다. 계획 파일을 주지
않으면 다섯 환경 전부를 비교 대상으로 보며, 그 경우 오늘은 반드시 1을 돌려줍니다.
넷째·다섯째 환경이 아직 실행될 수 없기 때문입니다. **차단된 환경을 빼고 나머지만
돌리는 일은 검사 도구가 대신해 주지 않습니다.** 계획 파일에서 사람이 명시적으로
빼야 합니다.

### 11.3 무엇을 확인하는가

| 확인 항목 | 확인 방법 |
|---|---|
| 필수 설정이 모두 있는가 | 3장 열다섯 항목과 9장 여덟 항목이 비어 있지 않은지 확인 |
| 다섯 환경의 실행 경로가 실제로 구현돼 있는가 | 실행 방식 이름 목록을 코드에서 직접 읽고, 각 환경을 담당하는 클래스를 실제로 불러와 확인 |
| 모델과 배포가 모든 비교에서 같은가 | 환경별 고정 조건을 서로 비교. 하나라도 다르면 어느 환경끼리 갈라졌는지 보고 |
| 자기 검토와 재시도 설정이 비교에 맞는가 | 첫 번째 비교면 다섯 환경에서 똑같아야 하고 자기 검토가 꺼져 있어야 함. 두 번째 비교면 달라도 됨 (3.1.1 참고) |
| 허용되지 않은 자동 모델 전환이 있는가 | 자동 전환 허용값이 참이면 문제로 보고 |
| Agentic Sandbox V2 차단을 우회하지 않는가 | 세 가지 차단을 **실제로 실행해 보고** 거부하는지 확인. 글자 검색이 아니라 동작 확인. 차단이 사라졌을 때 다른 이유로 거부되는 것을 통과로 오해하지 않도록, 나머지 조건을 모두 채운 뒤 확인함 |
| 승인 없이 유료 호출로 넘어가지 않는가 | 승인 표시가 없으면 "실행 가능"이던 환경을 전부 "차단됨"으로 내리고, 종료 코드도 1이 됨 |

### 11.4 승인 표시

유료 모델 호출을 승인했다는 표시는 환경 변수
`EXECUTION_COMPARISON_PAID_RUN_APPROVED`에 `yes`를 넣는 것입니다. 다른 값은
모두 승인하지 않은 것으로 봅니다. 승인 표시가 없으면 실행 가능한 환경도 전부
차단 상태가 되므로, 실수로 실험이 시작되지 않습니다.

### 11.5 지금 이 저장소에서 실행한 결과

```
서버 운영체제의 별도 Python 프로세스  → 유료 실행 승인이 없어 차단됨
Docker 컨테이너                     → 컨테이너 필수 설정이 계획에 없어 판단 불가
Azure Code Interpreter              → Azure 연결 설정이 없어 판단 불가
Agentic Sandbox V2                  → 모델을 호출하지 않는 구조 검사만 가능
Codex 기본 에이전트                  → 현재 저장소에 구현되지 않음
```

종료 코드는 1입니다.

1번 환경이 "차단됨"인 것은 코드가 없어서가 아니라 유료 실행 승인이 없기 때문입니다.
승인이 생기면 같은 도구가 자동으로 "현재 실제 실험 실행 가능"으로 바꿔 보고합니다.

### 13.2 고정한 5개 작업

작업을 사람이 고르지 않았습니다. 결과를 보기 전에 정해 둔 규칙이 고릅니다. 규칙은
`batch-runner/core/execution_envelope_tasks.py`에 있고, 검사 도구가 실행할 때마다
다시 계산해서 파일에 적힌 목록과 대조합니다.

**규칙**: 벤치마크의 모든 작업을 작업 번호 오름차순으로 정렬합니다. 그다음
스프레드시트, 문서, 발표자료, 그림, 글만 있는 작업 순서로 다섯 자리를 채웁니다.
각 자리에는 아직 뽑히지 않았고 직업이 겹치지 않으면서 **사람 전문가가 제출한 답안
파일이 모두 그 형식인** 작업 중 번호가 가장 작은 것을 넣습니다. 그런 작업이 벤치마크에
없으면, 답안 파일 중 하나라도 그 형식인 작업 중 번호가 가장 작은 것을 넣습니다.

이 규칙은 작업 번호, 산업, 직업, 그리고 사람 전문가가 낸 답안 파일의 확장자만
읽습니다. 점수는 읽지 않습니다.

| 결과물 형식 | 작업 번호 | 직업 | 전문가가 낸 답안 |
|---|---|---|---|
| 스프레드시트 | `02aa1805-c658-4069-8a6a-02dec146063a` | Project Management Specialists | `.xlsx` 파일 |
| 문서 | `0112fc9b-c3b2-4084-8993-5a4abb1f54f1` | Nurse Practitioners | `.pdf` 파일 |
| 발표자료 | `2ea2e5b5-257f-42e6-a7dc-93763f28b19d` | Computer and Information Systems Managers | `.pptx` 파일 |
| 그림 | `3baa0009-5a60-4ae8-ae99-4955cb328ff3` | News Analysts, Reporters, and Journalists | `.jpg` 파일과 `.pdf` 파일 |
| 글만 | `0818571f-5ff7-4d39-9d2c-ced5ae44299e` | Real Estate Brokers | 파일 없음, 글만 |

다섯 형식, 다섯 직업, 네 산업입니다.

**그림 자리에 대한 정직한 기록**: 이 벤치마크에는 그림 파일 **하나만** 내는 작업이
없습니다. 그림을 내는 작업은 두 개뿐이고 둘 다 문서를 함께 냅니다. 그래서 규칙의
두 번째 문장이 적용됐습니다. 없는 것을 있는 것처럼 적지 않았고, 다른 형식으로
바꿔 채우지도 않았습니다.

### 13.3 선택이 점수를 따라가지 않았음을 확인하는 값

### 13.5 Docker 컨테이너가 서버 운영체제로 넘어가지 못하게 막는 방법

5.3에 적은 위험이 이번 준비 단계에서 가장 중요한 문제입니다. 이 일이 벌어지면
비교표의 Docker 칸에 사실은 서버 칸의 숫자가 들어가고, **표를 보는 사람은 그것을
알 방법이 없습니다.**

`exp031`의 `use_docker` 값은 `always`입니다. 이 값이면 Docker가 없거나 이미지가
없을 때 작업이 실패로 기록되고 끝납니다. 서버로 넘어가지 않습니다.

`batch-runner/tests/test_execution_envelope_docker_containment.py`가 이것을 세 방향에서
고정합니다.

1. **동작 확인**: Docker가 없는 상태와 이미지가 없는 상태에서 실제로 실행 경로를
   불러 보고, 서버 실행기가 한 번이라도 불리면 테스트가 실패합니다.
2. **설정 확인**: 커밋된 `exp031` 파일의 값이 `always`인지 확인합니다.
3. **검사 도구 확인**: 계획 파일이나 실험 설정 파일에서 이 값을 `auto`나 `never`로
   약하게 만들면 검사 도구가 거부하는지 확인합니다.

네 번째 테스트는 기본값 `auto`가 **실제로** 서버로 넘어간다는 사실을 기록합니다.
그 테스트가 언젠가 실패한다면, 넘어가는 경로가 코드에서 사라졌다는 뜻입니다.

값이 그대로입니다. 자동 테스트가 이 두 줄이 토큰 하나까지 변하지 않는지 확인합니다.

#### 13.6.2 채점 줄이 상한이 아니었던 이유 (#230)

`core/execution_envelope_cost.py`는 첫 줄에서 "여기 모든 숫자는 예측이 아니라
상한"이라고 말합니다. **실행 쪽 절반은 그 약속을 지켰지만 채점 쪽 절반은 지키지
않았습니다.** 채점 비용은 계획 파일에 사람이 손으로 적은 세 숫자에 기대고 있었고,
그중 둘은 이 저장소의 채점 설정이 이미 한도로 정해 둔 값이며, 채점이 부를 수
있는 **모델 두 개는 아예 이름조차 나오지 않았습니다.**

`batch-runner/core/execution_envelope_grading_cost.py`가 실제로 쓰일 채점 설정
파일을 열어 그 한도를 읽고, 계획에 적힌 숫자가 한도 아래에 있으면 보고합니다.
`grading_configs/default_v2.yaml`에 대해 나온 결과는 다섯 가지였습니다.

| 계획에 적혀 있던 값 | 채점 설정이 실제로 허용하는 값 | 지금 상태 |
|---|---|---|
| 채점 항목 하나당 호출 1회 | **11회** (`max_iterations` 10 + 마무리 재시도 1) | 11로 올림 |
| 응답 하나당 1,000토큰 | **2,400토큰** (`judge.generation.max_output_tokens`) | 2,400으로 올림 |
| (없음) | 그림 읽기 `gpt-5.4`를 작업당 최대 **72회** | 계산에 넣음 |
| (없음) | 소리 듣기 `gpt-audio-1.5`를 작업당 최대 **3회** | 호출 수는 셈, 금액은 불가 |
| (없음) | `gpt-audio-1.5`는 **가격표에 없습니다** | **남음** |

마지막 줄이 가장 무겁습니다. `check_cost_ceiling`은 "가격이 없는 모델을 공짜로
세지 않기 위해" 이미 거부하도록 되어 있는데, 채점 쪽이 이 모델을 한 번도 이름을
대지 않았으므로 **그 거부가 발동할 기회 자체가 없었습니다.**

**한 숫자는 이 방식으로 고정할 수 없고, 고정한 척하지도 않습니다.** 호출 하나의
입력 길이(10,000토큰)는 채점 대상 답변이 얼마나 긴지에 따라 달라지고 설정 어디에도
그 한도가 없습니다. 이 값은 실제로 있었던 실행에서 나온 관측값으로 남으며
(`baseline_cost_truth.md`의 실측 평균 4,745토큰의 두 배 남짓),
`describe_grading_caps`가 "이 숫자만은 상한이 아니다"라고 직접 밝힙니다.

**한도는 문서가 아니라 코드에서 읽습니다.** 자동 테스트가 커밋된 채점 설정 아홉
개마다 `core/grader.py`로 진짜 채점기를 만들어 이 모듈이 읽은 한도와 대조하므로,
`core/grader.py`가 한도를 다르게 읽기 시작하면 그 자리에서 실패합니다.

**무료 검사의 출력도 바뀌었습니다.** "가장 큰 청구 금액" 항목 바로 밑에 그 합계가
너무 낮다는 경고가 함께 나옵니다. 아래쪽 문제 목록에만 적어 두고 합계는 최종값처럼
읽히게 두면, 낮다고 이미 알려진 숫자가 상한으로 인용됩니다.

#### 13.6.3 그림 읽기와 소리 듣기를 세는 계산 (#231)

13.6.2가 남긴 문제는 **계획 파일의 숫자를 올려서 풀 수 있는 것이 아니었습니다.**
비용 계산식에 그림 읽기와 소리 듣기를 담을 칸이 아예 없었기 때문입니다. 그 칸을
만든 것이 이 수정입니다.

계획 파일에 `grading_perception` 항목이 생겼습니다. 종류마다 **어느 모델을, 작업
하나당 몇 번, 한 번에 얼마나 보내고 얼마나 돌려받는지**를 적습니다. 호출 횟수는
채점 설정에서 읽어 대조하고, 어긋나면 거부합니다.

**두 종류의 거부를 구분합니다.** 둘 다 막지만 이유가 다르고, 고치는 방법도 다릅니다.

| 거부 이유 | 뜻 | 무엇을 해야 풀리나 |
|---|---|---|
| 가격이 없다 | 그 모델의 정가를 아무도 모른다 | 가격표에 정가를 넣어야 합니다 |
| 크기를 모른다 | 정가는 알지만 한 번에 몇 토큰인지 모른다 | 실제로 재 봐야 합니다 |

**그림 읽기의 숫자는 실측에서 왔습니다.** 저장소에 커밋된 모든 채점 실행에서
그림 모델을 실제로 부른 채점 항목 **817개**를 세었습니다. 한 번에 보낸 입력의
최댓값은 23,139토큰이었고 계획에는 24,000을 적었습니다. 돌려받은 응답의
최댓값은 3,202토큰이었고 4,000을 적었습니다.

**평균이 아니라 최댓값을 쓴 이유**가 바로 13.6.2가 고친 실수입니다. 같은 817개의
입력 평균은 2,123토큰으로, 이 저장소가 원래 쓰던 "실측 평균의 두 배" 방식이었다면
4,246이 되어 **실측 최댓값보다 낮은 값**이 나왔을 것입니다. 실제로 있었던 호출보다
낮은 숫자는 상한이 아닙니다.

**소리 듣기의 숫자는 일부러 비워 두었습니다.** 커밋된 모든 채점 실행에서 소리로
넘어간 채점 항목은 116개였지만, 소리 모델이 실제로 불린 횟수는 **0회**입니다.
전부 글 채점기가 판정했습니다. 그래서 실측할 값 자체가 없습니다.

여기에 0을 적으면 "이 호출은 공짜"라는 뜻이 되고, 아무 숫자나 적으면 없는 근거를
지어내는 것입니다. 그래서 빈칸으로 두었고, **빈칸은 거부로 처리됩니다.**

**이 수정으로 원래 있던 안전 장치가 처음으로 작동했습니다.** `gpt-audio-1.5`라는
이름이 처음으로 가격표 조회에 넘어갔고, "가격이 없는 모델은 거부한다"는 규칙이
이 모델에 대해 처음으로 발동했습니다.

남은 문제는 **두 가지이고 둘 다 같은 모델에 대한 것**입니다. 한 번도 부른 적이 없어
크기를 모르고, 가격표에 없어 값을 모릅니다. 나머지 셋은 닫혔습니다.

**금액이 오른 것은 나빠진 것이 아닙니다.** 43.77에서 364.00로 올랐지만, 부를 수
있는 호출은 예전과 똑같습니다. 예전 숫자가 그 호출들을 세지 않았을 뿐입니다.
숨어 있던 비용이 보이게 된 것이지 새로 생긴 것이 아닙니다.

**364.00는 계산 결과일 뿐 승인된 금액이 아닙니다.** 승인 금액은 32.23 그대로입니다.

#### 13.6.4 요청 한 번에 깔고 들어가는 글을 **실제로 만들어 재도록** 고쳤습니다 (#251)

`instruction_character_count`는 **모든 자리가 모든 호출마다** 내는 값입니다.
문제 지문과 참고 파일을 뺀 나머지 전부가 여기에 들어갑니다.

계획서는 여기에 **1,068자**를 적어 두었습니다. 그 숫자는 계획서가 들고 있는 문구
두 덩어리의 길이를 더해서 나온 값인데, **두 덩어리 다 틀렸습니다.**

- 세고 있던 `system_instruction` **345자는 아무도 안 읽습니다.**
  `core/prompt_loader.py`는 프롬프트 파일에 `system_message`가 있으면 **그쪽을
  쓰고** 실험 설정의 `system`은 버립니다. 커밋된 프롬프트 파일 셋 다 그것을
  가지고 있으므로, 그 345자는 **한 번도 보내지지 않습니다.**
- 정작 **프롬프트 파일 자체는 한 글자도 안 세고 있었습니다.** 보내는 글의 대부분이
  거기에 있습니다.

실제로 만들어서 재 보면 이렇습니다.

| 자리 | 쓰는 프롬프트 파일 | 파일의 지시문 | 파일이 과제를 감싸는 글 | 설정이 더하는 글 | 합계 |
|---|---|---:|---:|---:|---:|
| 서버 운영체제의 별도 Python 프로세스 | `subprocess_occupation_codegen` | 354 | 2,789 | 724 | **3,867자** |
| Docker 컨테이너 | `sandbox_occupation_codegen` | 571 | 3,725 | 724 | **5,020자** |
| Azure Code Interpreter | `code_interpreter_occupation_codegen` | 360 | 2,449 | 724 | **3,533자** |

컨테이너 자리는 **호출마다 3,952자를 덜 세고 있었습니다.**

세는 방법은 **직접 만들어 보는 것**입니다. 새 `fixed_prompt_characters()`가 실제
실행이 쓰는 그 `render_prompt()`로 프롬프트를 두 번 만듭니다 — 파일만으로 한 번,
그 자리의 `condition_a.prompt` 문구를 씌워서 한 번 — 그리고 **각 조각이 얼마나
늘렸는지**를 적습니다. 그래서 조각의 합은 **만들어진 글의 실제 길이**가 되고,
거절 문구가 "무엇으로 이루어진 값인지"를 말할 수 있습니다.

**과제 지문만 빼고 셉니다.** 지문은 과제마다 따로 값을 매기고 있으므로, 여기서 또
세면 **같은 글을 두 번 청구**하게 됩니다.

**직업 이름은 과제 목록표에서 가장 긴 것을 씁니다.** 프롬프트가 직업 이름을 최대
세 번까지 써 넣기 때문입니다. 목록표가 비어 있으면 **거절합니다** — 아무 직업도
안 적힌 프롬프트로 값을 매기지 않기 위해서입니다.

이 수정으로 상한이 **363.59에서 364.00 미국 달러로** 움직입니다. 실행 쪽이
21.00에서 21.33로 오르고, 채점 쪽(269.87)과 인지 쪽은 그대로입니다. **어느
숫자로도 돈은 나가지 않았습니다.** 두 값 모두 승인된 32.23을 넘어 계획서는
그대로 거절되며, 이 수정은 **새 승인을 요청하지 않습니다.**

**남아 있던 하나는 아래 13.6.5에서 셌습니다.** `SandboxRunner._augment_prompt`가
컨테이너의 **첫 요청**에 덧붙이는 제출물 규약·의존성 안내·기술 설명서가 위 표에
빠져 있었고, 그래서 컨테이너에 요구하는 값은 **실제보다 작았습니다.**

**작업 하나가 쓸 수 있는 최대량**: 입력은 그 자리가 보내는 프롬프트를 실제로
만들어 잰 길이(위 표, 최대 5,020자),
문제 지문의 실제 길이, 그리고 참고 자료 파일마다 50,000자를 더한 값입니다. 50,000자는
`core/file_reader.py`가 파일 하나에서 모델에게 보내는 최대 글자 수이므로, 원본 파일이
아무리 커도 이 값을 넘지 않습니다. 글자를 토큰으로 바꿀 때는 3글자를 1토큰으로
셌습니다. 영어는 보통 4글자쯤이 1토큰이므로, 이렇게 세면 상한이 더 크게 나옵니다.
출력은 작업마다 32,768토큰입니다.

**재시도를 모두 썼을 때**: 첫 시도 1회에 인프라 재시도 3회를 더해 작업당 4회입니다.
자기 검토는 꺼져 있으므로 더하지 않습니다.

**Azure Code Interpreter의 호출 수가 많은 이유**: 이 서비스는 모델의 Python을 대신
실행하고, 실행 결과를 들고 모델에게 여러 번 되돌아갈 수 있습니다. Microsoft 문서에
그 횟수의 상한이 나와 있지 않습니다. 그래서 여기서 8회로 정했습니다. 다만 응답
하나의 최대 생성량은 도구 왕복을 모두 합쳐 한 번만 적용되므로, 출력 쪽은 시도당
한 번만 셌습니다.

**채점 비용**: 채점 항목 하나마다 채점 호출 **11회**로 셌습니다. 채점 설정이
허용하는 최대치이며(도구 왕복 10회 + 마무리 답 1회), 실제 실행이 그만큼 썼기
때문이 아니라 **그만큼 쓸 수 있기 때문**에 그 값을 씁니다. 호출 한 번의 입력은
10,000토큰으로 셌습니다. `tasks/rebuilding_grading_task/baseline_cost_truth.md`의
실측 평균은 4,745토큰(84회에 398,629토큰)이므로 두 배 남짓 여유가 있습니다.
여기에 그림 읽기가 작업당 72회씩 더해집니다(13.6.3).

**가격표에 대한 정직한 기록**: 이 값들은 저장소에 적힌 정가이지 청구서에서 확인한
값이 아닙니다. 협상 단가를 쓰는 경우 실제 호출 전에 바꿔야 합니다.

#### 13.6.5 컨테이너가 **첫 요청에만** 덧붙이는 글도 세도록 고쳤습니다

13.6.4의 표는 `render_prompt()`가 만든 글만 잰 값입니다. 그런데 컨테이너 자리는 그 앞에
한 단계가 더 있습니다. `SandboxRunner._run_attempt`는 `_augment_prompt`를 **먼저**
부르고, **그 결과물**을 `render_prompt`에 "과제 지문"이라며 넘깁니다. 그리고
`fixed_prompt_characters`는 과제 지문 자리에 **일부러 한 글자짜리 대역**을 넣고
잽니다 — 지문을 두 번 청구하지 않으려고 그렇게 만든 것입니다. 그래서
`_augment_prompt`가 붙인 글은 **전부 그 한 글자에 가려져** 한 글자로 세어졌습니다.

실제로 만들어서 재 보면 이렇습니다.

| 조각 | 누가 만드나 | 길이 |
|---|---|---:|
| 제출물 규약 | `infer_deliverable_contract()` | 1,365자 |
| 의존성 안내 | `dependency_resolver.resolve()` | 922자 |
| 기술 설명서 | `SkillsRegistry.render_manual()` | **0자** — 설정이 `max_skills: 0`이라 꺼져 있습니다 |
| | **합계** | **2,287자** |

그래서 컨테이너의 첫 요청은 **5,020 + 2,287 = 7,307자**입니다. 계획서의
`instruction_character_count`를 5,020에서 **7,307로** 올렸습니다. 나머지 두 자리는
`_augment_prompt`를 아예 갖고 있지 않아 3,867자와 3,533자 그대로이고, 하나뿐인 이
값은 셋 중 가장 큰 값이어야 하므로 7,307이 셋 모두를 덮습니다.

**길이를 손으로 적지 않았습니다.** 새 `core/first_request_sections.py`는 위 세
함수를 **실제 실행이 부르는 그대로** 부르고, 실제 실행과 **같은**
`assemble_sections()`로, 그 자리의 프롬프트 명세가 정한 **순서 그대로** 늘어놓은
뒤 길이를 잽니다. 표의 숫자는 그렇게 나온 값이고, 저 문구 중 하나라도 고치면
숫자가 따라 움직입니다.

**얼마나 넓게 잡았나.** 셋 중 둘은 과제 지문의 낱말을 읽습니다. 그런데 과제
목록표에는 지문의 **길이**는 있어도 **지문 자체**는 없습니다. "아무 낱말도 안
걸렸겠지"라고 하면 못 읽은 값을 0으로 처리하는 것이므로, 대신 **커밋된 표가 만들 수
있는 가장 넓은 지문**으로 몰아 잽니다 — `detection_vocabulary()`가 걸 수 있는 모든
낱말, `KEYWORD_PACKAGES`의 모든 열쇠말, `EXT_PACKAGES`의 확장자마다 파일 하나,
그리고 기술 설명서 꾸러미들이 스스로 적어 둔 확장자와 열쇠말 전부입니다. 의존성
안내는 **빈 이미지**를 상대로 풉니다 — 그 안내의 경고문이 "이미지에 없는 꾸러미"를
줄줄이 적는 글이라, 전부 없을 때 가장 길어지기 때문입니다. 실제 과제는 여기에 한참
못 미치므로 이 값은 **더 많이 청구합니다.** 상한은 원래 그래도 되는 방향이고, 대신
저 표들에 낱말을 더해도 **청구를 피해 갈 수 없게** 됩니다.

**같은 글을 두 번 청구하지 않습니다.** 과제 지문은 과제마다, 참고 자료는 파일마다
같은 계산서의 **다른 칸**에서 이미 값을 매기고 있습니다. `SECTIONS_PRICED_SOMEWHERE_ELSE`가 그 조각들을
하나씩 이름과 **어디서 세는지**까지 적어 두고,
`classify_every_section()`이 **둘 중 어느 쪽에도 없는 조각**이 새로 생기면
거절합니다. 값을 안 매긴 채 조용히 실려 나가는 조각이 없도록 하는 장치입니다.

**못 읽으면 0이 아니라 거절합니다.** 기술 설명서 꾸러미 폴더를 못 읽었을 때,
프롬프트 파일이 없을 때, `max_skills`가 정수가 아닐 때, 그리고 **그 자리의 실행기가
자기가 뭘 덧붙이는지 아예 안 적어 놨을 때** — 전부 거절합니다. 특히 마지막이
중요합니다. `FIRST_REQUEST_EXTRA_SECTIONS`가 빈 괄호인 것은 "나는 아무것도 안
붙인다"는 **주장**이고 Azure와 서버 프로세스 자리에서는 참이지만, 아무 말도 없는
것은 주장이 아니라 **침묵**입니다. 침묵을 0으로 세는 것이 바로 이 조각들이 그동안
공짜로 실려 나간 이유였습니다.

이 수정으로 상한이 **363.99643750에서 364.23468750 미국 달러로** 움직입니다. 실행
쪽이 21.327650에서 21.518250으로 오르고, 채점 쪽(215.8695)과 인지 쪽(54.00)은
그대로입니다. **어느 숫자로도 돈은 나가지 않았습니다.** 2026-08-28 정책대로 비용은
**기록 전용**이므로 이 숫자가 실행을 막지는 않으며, 비용 밖의 보안·계정 차단은
**그대로 남아 있습니다.**

길이 하나는 **세 자리 전부**에 걸립니다. 계획서의 `instruction_character_count`는
자리마다 따로 있는 게 아니라 **하나뿐이고**, 셋 중 가장 넓은 자리에 맞춰 둡니다.
그래서 컨테이너 때문에 올린 값이 Azure 자리(14.33 → 14.48달러)와 서버 프로세스
자리(3.51 → 3.53달러)도 같이 올립니다. 이건 실수가 아니라 **의도한 여유**입니다 —
상한은 재는 대상보다 조심스러워도 되고, 모자라기만 하면 안 됩니다.

**딸려 나온 것 하나.** 전체 테스트를 돌리니 `test_catalogue_counts_could_be_true.py`
하나가 깨졌습니다. 상한을 **반올림해서** `"364.00"`으로 적어 둔 테스트였고, 제가
정밀한 숫자(`363.99643750`)로만 찾아봐서 놓쳤던 자리입니다. 고치면서 같은 숫자를
**글로 적어 둔 자리 네 곳**이 더 나왔고, 전부 다시 재서 맞췄습니다:

| 자리 | 옛 값 | 다시 잰 값 |
|------|-------|-----------|
| 채점 줄 0으로 만들 때 (`execution_envelope_tasks.py` 설명글, 테스트 2곳) | 364.00 → 94.16 | **364.24 → 94.40** |
| Azure 한도 주장 뒤집을 때 전체 | 414.17 | **414.42** |
| 같은 경우 Azure 한 줄 | 14.32 → 54.46 (3.80배) | **14.48 → 54.62 (3.77배)** |
| 컨테이너 2턴에서 잘못 `true` 할 때 | 369.40 → 365.30 | **369.67 → 365.57** |

없어진 금액 **269.84달러는 그대로**입니다. 제가 고친 건 실행 쪽뿐이고 채점 쪽은
안 건드렸으니, 채점을 0으로 만들 때 빠지는 액수가 안 변하는 게 **맞는 결과**입니다.

이 네 곳은 **아무도 안 읽고 있었습니다.** 그래서 설명글이 지금 값을 인용하는지
확인하는 테스트를 새로 넣었습니다. 일부러 옛 숫자로 되돌려 **걸리는 것까지**
확인했습니다. 값을 글로 적어 두면 다시 계산되지 않으니, 읽어 보는 쪽을
만들어 둔 것입니다.

### 13.7 실제 호출 직전까지의 무료 사전 점검

`batch-runner/scripts/check_execution_envelope_advance_check.py`

```bash
cd batch-runner
python scripts/check_execution_envelope_advance_check.py
python scripts/check_execution_envelope_advance_check.py --json
```

아래 중 하나라도 해당하면 종료 코드 1을 돌려주고 실행을 막습니다.

| 막는 조건 | 확인 방법 |
|---|---|
| 설정 누락 | 3장 열다섯 항목과 9장 여덟 항목이 비어 있는지 확인 |
| 다른 모델·배포 사용 | 세 실험 설정 파일을 실제로 열어 배포 이름과 모델 이름을 고정 조건과 대조 |
| 다른 지시문·작업 목록·입력 파일 사용 | 세 파일의 지시문 원문을 글자 단위로 대조하고, 작업 목록을 고정 규칙으로 다시 계산해 대조하고, 입력 파일 확인 값을 데이터 저장소 경로와 대조 |
| 한 곳만 다른 설정을 씀 | `condition_a`의 모델·프롬프트·채점자 항목과 `data.filter` 안의 **모든 값**이 세 파일에서 같은지 대조. 비교할 항목 이름을 적어 두지 않고 **파일에서 읽어 정하므로**, 나중에 추가된 설정도 자동으로 대조됩니다 (13.10) |
| 자동 환경 전환 | 계획 파일과 `exp031` 양쪽에서 컨테이너 필수 설정이 `always`인지 확인 |
| 자동 모델 전환 | 자동 전환 허용값이 참이면 거부 |
| 승인 누락 | `EXECUTION_COMPARISON_PAID_RUN_APPROVED`가 `yes`가 아니면 실행 가능한 환경도 전부 차단으로 내림 |
| 비용 상한 초과 또는 미지정 | 계산한 상한을 승인 금액과 대조. 승인 금액이 비어 있으면 통과가 아니라 거부. 가격이 없는 모델은 공짜로 세지 않고 거부 |
| 채점 비용이 상한이 아님 | 계획이 지목한 채점 설정 파일을 열어 한도를 읽고, 계획에 적힌 숫자가 그 아래면 거부. **계획이 채점을 하겠다면서 설정 파일을 지목하지 않아도 거부** — 아무것도 확인하지 않은 것은 "숫자가 충분하다"가 아닙니다 |
| Agentic Sandbox V2 차단 우회 | 세 가지 차단을 실제로 실행해 보고 거부하는지 확인 |
| 실행할 수 없는 환경을 비교에 넣음 | 4·5번 환경을 계획에 넣으면 거부 |

**차단된 환경을 빼고 나머지만 돌리는 일은 이 도구가 대신 해 주지 않습니다.**

### 13.10 프롬프트의 절반만 대조하고 있었습니다 (2026-08-26 수정)

이 비교의 주장은 단 하나입니다. **"실행 장소 말고는 아무것도 다르지 않다."**
그 주장을 사실로 만드는 것이 `check_experiment_files_match_conditions`이고,
돈이 나가기 직전의 마지막 관문입니다.

#### 재 보고 알았습니다

세 설정 파일에 들어 있는 값 **34개를 하나씩 바꿔 보고**, 검사가 알아채는지
세었습니다. 읽어서 판단한 것이 아니라 실제로 바꿔 보고 센 것입니다.

```
알아챈 것   16개
못 알아챈 것 18개
```

18개를 하나씩 따져 보니 대부분은 **원래 달라야 하는 것**이었습니다. 실험 이름,
결과가 올라갈 저장소 주소, 각 실행 장소의 표시 이름 — 셋이 같으면 오히려 이상합니다.

그런데 그 안에 **달라서는 안 되는 것**이 섞여 있었습니다.

#### 프롬프트는 네 조각인데 두 개만 보고 있었습니다

| 프롬프트 조각 | 모델에게 실제로 전달되나 | 검사가 대조했나 |
|---|---|---|
| `system` (기본 지시문) | **아니요** | **예** |
| `prefix` (작업 앞에 붙는 말) | **예** | 아니요 |
| `body` (그 다음에 붙는 말) | **예** | 아니요 |
| `suffix` (작업 뒤에 붙는 말) | 예 | 예 |

**대조하던 쪽이 안 가고, 안 대조하던 쪽이 갑니다.**

`core/prompt_loader.py`는 `prefix + body + 작업 문장 + suffix`를 이어 붙여
모델에게 줍니다. 반대로 `system`은 각 실행 장소가 불러오는 코드 생성 프롬프트가
자기 것을 이미 갖고 있어서 **덮어써집니다.** 설정 파일에 기본 지시문을 적어 놓고
"고정했다"고 믿은 사람은 아무것도 고정하지 않은 것입니다.

세 파일 중 **하나에만** `prefix`를 넣어 보았습니다.

```
사전 점검이 지적한 문제 : 없음
설정 검사가 낸 오류      : 없음
그런데 실제로 쓰이는 값  : '!!!ONLY THIS RUN PLACE!!!'
```

한 실행 장소만 다른 말을 듣고 답을 쓰는데, 무료 검사 전부가 조용했습니다.
그 결과표를 본 사람은 **말이 달라서 생긴 차이를 실행 장소 차이로 읽게 됩니다.**

#### 아니었던 것 두 가지 — 확인하고 뺐습니다

의심스러워 보였지만 따져 보니 문제가 아니었던 것도 있습니다. 그대로 적어 둡니다.

- **`sector`·`occupation` 필터** — 조용히 다른 작업을 돌리게 만들지 못합니다.
  `step1_prepare_tasks.py`가 **이미 걸러진 목록**에서 작업을 찾기 때문에, 고정된
  작업이 필터에 걸려 사라지면 그 자리에서 **큰 소리로 멈춥니다.** 다만 그때는
  이미 실행이 시작된 뒤라, 시작 전에 막는 편이 낫습니다. 그래서 넣었습니다.
- **채점자 설정(`qa.model`·`min_score`·`prompt`)** — 지금 안전한 이유는 `qa.enabled`가
  꺼짐으로 고정돼 있고 그건 대조되기 때문입니다. **옆 값 덕분에 안전한 것은
  안전한 게 아니라 운이 좋은 것**이라 함께 넣었습니다.

#### 어떻게 고쳤나 — 이름을 적지 않고 파일에서 읽습니다

원인은 **비교할 항목 이름을 사람이 손으로 적어 둔 것**이었습니다. 세 개가 적혀
있었고, 프롬프트는 네 조각이었습니다.

이제는 이름을 적지 않습니다. 대신 **"여기 있는 값은 전부 같아야 한다"는 자리**를
적어 둡니다.

```
condition_a.model    condition_a.prompt    condition_a.qa    data.filter
```

비교할 항목은 **설정 파일을 열어서 그 안에 실제로 뭐가 들어 있는지 보고 정합니다.**
그래서 나중에 누가 새 설정을 추가해도 **아무도 기억하지 못해도 자동으로 대조됩니다.**
아무도 이름을 적어 둔 적 없는 `top_p`를 한 파일에만 넣어 확인했습니다.

```
the run places disagree on condition_a.model.top_p, so the difference between
their answers would not only be the run place: 0.5: host_python_process |
None: azure_code_interpreter, docker_container
```

#### 고친 뒤

```
알아채는 것   16개 → 23개
못 알아채는 것 18개 → 11개
```

남은 11개는 전부 **원래 달라야 하는 것들**입니다. 실험 이름·설명·작성자,
결과 저장소 주소, 실행 장소 표시 이름, 결과를 어디로 올릴지, 그리고 비교의
내용을 사람 말로 적어 둔 `control` 두 줄입니다.

**지금 저장소에 있는 세 파일은 그대로 통과합니다.** 검사가 더 엄해졌지만 멀쩡한
설정을 막지는 않습니다.

#### 기존 테스트 한 줄을 같이 고쳤습니다

거부 문구가 설정 이름을 **전체 경로로** 부르게 바뀌었습니다. `temperature`가
아니라 `condition_a.model.temperature`입니다. 채점자 설정도 같이 대조하게 되면서
**모델과 채점자가 각각 자기 `model`을 갖게 됐기 때문에**, 짧은 이름만으로는 어느
쪽인지 알 수 없습니다.

기존 테스트 세 개가 짧은 이름을 찾고 있어서 함께 고쳤습니다. **거부 자체는
그대로입니다** — 그 세 설정은 전에도 거부됐고 지금도 거부됩니다. 바뀐 것은
사람이 읽는 문구뿐입니다.

#### 검사 결과

- 신규 테스트 20개, 전부 통과. **그중 11개는 고치기 전 검사 범위에서 실제로 실패합니다**
- `mypy core/`: 기준선과 동일. 고친 파일에서 0개
- 모델 호출 0회, 명령 실행 0회, 승인한 금액 없음. **차단은 하나도 풀리지 않았습니다**


### 13.11 "점수가 안 들어 있음을 증명한다"는 검사가 실제로는 거의 못 잡았습니다 (2026-08-26 수정)

#### 무엇이 틀렸나

13.3절에 "자동 테스트가 파일 전체를 훑어 그런 항목이 없는지 확인합니다"라고
적혀 있었고, 코드 설명에는 더 세게 적혀 있었습니다.

> 점수도 등급도 판정도 들어 있지 않으며, `check_catalog_carries_no_scores`가
> **직접 훑어서 그것을 증명한다.**

실제로 그 검사는 **사람이 손으로 타이핑한 이름 14개**를 갖고 있었고, 그중 하나가
정확히 나올 때만 문제라고 말했습니다. `score`, `grade`, `verdict` 같은 것들입니다.

그 14개가 **이 저장소의 채점 결과 파일이 진짜로 쓰는 이름들과 맞는지** 아무도
대조한 적이 없었습니다.

#### 재어 봤습니다

이 저장소에 이미 올라와 있는 채점 결과 파일 19개를 열어서, 결과를 담고 있는
필드 이름을 **읽어 왔습니다**(손으로 적지 않았습니다). 45개가 나왔습니다.

그 45개를 **하나씩** 작업 목록 파일에 몰래 집어넣고 검사에게 물었습니다.

| | 잡아냄 | 놓침 |
|---|---|---|
| 고치기 전 | **8 / 45** | 37 / 45 |
| 고친 뒤 | **45 / 45** | 0 / 45 |

놓친 37개에는 이런 것들이 있습니다.

```
avg_score   scores      pass_rate     avg_pct       confidence
graded      graded_by   child_grades  critical_fail  num_grades
```

`avg_score`라는 이름으로 점수가 들어와도 검사는 **"깨끗합니다"** 라고 답했습니다.

#### 왜 이런 식이 되나

**금지할 이름을 적는 방식은, 마지막으로 그 목록을 생각한 사람만큼만 똑똑합니다.**
새 이름은 계속 생기고, 목록은 그 자리에 남습니다.

이 저장소에서 같은 모양의 결함을 이번이 여덟 번째로 찾았습니다.

#### 어떻게 고쳤나 — 질문을 반대로 뒤집었습니다

"이 이름이 금지 목록에 있나?"가 아니라 **"이 이름이 파일 형식에 적혀 있는
이름인가?"** 를 묻습니다.

작업 목록 파일의 형식은 이미 코드에 **두 개의 자료 구조**로 적혀 있습니다. 검사는
이제 그 두 곳에서 허용되는 이름을 **읽어 옵니다**. 18개입니다.

| 전 | 후 |
|---|---|
| 금지할 이름 14개를 손으로 적음 | 허용되는 이름 18개를 **형식에서 읽어 옴** |
| 목록에 없는 이름은 전부 통과 | 형식에 없는 이름은 **이름이 무엇이든 거부** |
| 값은 안 봄 | **소수점 숫자와 참/거짓도 거부** |

두 번째 규칙을 덧붙인 이유가 있습니다. 이 파일에 들어 있는 숫자는 **전부 개수**
입니다. 참고 자료가 몇 개, 채점 항목이 몇 개. 그런데 점수는 거의 항상 소수점이
붙은 값이거나 합격/불합격 표시입니다. 그러니 **이미 허용된 이름을 빼앗아** 점수를
숨기는 것도 막힙니다.

#### 이 검사가 못 하는 일 하나 — 적어 두었습니다

글자를 담아도 되는 칸에 점수를 **글로 써 넣으면** 못 잡습니다. 직업 이름 칸에
`"간호사 (0.87점)"`이라고 적는 식입니다.

이건 여기서 고칠 종류의 문제가 아닙니다. 하지만 **"증명한다"고 적어 두는 것보다는
못 하는 일을 적어 두는 편이 낫습니다.** 코드 설명을 그렇게 고쳤고, 그 문장이
지워지면 테스트가 실패합니다.

#### 파일을 만드는 쪽에서 먼저 막습니다

지금 올라와 있는 파일이 깨끗한 이유는, 파일을 만드는 프로그램이 칸을 하나씩 손으로
채우기 때문입니다. 즉 **다음에 누가 "이 값도 넣어 두면 쓸모 있겠다" 하고 한 줄
추가하면** 그대로 들어갑니다.

그래서 파일을 쓰기 **직전에** 같은 검사를 돌리게 했습니다. 문제가 있으면 파일을
아예 만들지 않고 멈춥니다. 실행 직전 점검에서 뒤늦게 발견하는 것보다 낫습니다.

#### 검사 결과

- 신규 테스트 21개. 그중 핵심 하나는 **채점 결과 파일에서 이름을 읽어 와** 45개
  전부가 거부되는지 확인합니다. 이름을 테스트에 옮겨 적지 않았습니다
- 고치기 전 코드에서는 이 파일이 **아예 불러와지지도 않습니다**. 형식에서 이름을

성립하려면 **실행 장소 말고는 전부 똑같아야** 하니까요.

그 검사는 대조할 덩어리 **4개를 손으로 적어** 두고 있었습니다. 모델, 프롬프트,
자기 검토, 작업 목록. 그리고 바로 위에 이렇게 적혀 있었습니다.

> 빠뜨린 덩어리들은 **원래 실행 장소마다 달라도 되는 것들이다.**

이 문장이 맞는지 아무도 대조한 적이 없었습니다.

#### 재어 봤습니다

계획서가 실제로 지목하는 설정 파일 3개를 열어서, 그 안에 든 설정을 **전부 펼쳐**
봤습니다. **44개**였습니다. 4개 덩어리가 덮는 건 **18개**였습니다.

그 44개를 하나씩, **한 환경에서만** 바꿔 놓고 검사에게 물었습니다.

| | 잡아냄 | 놓침 |
|---|---|---|
| 그 규칙 하나만 놓고 보면 (고치기 전) | 18 / 44 | 26 / 44 |
| 그 규칙 하나만 놓고 보면 (고친 뒤) | **26 / 44** | 18 / 44 |
| 검사 전체로 보면 (고치기 전) | 25 / 44 | 19 / 44 |
| 검사 전체로 보면 (고친 뒤) | **30 / 44** | 14 / 44 |

**두 줄로 나눠 적은 이유가 있습니다.** 놓친 26개 중 7개는 사실 **다른 규칙이**
잡고 있었습니다. 계획서가 시간 제한·재시도 횟수·이어하기 횟수·코드 길이를 못
박아 두었고, 파일이 계획서와 어긋나면 그 규칙이 거부했기 때문입니다.

그러니 "시간 제한을 아무도 안 보고 있었다"고 적으면 **과장입니다.** 정확히는
이렇습니다. 그건 **계획서에 적혀 있어서** 덮인 것이지, 파일에 있어서 덮인 게
아닙니다. 계획서에서 그 줄이 빠지는 날 같이 사라집니다.

**어느 규칙도 안 보고 있던 건 19개**였고, 이번에 그중 5개가 보이게 됐습니다.

#### 그 5개 중 하나가 진짜 문제였습니다

컨테이너 환경 설정에 `repair`라는 항목이 있습니다. **코드가 만들어진 다음에**
결과를 보고 반성문을 쓴 뒤 **모델에게 코드를 다시 달라고 요청하는** 되풀이
장치입니다.

그런데 이 비교 실험의 규칙 6.1절은 이렇게 적혀 있습니다.

> 모델은 코드를 쓰기 위해 **한 번만** 불린다. 자기 검토 없음, 재시도 없음.

즉 `repair`는 6.1절이 **문장으로 금지하고 있는 바로 그것**입니다. 그런데
`condition_a.qa`(자기 검토)만 검사하고 있었고, 컨테이너 쪽 통로는 아무도 보고
있지 않았습니다.

#### 더 나쁜 점 — 안 적으면 켜집니다

이게 이번에 가장 조심해야 했던 대목입니다.

`core/sandbox_runner.py`는 이 설정을 이렇게 만듭니다.

```python
self.repair_cfg = {"enabled": True, "max_attempts": 1, **(repair or {})}
```

**`enabled: True`가 먼저 깔려 있습니다.** 그러니 설정 파일에서 `repair` 항목을
**지우면 되풀이 장치가 켜집니다.** 지금 컨테이너 설정 파일에 적혀 있는
`enabled: false`는 장식이 아니라 **일하고 있는 한 줄**입니다.

검사가 "안 적혀 있음"을 "꺼져 있음"으로 읽으면, **가장 위험해진 순간에 깨끗하다고
답합니다.**

제가 처음 짠 규칙이 정확히 그랬습니다. `if not node:` 한 줄 때문에 `repair`
덩어리를 통째로 지우면 문제없다고 답했습니다. 그래서 감시하는 항목마다 **"안 적혀
있을 때 실행기가 실제로 쓰는 값"** 을 같이 적어 두고, 그 값을 **실행기 코드에서
읽어 와** 확인하는 테스트를 붙였습니다.

같은 실수를 한 번 더 했습니다. 컨테이너 환경인지 아닌지를 **"sandbox 덩어리에
내용이 있나"** 로 판단하고 있었는데, **내용이 비어 있는 상태가 바로 되풀이 장치가
켜지는 상태**입니다. 그래서 실행기가 실제로 보는 `execution.mode` 값으로 판단하게
바꿨습니다.

#### 어떻게 고쳤나 — 질문을 반대로 뒤집었습니다

"이 설정이 **대조할 목록**에 있나?"가 아니라 **"이 설정이 달라도 되는 이유가
적혀 있나?"** 를 묻습니다.

| 전 | 후 |
|---|---|
| 대조할 덩어리 4개를 손으로 적음 | 파일에 있는 설정을 **전부** 대조 |
| 목록 밖은 전부 통과 | 예외마다 **이유를 문장으로** 적어야 함 |
| 새로 생긴 설정은 아무도 안 봄 | 새로 생긴 설정은 **자동으로 대조 대상** |

**대조할 것을 적는 목록은, 마지막으로 그 목록을 생각한 사람만큼만 똑똑합니다.**
반대로 **달라도 되는 것을 적는 목록은 한 줄마다 이유를 대야 하고**, 아무도 이유를
대지 않은 것은 기본값으로 검사받습니다.

남은 예외는 5개이고, 각각 이런 이유가 붙어 있습니다.

| 예외 | 이유 |
|---|---|
| `experiment.*` | 실험의 이름·설명·날짜. 답을 바꾸지 않고 실행을 부르기만 함 |
| `condition_a.name` | 보고서에 찍히는 환경 이름표 |
| `data.source` | 준비 단계가 환경마다 저장소를 따로 복제함. 어느 작업을 읽는지는 `data.filter.task_ids`가 따로 못 박음 |
| `execution.mode` | **이 비교 실험이 바꾸려는 바로 그 하나** |
| `execution.sandbox.*` | 컨테이너에만 있는 설정. 컨테이너가 없는 환경과 "어긋난" 게 아님. 단, **코드가 만들어진 뒤 모델을 다시 부르는 것**은 이 예외에 안 들어감. 여기에 하나가 더 붙었습니다 → 13.14 |

마지막 줄이 이번에 붙인 두 번째 규칙입니다.

#### 이 규칙을 다른 비교에는 적용하지 않습니다

비교는 두 가지입니다. 6.1절은 **모델을 한 번만 부르는** 엄격한 비교이고, 6.2절은
**각 도구의 기능을 일부러 켜 둔 채로** 재는 비교입니다.

6.2절에서는 `repair`가 켜져 있는 게 **정상**입니다. 그래서 새 규칙은 6.1절에서만
작동하고, 6.2절에서는 아무 말도 하지 않습니다. 양쪽 다 테스트로 못 박았습니다.

#### 검사 결과

- 신규 테스트 **55개**. 그중 핵심 하나는 설정 이름을 **테스트에 옮겨 적지 않고**
  설정 파일에서 읽어 와, 하나씩 바꿔 보고 **거부되거나 이유가 적혀 있거나** 둘 중
  하나임을 확인합니다
- 같은 측정 스크립트를 **고치기 전 코드와 고친 뒤 코드에 똑같이** 돌렸습니다.
  위 표가 그 결과입니다
- 지금 올라와 있는 설정 파일 3개는 **그대로 통과**합니다. 없는 문제를 만들어 내지
  않습니다
- `mypy`: 오류 170개, 파일 32개 — **기준선과 같음**. 고친 파일에서 새 오류 0개
- 모델 호출 0회, 승인한 금액 없음, 로그인 없음. **차단은 하나도 풀리지 않았습니다**
- 검사는 **더 많이 거부하게** 됐을 뿐입니다

### 13.13 "입력 파일 지문을 전부 대조한다"고 적어 두고, 파일은 한 바이트도 안 읽고 있었습니다 (2026-08-26 수정)

#### 무엇이 문제였나

돈이 나가기 전 마지막 무료 검사의 설명문 열 번째 줄에 이렇게 적혀 있었습니다.

> 모든 입력 파일의 지문을 데이터셋과 대조한다

`check_input_file_versions`가 실제로 한 일은 이렇습니다. 지문은 64자입니다. 이
벤치마크는 참고 파일을 **그 파일 지문의 앞 32자로 이름 붙인 폴더**에 넣어 둡니다.
검사는 적혀 있는 지문의 앞 32자가 그 폴더 이름과 같은지만 봤습니다.

**뒤 32자는 아무것과도 대조하지 않았습니다.** 파일 자체는 열어 보지도 않았습니다.

#### 얼마나 못 잡았는지 재 봤습니다

지금 올라와 있는 계획 파일에 적힌 지문 3개(데이터셋 1 + 참고 파일 2)에 대해,
**64개 자리 전부**에서 글자를 하나씩 바꿔 봤습니다. 표본이 아니라 전수입니다.
같은 스크립트를 고치기 전 코드와 고친 뒤 코드에 똑같이 돌렸습니다.

| | 시도한 변조 | 못 잡은 것 |
|---|---|---|
| **고치기 전** | 210 | **70** |
| **고친 뒤** | 210 | **0** |

못 잡은 70개의 내역입니다.

| 항목 | 못 잡은 수 | 왜 |
|---|---|---|
| 데이터셋 지문 | 0 | 목록(catalogue)에 적힌 값과 64자 전부 대조하고 있었음 |
| 참고 파일 A | 35 | 33~64번째 자리 32개 + 뒤 절반 통째 바꿔치기 3가지 |
| 참고 파일 B | 35 | 같음 |

"뒤 절반 통째 바꿔치기 3가지"란, 뒤 32자를 **다른 참고 파일의 뒤 절반**,
**데이터셋 지문의 뒤 절반**, **아무 상관 없는 파일의 뒤 절반**으로 갈아 끼운
경우입니다. 셋 다 그냥 통과했습니다.

#### 어떻게 고쳤나

**파일을 읽습니다.** 이 컴퓨터에 이미 있는 사본을 찾아 해시를 계산하고, 64자를
전부 대조합니다.

**절대 내려받지 않습니다.** 두 군데만 봅니다.

1. Hugging Face 내려받기 캐시에 **못 박아 둔 그 개정판의 그 파일**이 이미 있는지
   물어봅니다. 없으면 없다고 답할 뿐, 받아 오지 않습니다
2. 사람이 `--dataset-root`로 직접 가리킨 폴더

#### 사본이 없을 때가 진짜 결정이었습니다

사본이 없으면 어떻게 할까요. 조용히 넘어가면 "대조했다"와 "못 했다"가 보고서에서
똑같이 생기게 됩니다. 그래서 **못 했다고 따로 말합니다.**

| 상태 | 뜻 | 대조한 글자 수 |
|---|---|---|
| `read the file` | 파일을 읽고 전부 대조함 | 64 / 64 |
| `folder name only` | 사본이 없어 폴더 이름만 봄 | 32 / 64 |
| `not checked` | 아무것도 대조 못 함 | 0 / 64 |

무료 검사는 **문제가 없을 때에도** 이 표를 찍습니다. 돈을 승인하는 사람이
"읽고 맞았다"와 "맞다고 치고 넘어갔다"를 구별할 수 있어야 하기 때문입니다.
문제 목록에는 **공짜로 해결하는 명령어**가 같이 적힙니다.

이건 이 저장소가 이미 쓰던 규칙과 같습니다. Docker 검사도 `--skip-docker-probe`를
쓰면 "준비됨"이 아니라 **"측정 안 함"**으로 적힙니다.

#### 덤으로 나온 구멍 하나

폴더 이름 규칙은 폴더 이름이 **정확히 32자일 때만** 작동했습니다. 모양이 다른
경로는 대조를 통째로 건너뛰고 **아무 문제도 보고하지 않았습니다.** 확실히 틀린
단 하나의 답입니다. 이제 그런 경로는 `not checked`로 보고됩니다.

#### 사본이 어디서 나왔는지가 "안 맞음"의 뜻을 바꿉니다

참고 파일 경로는 자기 지문의 앞 절반을 그대로 담고 있습니다. 그 경로에 있는
파일은 **그 파일일 수밖에 없습니다.** 그러니 안 맞으면 적힌 지문이 틀린 겁니다.

데이터셋 본체 파일은 그런 약속이 없습니다. 누가 가리킨 폴더에 **다른 개정판**이
들어 있었을 수도 있습니다. 그래서 이 경우에는 "적힌 지문이 틀렸다"가 아니라
**"둘이 서로 다른 파일을 가리킨다"**고만 적습니다. 아는 것보다 더 말하지
않습니다.

#### "못 봤다"와 "안 맞다"는 다른 말이라 목록도 따로 둡니다

처음 만들었을 때는 이 둘을 한 목록에 담았습니다. 그런데 이 컴퓨터에는 벤치마크
파일이 이미 내려받아져 있고, **빌드 서버에는 없습니다.** 그러니 같은 검사가
장소에 따라 다른 답을 냈고, "이거 말고 다른 문제는 없다"를 확인하던 기존 테스트
6개가 빌드 서버에서만 실패했습니다.

두 답은 뜻이 다릅니다.

- **안 맞다** = 계획서가 엉뚱한 파일을 적어 놨다. 어느 컴퓨터에서 돌려도 같은
  답이고, 계획서를 고쳐야 합니다
- **못 봤다** = 이 컴퓨터에 아직 그 파일이 없다. 계획서 잘못이 아니고, 공짜
  명령 한 번으로 없어집니다

그래서 목록을 둘로 나눴습니다. **둘 다 여전히 실행을 막고, 둘 다 여전히 같이
출력됩니다.** 달라진 건 "못 봤다" 쪽에 이름이 붙어서, 다른 걸 확인하는 테스트가
그것만 골라 **의도적으로 제쳐 둘 수 있다**는 점입니다.

여기서 제일 중요한 건 제쳐 두는 방법입니다. 글자를 걸러내는 방식이었다면 **진짜
"안 맞다"까지 같이 걸러질 수 있었습니다.** 그러면 엉뚱한 파일을 적어 놓은 계획서가
테스트 6개를 전부 통과해 버립니다. 그래서 목록에 들어 있는지로 거르고, **"안
맞다"가 저 목록에 절대 들어갈 수 없다**는 사실 자체를 테스트로 못 박았습니다.

#### 검사 결과

- 신규 테스트 **32개**. 그중 하나는 위의 전수 변조 시험을 **작은 가짜 벤치마크로
  다시 만들어**, 64자리 주장이 매번 다시 증명되게 합니다. 두 개는 **내려받기
  보관함을 비운 채로** 돌아갑니다 — 빌드 서버가 딱 그 상태이고, 처음 판은 그
  조건에서 한 번도 돌려 보지 않았습니다
- 지금 올라와 있는 계획 파일의 지문 3개는 이 컴퓨터에서 **전부 읽어서 대조했고
  전부 맞았습니다.** 없는 문제를 만들어 내지 않습니다
- `mypy`: 오류 170개, 파일 32개 — **기준선과 같음**
- 모델 호출 0회, 내려받기 0회, 로그인 없음. **차단은 하나도 풀리지 않았습니다**

### 13.14 "덩어리 하나"에 준 면제가, 프롬프트를 바꾸는 설정까지 덮고 있었습니다 (2026-08-26 수정)

#### 무엇이 문제였나

13.12에서 검사를 뒤집었습니다. "대조할 목록"을 손으로 적는 대신, **파일에 있는 설정을
전부 대조하고, 달라도 되는 것에만 이유를 적게** 했습니다. 예외는 5개만 남겼습니다.

그런데 예외를 적는 방식에 구멍이 있었습니다. 예외는 **설정 이름의 앞부분**으로
적습니다. `execution.sandbox`라고 한 줄 적으면, **그 아래에 있는 설정이 전부** 면제
됩니다. 그때 그 아래에 있던 건 10개였습니다.

9개는 정말로 "컨테이너가 어떻게 생겼는가"입니다. 어떤 이미지를 쓰는지, 메모리가 몇
기가인지, CPU를 몇 개 주는지. 이런 건 컨테이너를 **설명하는** 값이고, 컨테이너가 없는
나머지 두 환경과 "어긋났다"고 말할 수 있는 종류가 아닙니다.

**나머지 하나가 `max_skills`였습니다.**

이 설정은 컨테이너의 생김새와 아무 상관이 없습니다. 이건 **모델에게 주는 지시문에
설명서를 몇 개나 끼워 넣을지**를 정합니다. 코드를 따라가면 이렇습니다.

```
executor.py  →  sandbox_runner.py  →  _augment_prompt  →  prompt_sections
                                                              ↓
                                             "skills_manual" 칸에 들어감
                                                              ↓
                                       skills_registry.render_manual()
                                                              ↓
                                    최대 7,000자짜리 설명서가 프롬프트에
```

그리고 그 설명서가 들어가는 자리는 **작업 지시문보다 앞**입니다.

여기서 중요한 건, 실험 파일 3개가 **스스로 그러지 않겠다고 적어 놨다**는 점입니다.

```yaml
control:
  fixed: [model, tasks, temperature, prompt_strategy]   # 세 파일 전부 똑같이
```

`prompt_strategy`, 즉 **"프롬프트는 셋 다 똑같이 둔다"**. 파일이 약속을 하고 있는데,
면제가 그 약속을 깨는 걸 허용하고 있었습니다.

#### 얼마나 못 보고 있었나

컨테이너 파일의 `max_skills: 0`을 `3`으로 바꾸고 검사를 돌렸습니다.

| | 문제 개수 |
|---|---|
| 바꾸기 **전** | 10개 |
| 바꾼 **후** | 10개 |

**하나도 못 알아챘습니다.** 함께 바꿔 본 `repair.max_attempts`, `manifest.enabled`,
`memory_gb`도 마찬가지였습니다.

#### 없으면 꺼진 게 아니라, 전부 켜집니다

13.12의 `repair`와 **똑같은 함정**이 여기에도 있고, 여기가 더 나쁩니다.

- `executor.py`는 이 설정을 `opts.get("max_skills", 5)`로 읽습니다 → **없으면 5**
- `SandboxRunner`도 같은 값을 5로 둡니다 → **없으면 5**
- 그리고 이 저장소에 있는 설명서는 **정확히 5개**입니다

그러니까 이 한 줄을 **지우면** "설명서를 안 준다"가 아니라 **"있는 설명서를 전부
준다"** 가 됩니다. 컨테이너 파일에 적힌 `max_skills: 0`은 13.12의
`repair: enabled: false`와 똑같이 **지우면 안 되는 줄**이었고, 이제 지우면 거부됩니다.

#### 무엇을 고쳤나

**1. 이 설정에 자기 규칙을 줬습니다.**
`_check_the_container_is_told_no_more_than_the_others`가 `max_skills`가 0이 아니거나
아예 없으면 거부합니다. 검사 전체가 **44개 중 30개 → 31개**를 보게 됐습니다.

이 규칙은 13.12의 규칙과 달리 **두 비교 모두에서** 작동합니다. 6.2절 비교도 파일에
`prompt_strategy`를 고정한다고 적어 놨기 때문입니다. 약속은 어느 쪽에서든 약속입니다.

**2. 면제된 설정 15개에 전부 이유를 하나씩 붙였습니다.**

덩어리에 준 예외는 **덩어리에 대한 주장**입니다. 그 아래 설정들은 "거기 있다"는
이유만으로 면제됩니다. 그건 아무도 주장한 적 없는 면제입니다. 이제
`SETTINGS_EACH_EXCEPTION_COVERS`가 15개 각각에 이유를 적어 두고, **새 설정이 그 아래
생기면 이유를 적을 때까지 테스트가 실패**합니다.

이유를 적다가 하나 더 나왔습니다. `manifest.enabled`는 `manifest.json`을
**결과 파일 목록에 끼워 넣습니다.** 컨테이너만 파일을 하나 더 내놓는다는 뜻입니다.
다만 이건 답이 다 정해진 **뒤에** 만들어져서 모델에게 갈 수 없고, 담고 있는 내용도
"어디서 돌았는가" — 즉 이 실험이 **일부러 바꾸고 있는 그것** — 입니다. 그래서 면제로
두되, **물려받은 면제가 아니라 이유를 적은 면제**가 됐습니다.

#### 검사 결과

- 신규 테스트 **14개** (이 파일 총 69개). 그중 하나는 주석에 적힌 숫자를 **기억에
  맡기지 않습니다**: 설정 44개를 하나씩 바꿔 검사를 돌리고, 도달한 숫자가 주석이
  주장하는 31이 아니면 실패합니다
- 설명서가 정말 프롬프트에 들어가는지는 **진짜 등록기를 호출해서** 확인합니다.
  "없으면 5"라는 값도 `SandboxRunner`를 만들어서 읽어 옵니다. 문장을 믿지 않습니다
- 위의 변조 시험을 다시 돌렸습니다: **0 → 1**. 지우는 경우도 **0 → 1**
- 지금 올라와 있는 설정 파일 3개는 **그대로 통과**합니다
- `mypy`: 오류 170개, 파일 32개 — **기준선과 같음**
- 모델 호출 0회, 승인한 금액 없음, 로그인 없음. **차단은 하나도 풀리지 않았습니다**
- 검사는 **더 많이 거부하게** 됐을 뿐입니다

### 13.15 "한 번 시도에 모델을 몇 번 부르는가"를 계획서에 손으로 적어 두고 있었습니다 (2026-08-26 수정)

#### 한 줄 요약

**두 줄만 지우면 컨테이너는 모델을 두 번 부릅니다. 그런데 비용 계산은 계속
"한 번"이라고 답했습니다. 금액이 1원도 안 움직였습니다.**

#### 무슨 일이었나

비용 계산은 이렇게 합니다. **한 번 시도에 모델을 몇 번 부르는가**를 곱해서
최대 금액을 냅니다. 그 "몇 번"이 계획서에 이렇게 손으로 적혀 있습니다.

```yaml
tool_loop_max_model_turns:
  host_python_process: 1
  docker_container: 1
  azure_code_interpreter: 8
```

세 줄 중 **두 줄은 손으로 적는 게 맞습니다.**

- 서버에서 파이썬만 돌리는 자리(`host_python_process`)는 반복이 **아예 없습니다.**
  모델에게 한 번 물어보고, 나온 코드를 배치 러너가 직접 돌립니다. 1이 구조적으로
  참입니다
- Azure 자리(`azure_code_interpreter`)는 **Azure 안에서** 무슨 일이 일어나는지 이
  저장소에서 읽을 방법이 없습니다. 8은 **우리가 정한 상한**이고, 그렇게 적혀
  있습니다. 정직합니다

**문제는 가운데 줄입니다.** 컨테이너 자리는 그 숫자가 **이 저장소 안 파일에
적혀 있습니다.** 그런데 아무도 그 파일을 읽지 않고 있었습니다.

컨테이너에서 모델을 다시 부르는 길은 두 개입니다.

| 설정 | 하는 일 | **안 적으면** |
|---|---|---|
| `repair` | 코드가 잘못 나오면 **다시 써 달라고 모델에게 부탁**합니다 | **켜집니다** |
| `output_qa.vision` | 만들어진 문서를 그림으로 바꿔 **눈 달린 모델에게 보냅니다** | 꺼집니다 |

`core/sandbox_runner.py`가 `{"enabled": True, ...}`로 만들기 때문에, `repair`
덩어리를 **지우면 켜집니다.** 13.12·13.14와 **또 같은 함정**입니다 — 이번이 세
번째입니다.

#### 실제로 재 봤습니다

지금 올라와 있는 파일에서 `repair` 두 줄을 지우고, 검사를 다시 돌렸습니다.

| 상태 | 컨테이너 호출 수 | 금액 | 거부 건수 |
|---|---|---|---|
| 지금 그대로 | 20회 | 3.47달러 | 10 |
| `repair` 지움, 6.1절 비교 | **20회 그대로** | **3.47달러 그대로** | 11 |
| `repair` 지움, 6.2절 비교 | **20회 그대로** | **3.47달러 그대로** | **10 — 아무도 안 잡음** |

**금액이 한 번도 안 움직였습니다.** 실제로는 모델을 두 배로 부르는데
계산서는 그대로였습니다.

가운데 줄에서 거부 건수가 10 → 11로 는 건 **이 문제를 잡아서가 아닙니다.**
13.12에서 만든 다른 규칙("6.1절 비교에서는 모델을 두 번 부르면 안 된다")이
자기 이유로 막은 것뿐입니다. 그게 오히려 **낡은 금액을 가려 주고** 있었습니다.

그리고 맨 아랫줄 — **6.2절 비교에서는 아무도 안 막았습니다.** 이 비교는 같은
계획서가 이름을 적어 놨고, 채점판도 따로 있습니다. 여기서는 컨테이너 반복이
**켜져 있는 게 정상**입니다. 그러니 13.12 규칙은 (맞게) 가만히 있고, 금액만
조용히 모자랐습니다.

#### 무엇을 고쳤나

**1. 숫자를 컨테이너 설정에서 계산합니다.**

```
코드 쓰는 횟수  = 1 + (repair가 켜져 있으면 그 예산, 꺼져 있으면 0)
그림 검사 횟수  = 코드 쓰는 횟수 × (그림 검사가 켜져 있으면 1, 아니면 0)
```

이 식은 `core/sandbox_runner.py`가 실제로 도는 방식 그대로입니다. **"안 적었을 때
쓰는 값"도 문장에서 베끼지 않고 `SandboxRunner`를 하나 만들어서 읽어 옵니다.**
러너가 기본값을 바꾸면 이 검사도 따라 움직입니다. 13.14에서 쓴 방법과 같습니다.

**2. 계획서 숫자가 실제보다 "적을 때만" 거부합니다.**

많이 적어 둔 건 그냥 둡니다. 계획서가 설정보다 **더 조심스러운 건 괜찮고, 덜
조심스러운 건 안 됩니다.** 이렇게 해야 Azure의 8처럼 **정말 손으로 정해야 하는
숫자**는 손으로 정한 채로 남습니다. 읽을 수 있는 한 자리만 못 박습니다.

**3. 두 비교 모두에서 작동합니다.** 위 표의 맨 아랫줄이 이 규칙이 필요한 이유
그 자체입니다. **상한은 어느 비교에서든 상한입니다.**

**4. 그림 검사가 다른 모델을 부르면, 그것도 따로 말합니다.**
`output_qa.vision.deployment`는 아무 모델이나 적을 수 있고, `core/output_qa.py`는
적힌 이름을 그대로 넘깁니다. **횟수를 맞게 세도 값을 틀린 가격에 매기면 계산은
여전히 틀립니다.** 그래서 문장 하나를 따로 냅니다. 켜 놓고 모델 이름을 안 적은
경우도 — 그건 아예 값을 매길 수가 없으니 — 따로 말합니다.

#### 검사 결과

- 신규 테스트 **34개** (새 파일 `test_envelope_preflight_prices_the_container_loop.py`)
- 계산이 진짜 무는지 **일부러 세 군데를 망가뜨려** 확인했습니다: 그림 검사를 안

  잡았습니다
- 위의 변조 시험을 다시 돌렸습니다. 6.2절 비교에서 **0 → 1**. 그림 검사까지 켠
  경우는 **0 → 2**이고, 세는 방식도 맞습니다: `4번 (코드 2번 + 그림 2번)`
- 지금 올라와 있는 설정 파일 3개는 **그대로 통과**합니다. 계획서의 1은 오늘 맞고,
  이제 **왜 맞는지**가 검사로 남습니다
- `mypy`: 오류 170개, 파일 32개 — **기준선과 같음**
- 모델 호출 0회, 승인한 금액 없음, 로그인 없음. **차단은 하나도 풀리지 않았습니다**
- 검사는 **더 많이 거부하게** 됐을 뿐입니다

### 13.16 "이 숫자는 설정으로 못 박을 수 없다"고 적어 두었는데, 설정 두 곳이 못 박고 있었습니다 (2026-08-26 수정)

#### 한 줄 요약

계획서는 **채점 한 번에 입력 1만 토큰**이라고 값을 매겼습니다. 설정이 허용하는
실제 최대는 **53만 3,334 토큰**입니다. 그런데 계획서에도, 검사하는 코드에도
**"이 숫자는 어떤 설정 파일로도 못 박을 수 없다"**고 글로 적혀 있었습니다.
못 박을 수 있습니다.

#### 무슨 일이었나

채점 모델은 답안을 **통째로 보지 않습니다.** `read_deliverable`이라는 도구로
조각조각 요청해서 읽습니다. 그 조각의 크기를 정해 두는 자리가 두 군데입니다.

| 어디 | 무엇을 정하나 | 값 |
|---|---|---|
| `core/tools/read_deliverable.py` | 도구가 **한 번에** 돌려주는 글자 수 | 200,000자 |
| `grading_configs/default_v2.yaml` | 채점 항목 하나에 도구를 **몇 번** 쓸 수 있나 | 8번 |

여기에 결정적인 사실이 하나 붙습니다. `core/tool_calling_judge.py`는 도구가
돌려준 결과를 **자르지 않고 그대로** 대화에 붙이고, **그다음 차례마다 대화 전체를
다시 보냅니다.** 그러니 마지막 차례 한 번은 **8 × 200,000자**를 통째로 실어 나를
수 있습니다. 계획서의 글자당 토큰 비율(3.0)로 나누면 **53만 3,334 토큰**입니다.

계획서가 적어 둔 1만은 그중 **1.87%**입니다.

#### 가장 아픈 대목

이 계산을 못 한 게 **모르는 곳**에서가 아닙니다. `core/execution_envelope_grading_cost.py`는
이미 "도구는 8번까지"라는 숫자를 **읽고 있었고**, 화면에 찍는 설명문에까지
**"이 결과는 뒤따르는 모든 차례가 다시 읽는다"**고 써 두고 있었습니다.
곱셈만 안 했습니다.

#### 얼마짜리였나 (실제로 재 봤습니다)

| 계산 | 최대 비용 |
|---|---|
| 계획서에 적힌 대로 (1만 토큰) | **363.58 달러** |

#### 무엇을 고쳤나

**1. 곱셈을 합니다.** 도구의 한도는 `core/tools/read_deliverable.py`에서

더 크게 적어 둔 건 그냥 둡니다.

**3. 돈 말고 다른 답도 열어 뒀습니다.** 이 지적은 "더 내라"로만 풀리지 않습니다.
설정의 `per_item_call_cap`을 8에서 낮추면 요구치도 그만큼 내려갑니다. 그게 진짜로
되는지 테스트로 박아 뒀습니다 — 8일 때는 거부, 1일 때는 통과.

**4. 아직 못 박히는 것은 이제 좁게 말합니다.** 대화가 **시작할 때** 들어 있는 말
— 채점 지시문, 채점 항목 문장, 과제 앞 500자 — 은 아무것도 안 잘라 냅니다.
그래서 53만 3,334는 **"최대의 하한"**이지 최대 그 자체가 아닙니다. 예전 설명문은
**숫자 전체가 알 수 없다**고 뭉뚱그렸고, 읽을 수 있는 한도가 안 읽힌 게 바로
그래서였습니다. 이제 숫자와 단서를 **둘 다** 찍습니다.

**5. 상한이 스스로 내림하던 것도 잡았습니다.** 올림하려고 `-(-토큰 // 1)`을 썼는데,
`Decimal`의 `//`는 내림이 아니라 **0쪽으로 잘라 내기**입니다. 그래서 상한을
**내려** 잡았습니다(정답 533,334을 533,333으로). 나머지 계산과 똑같이
`ROUND_CEILING`으로 바꿨습니다.

#### 덧 — 같은 문장이 테스트에도 들어 있었습니다

고치고 나니 기존 테스트 두 개가 깨졌습니다. 그 둘은 이렇게 적고 있었습니다.
**"측정으로 해결할 수 있는 것은 전부 해결됐다. 남은 건 측정 자체가 불가능한
하나뿐이다."** 그 '하나'는 값이 안 매겨진 소리 모델입니다.

틀린 문장이었습니다. 측정으로 해결할 수 있는 게 하나 더 있었고, 그게 바로 이번
항목입니다. 게다가 그 파일의 도우미 함수가 채점 관련 문제를 **통째로 옆으로
치워 두고** 다른 테스트 여섯 개를 돌리고 있어서, 새 문제가 조용히 묻힐 수 있는
자리였습니다.

그래서 두 테스트를 고쳐, 남은 것을 **하나씩 이름을 불러** 확인하게 했습니다.
① 소리 모델(측정 방법이 없음), ② 채점 입력 토큰 숫자(측정했고, 검사가 보여줄 게
있도록 일부러 낮게 남겨 둠). 그리고 **그 둘 말고는 아무것도 없다**는 것까지
확인합니다.

#### 검사 결과

- 신규 테스트 **20개** (새 파일 `test_envelope_preflight_prices_the_marking_tool_results.py`),
  기존 두 파일 조정 후 관련 세 파일 **171개 전부 통과**, 전체 묶음 **4,303개 통과 /
  6개 건너뜀 / 실패 0**
- 계산이 진짜 무는지 **일부러 세 군데를 망가뜨려** 확인했습니다: 도구 결과를 한
  번치만 세게 → **6개 실패**, 올림을 내림으로 → **6개 실패**, 계산은 하되 거부만
  안 하게 → **5개 실패**
- 지금 올라와 있는 계획서는 이제 **문제 10개 → 11개**로 거부됩니다. 늘어난 한
  줄이 이 항목입니다
- 계획서의 1만은 **일부러 그대로 뒀습니다.** 조용히 고쳐 두면 검사가 무엇을
  잡았는지 아무도 못 보기 때문입니다
- `mypy`: 오류 170개, 파일 32개 — **기준선과 같음**
- 모델 호출 0회, 채점 실행 0회, 승인한 금액 없음, 로그인 없음.
  **차단은 하나도 풀리지 않았습니다**

### 13.17 "한 번만 묻고 아무것도 넘어가지 않는다"는 문장이, 설정 한 줄에만 기대고 있었습니다 (2026-08-26 수정)

#### 한 줄 요약

컨테이너가 **다음 차례로 들고 가는 내용**에 계획서가 **0원**을 매겨 두고,
그 옆에 이유까지 적어 뒀습니다. **"모델을 한 번만 묻고 아무것도 넘어가지 않으니
0."** 그 문장은 컨테이너의 성질이 아니라, 설정 파일의 **딱 한 줄**에 기대고 있던
말이었습니다.

#### 무슨 일이었나

바로 앞 항목(13.15)에서 **"한 번 시도에 모델을 몇 번 부르는가"**를 설정에서 읽게
만들었습니다. 수리 반복(repair)을 켜면 두 번 부른다는 걸 검사가 잡아 줍니다.
그런데 **두 번째 질문이 무엇을 싣고 가는지**는 아무도 값을 매기지 않았습니다.
차례 수만 늘려 놓고, 그 차례가 들고 가는 짐은 여전히 0이었던 겁니다.

`core/sandbox_runner.py`의 `_build_reflection`은 수리 반복이 켜지면 **실행 결과를
다음 요청에 그대로 붙여 넣습니다.** 크기가 정해져 있는 게 세 가지입니다.

| 무엇 | 글자 수 |
|---|---|
| 코드가 화면에 찍은 것의 **끝부분** | 800자 |
| 코드가 오류로 찍은 것의 **끝부분** | 800자 |
| 실행을 멈춘 실패의 **끝부분** | 600자 |
| **합계** | **2,200자** |

계획서의 비율(글자당 3.0토큰)로 나누면 **734토큰**입니다. 계획서는 여기에
**0**을 적어 뒀습니다.

#### 가장 아픈 대목

그 한 줄이 얼마나 약하냐면 — `core/sandbox_runner.py`는 수리 설정을 이렇게
만듭니다.

```python
self.repair_cfg = {"enabled": True, "max_attempts": 1, **(repair or {})}
```

즉 **설정 덩어리를 지우면 꺼지는 게 아니라 켜집니다.** 실험 파일의
`repair: enabled: false` 한 줄이 지금 이 계산 전체를 떠받치고 있었고,
계획서의 문장은 그 사실을 **읽는 사람에게 확인하지 말라고 설득하고 있었습니다.**

#### 얼마짜리였나 (실제로 재 봤습니다)

여기서는 솔직하게 말해야 합니다. **금액은 작습니다.**

| 상황 | 최대 비용 |
|---|---|
| 지금 그대로 (수리 꺼짐, 차례 1) | **363.58 달러** |
| 수리 1회 켬, 차례 2, 짐을 0으로 계산 | **368.95 달러** |
| 수리 1회 켬, 차례 2, 읽어 낸 734토큰으로 계산 | **368.97 달러** |
| **0이 감추고 있던 금액** | **약 2센트** |

수리 횟수를 늘리면 커집니다. 뒤 차례가 앞 차례를 **모두** 다시 읽기 때문입니다.
2차례면 시도당 734토큰, 3차례면 2,202토큰, 4차례면 4,404토큰입니다(금액으로는
0.07달러, 0.14달러).

**작다는 사실 자체가 이 항목의 결론 중 하나입니다.** 여기서 잘못된 것은 큰
금액이 아니라, **켤 수 있는 설정에서 거짓이 되는 문장**입니다. 13.16이
7,204달러였다고 해서 이번 것도 그럴 거라고 부풀리지 않았습니다.

#### 무엇을 고쳤나

**1. 세 숫자에 이름을 붙였습니다.** `core/sandbox_runner.py`에
`REFLECTION_STDOUT_TAIL_CHARS`(800), `REFLECTION_STDERR_TAIL_CHARS`(800),
`EXECUTION_ERROR_TAIL_CHARS`(600)를 만들고 원래 자리에서 그걸 쓰게 했습니다.
13.16에서 `MAX_CONTENT_CHARS`가 해 준 역할과 같습니다 — **검사가 숫자를 베껴
적지 않고 읽어 갑니다.**

**2. 검사를 새로 붙였습니다.** 컨테이너의 **자기 설정**이 진짜로 반복할 상황
(수리가 켜져 있음)에서, 계획서의 숫자가 **734보다 낮으면 거부**합니다. 계획서가
설정보다 **더 넉넉하게** 잡는 것은 그냥 둡니다. 부족한 쪽만 막습니다.

**3. 오늘은 조용합니다. 그게 맞습니다.** 지금 올라와 있는 컨테이너 파일은
수리가 꺼져 있으므로 검사는 아무 말도 하지 않고, 계획서의 0은 그대로 유효합니다.
13.15가 남긴 것과 같은 모양입니다 — **계획서의 0은 오늘 맞고, 이제 왜 맞는지가
검사로 남습니다.** 그 한 줄이 바뀌는 순간 검사가 입을 엽니다.

**4. 734는 "하한"이라고 명시했습니다.** 같은 수리 프롬프트는 막힘 오류 최대 12줄,
경고 최대 6줄, 오류 종류별 수리 지침, 산출물 계약서 전체도 함께 싣는데
**이것들은 어디에도 크기가 정해져 있지 않습니다.** 그래서 734는 최대가 아니라
**최소한 이만큼**입니다.

**5. 직전 코드는 일부러 안 셌습니다.** 수리 프롬프트는 앞서 쓴 코드도 최대
4,000자까지 함께 보냅니다. 하지만 그건 **모델이 스스로 쓴 답**이고,
`max_input_tokens_per_attempt`가 이미 앞 차례마다 `max_output_tokens`(32,768토큰)를
꽉 채워 물리고 있습니다. 여기서 또 세면 **같은 글자에 두 번 값을 매기는** 셈이고,
상한이 실제보다 더 근거 있어 보이게 됩니다.

#### 덧 — 아무도 안 부르는 규칙은 아무것도 막지 못합니다

일부러 망가뜨려 보는 단계에서 하나가 걸렸습니다. **검사를 배선에서 빼 버렸는데
테스트 34개가 전부 통과했습니다.** 전부 규칙을 **직접** 불러서 시험하고 있었기
때문입니다. 규칙이 동작한다는 건 증명했지만, **자유 검사가 그 규칙을 실제로
부르는지**는 아무것도 증명하지 못하고 있었습니다.

그래서 테스트 두 개를 더 붙였습니다. 계획서가 가리키는 설정 파일들을 임시
폴더로 복사하고, 거기서 컨테이너의 수리 반복을 켠 다음, **사람이 하듯 자유 검사를
그대로 호출합니다.** 이제 배선을 빼면 테스트가 깨집니다.

#### 검사 결과

- 신규 테스트 **36개** (새 파일
  `test_envelope_preflight_prices_what_the_container_carries_forward.py`),
  관련 파일 **240개 전부 통과**, 전체 묶음 **4,339개 통과 / 6개 건너뜀 / 실패 0**
- 계산이 진짜 무는지 **일부러 다섯 군데를 망가뜨려** 확인했습니다: 검사를
  배선에서 빼기 → **1개 실패**, 800자를 400자로 → **6개 실패**, 올림을 잘라내기로
  → **3개 실패**, 계획서에 옛 문장 되돌리기 → **1개 실패**, 직전 코드 4,000자를
  같이 세기 → **6개 실패**
- 지금 올라와 있는 계획서의 검사 결과는 **문제 11개 그대로**입니다. 오늘의
  설정에서는 이 규칙이 조용한 게 정답이기 때문입니다
- `mypy`: 오류 170개, 파일 32개 — **기준선과 같음**
- 모델 호출 0회, 채점 실행 0회, 승인한 금액 없음, 로그인 없음.
  **차단은 하나도 풀리지 않았습니다**

### 13.18 "답변 길이 제한 한 번이 시도 전체를 덮는가"를, 손으로 적은 참/거짓 세 개가 정하고 있었습니다 (2026-08-26 수정)

#### 한 줄 요약

계획서에 **참 / 거짓 / 거짓** 세 글자가 적혀 있고, 옆에 네 줄짜리 설명이
붙어 있었습니다. **아무도 그 세 글자를 무엇과도 대조하지 않았습니다.** 그런데
이 세 글자는 **비용 계산 전체에서 가장 크게 나누는 값**입니다.

#### 이게 왜 그렇게 큰 값인가

한 번 시도할 때 모델에게 답을 **몇 번 값을 치를지**를 이 값이 정합니다.

```python
answers_per_attempt = 1 if output_tokens_capped_per_attempt else tool_loop_max_model_turns
```

- **참**이면 → 답 **한 번** 치입니다.
- **거짓**이면 → **차례 수만큼** 치입니다.

입력 쪽도 같이 움직입니다. 뒤 차례는 앞 차례가 쓴 답을 **다시 읽기** 때문에,
참이면 `차례-1`번, 거짓이면 `차례×(차례-1)÷2`번 값을 치릅니다.

#### 얼마짜리였나 (실제로 재 봤습니다)

| 상황 | 최대 비용 | Azure 한 줄 |
|---|---|---|
| 지금 그대로 (Azure 참) | **363.58 달러** | 14.06 달러 |
| Azure를 거짓으로 바꾸면 | **413.76 달러** | **54.20 달러** (3.86배) |
| **차이** | **50.18 달러** | |

**승인 금액 전체가 32.23 달러입니다.** 이 한 글자가 틀리면
**승인 금액보다 더 큰 금액**이 움직입니다.

컨테이너 쪽은 **더 안 보이는 방향으로** 틀립니다. 13.15에서 도달 가능하게
만든 "차례 2" 상황에서, 거짓을 참으로 잘못 적으면 상한이 **368.95 → 364.85
달러로 내려갑니다.** 늘어난 차례가 **공짜처럼 보이게** 됩니다. 금액이 커지는
실수는 누가 봐도 이상하지만, **작아지는 실수는 아무도 찾으러 가지 않습니다.**

#### 사실은 읽을 수 있는 값이었습니다

"제한 한 번이 시도 전체를 덮는가"는 **설정이 정하는 게 아니라, 요청을 어떤
모양으로 보내느냐가 정합니다.** 그건 이 저장소 안에 그대로 적혀 있습니다.

| 실행 장소 | 한 번 시도에 보내는 요청 | 제한이 덮는 범위 |
|---|---|---|
| Azure 코드 인터프리터 | `responses.create` **한 번**, 도구를 그 요청에 붙여서 | 그 **한 번**의 `max_output_tokens` |
| 도커 컨테이너 | 파이썬 `for` 반복문이 돌 때마다 `complete` **다시** | 매번 **예산을 새로 통째로** |
| 로컬 파이썬 프로세스 | `complete` **한 번**, 코드는 자기가 실행 | 반복문 자체가 없음 |

#### 무엇을 고쳤나

**1. 실행기 세 개가 스스로 밝히게 했습니다.** 각 클래스에
`SENDS_A_FRESH_REQUEST_PER_TURN`을 두고, **왜 그런지**를 그 자리에 적었습니다.
13.16의 `MAX_CONTENT_CHARS`, 13.17의 800/800/600과 같은 방식입니다 — **검사가
숫자를 베껴 적지 않고 읽어 갑니다.**

**2. 그 값이 진짜인지 실제로 돌려서 확인합니다.** 글자를 찾아보는 게 아니라
**진짜 실행기를 굴려서 요청 횟수를 셉니다.** 모델 호출만 가짜로 바꿔 두고,
Azure는 `responses.create`가 **정확히 1번** 불리는지, 컨테이너는 수리 반복
2차례에서 `complete`가 **2번** 불리고 **두 번 다 예산 7,777을 통째로** 들고
가는지, 로컬은 **1번**인지 셉니다.

**3. 싼 쪽으로 우기는 것만 막습니다.** 저장소가 "매 차례 새 요청을 보낸다"고
말하는데 계획서가 "제한 한 번으로 덮인다"고 적으면 **거부**합니다. 반대는
그냥 둡니다 — **더 비싸게 잡는 건 안전하기 때문입니다.**

**4. "아무도 안 봤다"도 통과가 아닙니다.** 실행기가 등록돼 있지 않거나
아무 말도 하지 않는 실행장소에 참을 적어 두면 역시 거부합니다.

### 13.20 못 읽은 값을 **0으로 적어 두고**, 그 0을 "돈이 안 드는 일"로 계산하고 있었습니다 (2026-08-26 수정)

#### 한 줄 요약

과제 목록표를 만드는 스크립트가, **읽지 못한 칸을 전부 "0"으로 적고
있었습니다.** 그런데 뒤쪽 비용 계산은 그 0을 **"못 읽었다"가 아니라 "정말로
그만큼 작은 일"로 읽습니다.** 채점은 **채점 항목 한 줄마다** 돈을 매기기
때문에, 항목 수가 전부 0이 되면 상한이 **7,608.41달러에서 94.40달러로**
떨어집니다. **7,514.01달러, 98.8%가 사라집니다.** 그런데도 모든 자유
검사는 "깨끗하고 일치한다"고 보고합니다.

#### 어떻게 확인했나

`scripts/build_gdpval_task_catalog.py`가 데이터에서 값을 꺼내는 방식이 이랬습니다.

```python
deliverables = list(row.get("deliverable_files") or [])
references   = list(row.get("reference_files")   or [])
prompt       = str(row.get("prompt")             or "")
rubric_items = json.loads(rubric_json) if rubric_json else []
```

`or []`, `or ""`가 하는 일은 **"없으면 빈 걸로 치자"**입니다. 그래서 이 셋이
전부 같은 결과가 됩니다.

- 칸 이름이 바뀌었다 → 빈 값
- 값이 정말 비어 있다 → 빈 값
- 읽다가 실패했다 → 빈 값 (`except` 안에서 조용히 `[]`)

**"아무도 못 찾았다"와 "정말로 없다"가 구분되지 않습니다.** 그리고 목록표에
적히는 순간 둘의 차이는 영영 사라집니다.

#### 얼마나 큰 차이인가 — 직접 계산해 봤습니다

| 무엇을 0으로 만들었나 | 상한 | 사라진 금액 |
|---|---|---|
| 아무것도 안 함 (지금 파일) | **363.58481250** | — |
| 채점 항목 수 전부 0 | **93.74793750** | **269.83687500** |
| 과제 글자 수 전부 0 | 363.36250000 | 0.22231250 |
| 참고 파일 수 전부 0 | 361.50143750 | 2.08337500 |

**채점 항목 하나가 압도적입니다.** 채점이 항목 줄 수만큼 값이 매겨지기
때문입니다.

#### 13.19와는 방향이 반대입니다

13.19는 **비싸게 잡는 쪽**이었습니다. 그건 안전합니다 — 상한이 실제보다
조심스러운 건 상한의 잘못이 아닙니다. 이번 건은 **싸게 잡는 쪽**이고,
막는 것이 **아무것도 없었습니다.** 이 파일이 애초에 막으려고 만들어진 실수가
바로 이 방향입니다.

#### 왜 아무도 못 잡았나 — 네 군데가 전부 비켜갔습니다

1. **`TaskCatalog.from_mapping`** — 0도 멀쩡한 정수라 그냥 통과합니다.
2. **`catalog_score_problems`** — "점수가 섞여 들어갔는가"라는 **다른 질문**에
   정확히 답합니다. 이 질문은 안 합니다.
3. **`test_a_whole_number_is_still_a_perfectly_good_count`** — 0을 **명시적으로
   허용하는 테스트**입니다.
4. **`--check`** — **같은 코드로 다시 만들어서** 비교합니다. 칸 이름이
   바뀌었으면 양쪽 다 똑같이 0이 되므로, **"일치합니다"라고 보고합니다.**

4번은 `--check`의 결함이 아닙니다. 다시 만들어 committed 파일과 대보는 건

| 센 개수와 적어 둔 경로 수가 다름 | 같은 목록에서 나온 둘이라 다를 수 없음 |

**4. 참고 파일 0개는 아무것도 안 막습니다.** 위에 적은 대로 95개가 진짜
0이기 때문입니다. **작아 보이게 만드는 방향만 거부합니다.** 커지는 방향은
막지 않습니다 — 그건 상한을 실제보다 넉넉하게 잡을 뿐이니까요.

**5. 자유 검사가 이 질문을 **비용을 계산하기 전에** 합니다.** 그리고 스크립트도
**쓰기 전에** 같은 질문을 자기 자신에게 합니다.

#### 이 규칙이 못 잡는 것도 적어 뒀습니다

**0은 잡지만, "그냥 좀 작은 수"는 못 잡습니다.** 137개짜리 과제가 3개로
적혀 있으면 이 규칙은 통과시킵니다. 정직하게 문서에 적어 뒀습니다.

#### 원본 데이터로 **한 바이트도 다르지 않게** 다시 만들어 봤습니다

고친 스크립트로 못 박아 둔 데이터 판본에서 목록표를 다시 만들었더니,

```

```

**고친 것은 읽는 방식이고, 읽어낸 값은 하나도 안 바뀌었습니다.**

#### 오늘은 조용합니다. 그게 맞습니다

지금 목록표는 깨끗해서 새 규칙은 아무 말도 하지 않습니다. 자유 검사 보고서는
**이 규칙을 꺼놓고 돌렸을 때와 글자 하나 다르지 않고**, 상한도 **363.58달러

### 13.21 "대화가 시작될 때 깔고 들어가는 글은 아무도 못 잰다"고 써 놓고, **그 문장 안에 잰 숫자를 적어 두었습니다** (2026-08-26 수정)

#### 한 줄 요약

채점 한 번이 최소 얼마나 많은 글을 지고 가는지를 따지는 검사가, **대화가
열릴 때 깔고 들어가는 글을 아예 안 세고 있었습니다.** 이유도 코드에 적혀
있었습니다 — "그건 무엇으로도 제한되지 않는다". **그런데 그 문장이 제한을
스스로 적고 있었습니다.** "과제 글의 앞 **500글자**"라고요. 500이 바로 그
제한입니다.

#### 무엇을 안 세고 있었나

채점 대화가 열릴 때 항상 같이 나가는 것이 셋입니다.

| 무엇 | 제한이 있나 | 얼마 |
|---|---|---|
| 채점 지침서 (`prompts/grader_judge_v2.md`) | **있습니다** — 저장소에 든 파일 하나 | **6,263글자** |
| 채점할 항목 한 줄 | 없습니다 — 데이터에서 옵니다 | 알 수 없음 |
| 과제 글 앞부분 | **있습니다** — 500글자에서 자릅니다 | **500글자** |

셋 중 **둘은 이 저장소가 이미 정해 놓은 값**입니다. 파일을 열어 보면
길이가 나옵니다. 그런데 검사는 셋 다 "못 잰다"로 묶어서 **0으로 치고**
있었습니다.

지침서는 한 번만 보내는 것도 아닙니다. 채점기가 그 파일을 **둘로 쪼개서 한쪽은
지시문으로, 한쪽은 메시지 안에 넣어** 보내기 때문에, **매 호출마다 파일 전체가
그대로 나갑니다.**

#### 방향이 문제입니다 — 13.19가 아니라 13.20 쪽입니다

13.19는 **비싸게 잡는 쪽**이라 안전했습니다. 이번은 **싸게 잡는 쪽**입니다.
요구하는 최소치가 실제보다 낮으면, 그 최소치를 넘긴 계획서가 **"검사 통과"로
기록됩니다.** 통과할 자격이 없는데도요.

- 예전 요구치: **533,334토큰** (도구가 물어 온 글만)
- 지금 요구치: **535,589토큰** (＋ 열 때 깔리는 **2,255토큰**)

#### 글자로 셉니다, 바이트가 아니라

나누는 값이 "토큰 하나에 몇 **글자**"이기 때문입니다. 지침서에는 여러 바이트를
쓰는 글자가 몇 개 섞여 있어서, 바이트로 세면 **6,267**, 글자로 세면
**6,263**이 나옵니다. 이번엔 안전한 쪽으로 틀리지만, 틀리는 크기가 **누가
다음에 어떤 글자를 치느냐에 따라 달라집니다.** 그래서 글자로 셉니다.

#### 여전히 "최소치"라고 말합니다

셋 중 **채점 항목 한 줄은 정말로 제한이 없습니다.** 데이터에서 오고, 길이를
묶어 두는 설정이 없습니다. 그래서 이 숫자는 **"넘으면 안 되는 바닥"이지 "가장
큰 값"이 아닙니다.** 이 아래인 계획서는 확실히 상한이 아니고, 이 위인 계획서도
상한이 아닐 수 있습니다. 검사 문구와 설명 문구 **양쪽 다 이 말을 그대로
유지합니다.**

#### 못 읽으면 0으로 치지 않고 거절합니다

- 설정 파일이 지침서를 **아무것도 안 가리키면** → 거절
- 가리킨 파일이 **그 자리에 없으면** → 거절
- 거절 문구에 **어느 설정 파일인지 이름을 적습니다** — 여러 개를 놓고 보는
  사람이 어느 걸 열어야 할지 알아야 하니까요

13.20에서 배운 그대로입니다. **못 읽은 값을 0으로 적으면, 그 0은 "돈이 안 드는

#### 옆에서 하나 더 나왔습니다 — **9개 파일에 적혀 있는데 아무 데도 안 닿는 설정**

**우연히 같은 값이라 지금은 아무 일도 안 일어납니다.** 누군가 이 설정을
1000으로 고치면, 실제 실행은 그대로 500인데 파일에는 1000이라고 적힌 채
남습니다.

그래서 검사는 **실제로 적용되는 값**을 세고, 적힌 값과 다르면 **"이 설정은
아무 데도 안 닿습니다"라고 보고**합니다. 고쳐도 아무 일이 안 일어나는 숫자야말로,

않습니다.

한 줄만 달라졌다는 것도 **테스트로 못 박았습니다.** 컴퓨터마다 다른 숫자를

### 13.22 같은 숫자를 **네 군데에 손으로 적어 두고**, 서로 맞는지 아무도 안 보고 있었습니다 (2026-08-27 수정)

#### 한 줄 요약

채점할 때 그림을 보거나 소리를 듣는 일을 **한 과제에 몇 번까지 하는지**, 그
숫자가 **네 군데에 따로따로 손으로 적혀** 있었습니다. 네 개가 마침 다 같은
값이라 오늘은 아무것도 틀리지 않았습니다. **서로 맞춰 주는 장치가 하나도
없었을 뿐입니다.**

#### 어디에 몇 번 적혀 있었나

| 어디 | 무엇이라고 적혀 있었나 |
|---|---|
| `core/perception/vision.py` | 그림 보기 **5번** |
| `core/perception/audio.py` | 소리 듣기 **3번**, 한 번에 보내는 소리 **30초** |
| `core/grader.py` (실제 채점기) | **5**, **3**, **30** — 위 세 개를 **한 번도 안 보고** 다시 적음 |
| `core/execution_envelope_grading_cost.py` (비용 검사) | **5**, **3** — 세 번째로 다시 적음 |

#### 왜 위험한가 — 또 **싸게 잡는 쪽**입니다

비용 검사는 이렇게 일합니다. **설정이 허락하는 횟수보다 계획서가 적게 잡으면
거절**합니다. 그런데 설정 파일이 횟수를 **안 적어 두면**, 검사는 자기가 손으로
적어 둔 숫자를 대신 씁니다. 그러니까 그 숫자가 **거절의 기준선 그
자체**입니다.

누가 실제 실행 쪽 숫자만 5에서 8로 올리고 검사 쪽을 안 올리면:

- 실제 실행은 한 과제에 **8번** 부릅니다
- 상한은 **5번**어치만 잡아 둡니다
- 검사는 **아무 말도 안 합니다**

**실제보다 싸게 잡히는 것**입니다. 13.20, 13.21과 같은 방향입니다.

#### "이건 이미 지키고 있다"던 문장도 틀렸습니다

비용 검사 위에는 이런 메모가 붙어 있었습니다 — "실제 채점기를 진짜 설정으로
만들어서 비교하는 테스트가 있으니, 이 값들은 **조용히 낡을 수 없다**."

그 테스트는 **진짜로 있습니다.** 그런데 그 테스트는 **저장소에 든 설정
파일들**로 채점기를 만듭니다. 그리고 **아홉 개 전부 횟수를 직접 적어 두고
있습니다.** 즉 양쪽 다 설정에서 읽어 가고, **손으로 적어 둔 값에는 한 번도 안
닿습니다.**

테스트는 진짜였고, **그 테스트가 무엇을 지키는지에 대한 설명이
가짜**였습니다.

그래서 이번에 **횟수를 안 적은 설정으로 같은 비교를 한 번 더** 돌립니다. 손으로
적어 둔 값에 닿는 **유일한 모양**입니다.

#### "절대 못 넘는 상한"이라고 적혀 있었는데, 아니었습니다

`vision.py`와 `audio.py` 두 곳 다 그 숫자를 "**과제당 절대 상한**"이라고
불렀습니다. 아닙니다. 설정에 `call_cap_per_task`를 적으면 **그 값으로
바뀝니다.** 실제로 채점기를 만들 때마다 설정 값이 그대로 넘어갑니다. 이제
설명을 고쳤습니다 — **설정이 아무 말 안 할 때 쓰는 값**이고, **어느 설정 키가
이걸 대신하는지**까지 적었습니다.

#### 어떻게 고쳤나

숫자는 이제 **한 군데에만** 있습니다. 채점기도 비용 검사도 **그걸 가져다
씁니다.**

가장 중요한 테스트는 이겁니다. **새 파이썬을 하나 띄워서, 비용 검사가 처음
불려 오기 전에 실제 실행 쪽 숫자를 9와 7로 바꿔 놓고**, 비용 검사가 9와 7을
따라오는지 봅니다. 따라오면 한 군데에서 가져다 쓰는 게 맞고, **안 따라오면
어딘가에 또 손으로 적어 둔 것**입니다.

이 테스트만이 **"값이 아직 서로 같은 채로 누가 숫자를 다시 손으로 적는"**
경우를 잡습니다. 이 결함이 돌아온다면 정확히 그 모양일 겁니다.

#### 오늘 숫자는 하나도 안 움직였습니다

- 자유 검사 출력이 **바로 앞 커밋과 글자 하나까지 똑같습니다**
- 상한 **363.59달러** (반올림 전 363.58481250) — **그대로**
- 문제 개수 **14개** — **그대로**, 검사 결과도 여전히 **실패(1)**

저장소에 든 설정 파일이 **전부 횟수를 적어 두고 있어서**, 손으로 적어 둔 값이
오늘은 아예 안 쓰입니다. 그래서 이번 수정은 **지금 틀린 숫자를 고친 게
아니라, 앞으로 틀어질 자리를 미리 막은 것**입니다.

#### 검사 결과

- 신규 테스트 **41개** (새 파일 `test_perception_caps_have_one_source.py`),

### 13.23 합계는 "최대"라고 불러 놓고, 그 합계의 한 조각은 "상한이 없다"고 적어 두었습니다 (2026-08-27 수정)

#### 한 줄 요약

비용 검사가 낸 보고서 안에서 **같은 숫자를 두 가지로 부르고** 있었습니다. 한
쪽에서는 "**나올 수 있는 가장 큰 금액**"이라고 부르고, 몇 줄 아래에서는 그
금액을 이루는 조각 하나를 두고 "**이건 상한이 없다**"고 적어 두었습니다.

**둘 다 맞을 수는 없습니다.** 더하는 것 중 하나에 끝이 없으면, 그 합계에도
끝이 없습니다. 그러면 "가장 큰 금액"이라는 말이 거짓이거나, "상한이 없다"는
말이 거짓입니다.

거짓인 쪽은 **"상한이 없다"** 였습니다.

#### 그 조각이 무엇이었나

채점은 과제 하나마다 **채점 기준 줄**을 하나씩 읽고 점수를 매깁니다. 그
기준 줄의 글이 대화에 그대로 실려 갑니다. 그러니 그 글의 길이만큼 돈이
듭니다.

비용 검사는 이 길이를 **아예 안 세고 있었습니다.** 세지 않은 이유가 "설정에
그 길이를 못 박는 칸이 없어서"였습니다.

그런데 **설정에 칸이 없다**는 말과 **길이가 정해져 있지 않다**는 말은 전혀
다른 말입니다.

기준 줄의 글은 **이미 고정된 데이터 파일 안에 들어 있습니다.** 그 파일은
비용 검사가 이미 찾아내서, **지문 64글자를 전부 대조해서**, 바뀌지 않았음을
확인하고 있는 바로 그 파일입니다. 그 파일에서 채점기까지 가는 길에 글을
잘라 내는 곳은 **한 군데도 없습니다.**

**읽으면 나오는 숫자를, 없는 숫자라고 불러 왔던 것**입니다.

### 13.24 "프로그램만 바꾼 비교"에 자리를 셋 더 넣었습니다 — 그중 하나는 같은 종류가 아니었습니다 (2026-08-27 추가)

#### 한 줄 요약

지금까지 이 비교는 **모델에게 파이썬 코드를 받아서 우리가 실행하는 자리**만
다뤘습니다. 그런데 요즘 나온 도구들은 **자기가 알아서 끝까지 일합니다.**
Codex의 명령줄 도구, GitHub Copilot의 명령줄 도구가 그렇습니다.

그래서 자리를 셋 더 넣었습니다. 넣고 보니 **셋이 같은 종류가 아니었습니다.**

- 앞의 둘은 **우리가 정한 그 모델**에게 묻습니다. 그러니 바뀌는 건 **일을
  끌고 가는 프로그램뿐**입니다.
- 셋째는 **GitHub이 고른 모델**에게 묻습니다. 우리가 고른 게 아닙니다.

셋째를 앞의 둘과 같은 점수판에 올리면, **프로그램이 잘해서 이긴 건지 모델이
달라서 이긴 건지 영영 구분할 수 없습니다.** 그래서 점수판을 따로 팠습니다.

#### 셋이 무엇인가

| 번호 | 이 문서에서 부르는 이름 | 무엇이 일을 끌고 가나 | 어느 모델에게 묻나 |
|---|---|---|---|
| 6 | Codex 명령줄 도구 + 우리 Foundry 배포 | Codex의 명령줄 도구 | **우리가 정한 그 배포** |
| 7 | Copilot 명령줄 도구 + 우리 Foundry 배포 | GitHub Copilot 명령줄 도구 | **우리가 정한 그 배포** |
| 8 | Copilot 명령줄 도구 + GitHub이 주는 모델 | GitHub Copilot 명령줄 도구 | **GitHub이 고르는 모델** |

6번과 7번은 3번(Azure Code Interpreter)이 묻는 **바로 그 자리**에 묻습니다.
같은 회사, 같은 리소스, 같은 배포 이름, 같은 API 버전입니다. 코드가 이걸
표로 들고 있고, 테스트가 **6·7번과 3번의 값이 같은지를 직접 대조**합니다.
사람이 "같습니다"라고 적어 둔 게 아닙니다.

#### 새로 만든 칸: "이 모델은 어디서 오나"

이번에 실행 조건에 칸을 하나 더 만들었습니다. **모델이 어디서 오는가**입니다.
값은 둘뿐입니다 — **우리 Foundry 배포**, 또는 **GitHub이 주는 것**.

이 칸이 왜 필요했냐면, 다른 칸을 **전부 똑같이 맞춰 놓고도** 서로 다른
모델에게 묻고 있을 수 있기 때문입니다. 제품이 자기 마음대로 고르면 그렇게
됩니다. 그러면 계획서에 적힌 배포 이름은 **아무 일도 하지 않는 글자**가
됩니다.

그래서 이렇게 막았습니다.

- 자리마다 **어디서 모델이 오는지가 표에 못 박혀 있습니다.** 계획서가 그
  표와 다른 말을 적으면 **거절**합니다. 8번을 "우리 배포를 쓴다"고 적어
  둘 수 없습니다.
- 목록에 없는 값을 적어도 **거절**합니다.
- **제품이 스스로 고르는 자리 목록은 손으로 적지 않았습니다.** 위의 표에서
  **계산해서 뽑습니다.** 나중에 그런 자리가 하나 더 생기면 표만 고치면
  되고, 두 번째 목록을 같이 안 고쳐서 어긋나는 일이 없습니다. **13.22에서
  고친 것과 정확히 같은 모양**이라 (같은 숫자를 네 군데에 손으로 적어 두고
  아무도 대조 안 하던 문제), 이번엔 **그 계산이 맞는지 검사하는 테스트**까지
  붙였습니다.

#### 점수판을 하나 더 팠습니다

이제 점수판이 셋입니다.

| 점수판 | 무엇을 재나 | 반드시 있어야 하나 |
|---|---|---|
| 같은 코드로 재기 | 모델이 쓴 같은 코드를, 자리만 바꿔 가며 실행 | **네** |
| 도구가 스스로 하는 일까지 재기 | 자리마다 다른 도구 기능을 켜 놓고 실행 | **네** |
| **제품 통째로 재기** | 프로그램·도구·제품이 고른 모델까지 **묶어서** 실행 | **아니요** |

셋째는 **없어도 됩니다.** 돈이 더 드는 비교이고, 운영자가 "이건 안 하겠다"고
정할 수 있어야 하기 때문입니다. 대신 **하기로 했으면 따로 있어야 합니다.**

- 셋째 점수판을 앞의 둘 중 하나로 **이름만 바꿔 붙이면 거절**합니다.
- 앞의 두 점수판에 **8번 자리를 끼워 넣으면 거절**합니다.
- 셋째 점수판은 **자리가 최소 둘** 있어야 합니다. 하나만 있으면 비교가
  아닙니다.

셋째 점수판이라고 아무거나 되는 건 아닙니다. **모델은 달라도 되지만**,
**묻는 내용과 쓸 수 있는 돈은 여전히 똑같아야 합니다** — 같은 지시문, 같은
과제 목록, 같은 입력 파일, 같은 토큰·시간 한도입니다. 그게 안 맞으면
거절하고, 이렇게 말합니다: *"같은 값을 내고 같은 걸 물어본 게 아닙니다."*

#### 실행 환경이 절대 스스로 정하면 안 되는 세 가지

계획서가 **셋을 각각** "안 된다"고 적어야 합니다. 하나만 적고 나머지를
비워 두면 **거절**합니다. 셋이 서로 다른 사고이기 때문입니다.

| 무엇 | 무엇이 달라지나 |
|---|---|
| 모델을 도중에 바꾸기 | **누가 답했는지**가 달라집니다 |
| 안 되면 대신 다른 걸로 계속하기 | **무엇이 실행됐는지**가 달라집니다 |
| 지원 안 되는 자리를 다른 자리로 때우기 | **어디서 실행됐는지**가 달라집니다 |

"모델은 안 바꾼다"고 적어 놓은 것이 "대신 다른 걸로 계속해도 된다"까지
허락한 게 아닙니다. **말 안 한 건 허락한 게 아닙니다.** 그래서 세 칸 전부
계획서에 **반드시 적어야 하는 칸**으로 만들었고, 비워 두면 파일을 읽는
단계에서 거절합니다.

#### 반복은 세 종류를 따로 셉니다

이건 앞선 작업에서 이미 만들어 둔 것이고, 새 자리 셋도 그대로 따릅니다.

| 무엇 | 언제 |
|---|---|
| 장비 문제로 다시 하기 | 연결이 끊기거나 서비스가 오류를 냄 |
| 모델이 자기 답을 보고 다시 하기 | 스스로 부족하다고 판단 |
| 도구를 쓰다 안에서 되돌리기 | 도구 실행이 실패해 그 안에서 복구 |

합쳐서 세면 "장비가 불안정한 자리"와 "모델이 자기 답에 자신이 없는 자리"가
**같은 숫자로 보입니다.** 전혀 다른 이야기입니다.

#### 셋 다 오늘은 실행할 수 없습니다 — 이유를 코드로 증명했습니다

이 저장소에는 **이 셋으로 과제를 돌리는 코드가 없습니다.** 그래서 셋 다
"현재 저장소에 구현되지 않음"으로 나옵니다. 이건 누가 그렇게 적어 둔 게
아니라, **실행 방식 이름과 담당 클래스가 비어 있다는 사실에서 자동으로**
그렇게 됩니다.

구현이 없다는 것 말고도, **각각 따로 막혀 있습니다.**

**6번 — Codex 명령줄 도구 (막힌 이유 3개)**

1. Codex 설정 문서는 모델 열쇠를 **환경 변수에 담긴 고정 API 키**로
   주거나, **토큰을 찍어 주는 명령**으로 줍니다. 이 저장소는 고정 Azure
   열쇠 변수를 **전부 금지**하고 있고, 하나라도 설정돼 있으면 실행을
   멈춥니다. **둘이 동시에 참일 수 없습니다.**
2. 같은 문서에 **Microsoft Entra 로그인으로 연결하는 방법이 없고**, Azure
   예시도 없습니다. 그러니 이 저장소의 로그인 규칙을 지키면서 Foundry
   배포에 닿는 **공개된 길이 없습니다.** *문서에 길이 없다는 것이 "길이
   있는데 안 적혔을 뿐"이라는 근거가 되지는 않습니다.*
3. 같은 문서에 **API 버전을 지정하는 칸이 없습니다.** 이 비교는 API
   버전까지 못 박는데, **실제로 어느 버전이 쓰였는지 보여 줄 수가
   없습니다.**

**7번 — Copilot 명령줄 도구, 우리 열쇠로 (막힌 이유 2개)**

1. 문서가 모델 열쇠를 **고정 API 키 환경 변수**로 줍니다. 6번의 1번과 같은
   충돌입니다.
2. 문서의 Azure 예시가 주소를 `/openai/deployments/<배포이름>` 모양으로
   적습니다. 이 저장소가 받아 주는 주소는 **세 가지 모양뿐**이고, 이건
   **그 셋 중 어느 것도 아닙니다.** 열쇠 문제가 풀려도 **주소에서
   거절**됩니다.

**8번 — Copilot 명령줄 도구, GitHub이 주는 모델로 (막힌 이유 3개)**

1. GitHub 문서가 **자동 모델 선택**을 설명합니다. 그때그때 여유와 일의
   난이도를 보고 **알아서 고릅니다.** 계획서가 시킨 적 없고, **계획서가
   볼 수도 없는** 변경입니다.
2. 같은 문서가 **다른 모델을 못 쓰게 되면 쓰는 기본 모델**을 정해 두고
   있습니다. **멈추는 게 아니라 다른 모델로 넘어갑니다.**
3. 그래서 **누가 답했는지가 GitHub의 결정**입니다. 모델을 고정하는
   비교에는 못 들어가고, **제품 통째로 재는 점수판에만** 들어갑니다.

**이 이유들을 그냥 적어만 두지 않았습니다.** 이유가 이름을 대는 코드를
테스트가 직접 불러서 확인합니다.

- 금지된 열쇠 변수 목록을 **목록 자체에서** 읽어 확인합니다. 나중에 누가
  그중 하나를 허용하기로 하면, 이유가 조용히 틀린 글이 되는 게 아니라
  **테스트가 깨집니다.**
- Copilot 문서가 준 그 주소를 **실제로 넣어 봅니다.** 정말 거절합니다.
  그리고 이 저장소가 **받아 주는** 주소도 같이 넣어 봅니다 — 그래야 위
  결과가 "그 주소 모양이 문제"라는 뜻이지 "그 함수는 다 거절한다"는 뜻이
  아님이 증명됩니다.
- 셋 각각 **이유가 몇 개인지**를 셉니다. 하나 풀렸다고 길이 열린 걸로
  읽히면 안 되기 때문입니다.

### 13.25 "길이를 알 수 없다"고 넘어간 네 조각은, 사실 전부 세어 볼 수 있었습니다 (2026-08-27 수정)

#### 한 줄 요약

컨테이너 자리에서 코드가 실패하면, 다음 번에 다시 물을 때 **실패한 실행의
기록을 같이 보내 줍니다.** 그 보내 주는 글의 길이를 재는 자리가 있는데,
**여덟 조각 중 셋만 세고 넷은 "길이가 정해져 있지 않다"며 건너뛰었습니다.**

그런데 넷 다 **길이가 정해져 있었습니다.** 코드에 열두 줄·여섯 줄로 잘라
놓았고, 나머지 둘은 이 저장소에 **파일로 들어 있는 글**입니다.

그래서 세어 봤더니 **2,200자가 아니라 3,922자**였습니다. **78% 적게 세고
있었습니다.**

#### 무엇을 안 세고 있었나

| 조각 | 전에 | 왜 안 셌다고 했나 | 실제로는 |
|---|---|---|---|
| 화면에 찍힌 글의 끝부분 | **셌음** | — | 826자 |
| 오류로 찍힌 글의 끝부분 | **셌음** | — | 832자 |
| 실행을 멈춘 그 오류 | **셌음** | — | 671자 안에 포함 |
| **막은 오류 줄들** | 안 셈 | "몇 줄인지 모른다" | **열두 줄로 잘려 있음** |
| **경고 줄들** | 안 셈 | "몇 줄인지 모른다" | **여섯 줄로 잘려 있음** |
| **고치는 방법 안내** | 안 셈 | "길이를 모른다" | **저장소에 든 파일에서 옴, 866자** |
| **제출물 규약** | 안 셈 | "과제마다 다르다" | **가장 짧게 만들어도 430자** |
| **여는 줄·머리글·닫는 줄** | 안 셈 | "고정 문구라 작다" | **179자** |

"몇 줄인지 모른다"는 말이 틀렸던 이유가 제일 단순합니다. 코드에 **딱
그렇게 적혀 있었습니다** — 오류는 열두 줄까지, 경고는 여섯 줄까지. 모르는
게 아니라 **아무도 안 본 것**이었습니다.

#### 어떻게 셌나 — 진짜 문서를 만들어서 재는 방식

숫자를 손으로 더하지 않았습니다. **실제로 보내는 그 문서를 만들어 보고,
길이를 잽니다.**

조각을 하나씩 얹으면서 **얹을 때마다 길이가 얼마나 늘었는지**를 적습니다.
그러면 조각들의 합이 **완성된 문서의 길이와 정확히 같아집니다.** 계산이
맞는지 따로 증명할 필요가 없습니다 — 만들어 본 것이니까요.

이렇게 하면 좋은 점이 있습니다.

- 안내 문구를 파일에서 한 줄 늘리면 **숫자가 저절로 따라 올라갑니다.**
- 열두 줄 제한을 열세 줄로 바꾸면 **역시 따라 올라갑니다.**
- 머리글 한 단어만 길게 고쳐도 **따라 올라갑니다.**
- 검사하는 쪽 코드에는 **3,922도 1,308도 12도 6도 적혀 있지 않습니다.**
  전부 물어봐서 받아 옵니다.

**진짜 보내는 그 함수로 만듭니다.** 재기 위한 별도의 계산식을 만들지
않았습니다. 두 개를 만들면 언젠가 서로 다른 답을 내는데, **비싼 쪽이 아니라
싼 쪽이 조용히 틀립니다.**

#### 일부러 안 세는 것 하나, 못 세는 것 하나

**모델이 지난번에 쓴 코드는 안 셉니다.** 이건 봐주는 게 아니라 **두 번
받지 않으려는 것**입니다. 그 코드는 모델이 **이미 써서 값을 치른 글**이고,
비용 계산은 지난 답변마다 **최대 출력 길이를 통째로** 이미 청구하고
있습니다. 여기서 또 세면 같은 글에 두 번 돈을 매기는 셈입니다.

다만 **그 코드를 감싸는 우리 쪽 문구는 셉니다** (57자). 그건 우리가 붙이는
글이고, 아무도 그 값을 안 내고 있었습니다.

**못 세는 것도 하나 있습니다.** 오류 줄과 경고 줄에 **실행 중에 실제로
적히는 영어 문장**입니다. 그건 과제와 실패 내용에 따라 달라지니 미리 알
수 없습니다. 그래서 그 줄들을 **비워 놓고** 잽니다. 진짜 실행은 이보다
**깁니다** — 그리고 그 방향은 **틀려도 안전한 방향**입니다. 거절 문구가
이 한 가지를 **빠뜨렸다고 이름을 대고 말합니다.**

#### 읽을 수 없으면 그냥 멈춥니다

안내 문구가 든 파일을 못 읽으면 어떻게 되나? 전에는 그런 경우가 없었지만
이제는 **거절합니다.**

- 파일이 없으면 → 거절
- 파일이 깨져서 안 읽히면 → 거절
- 파일은 있는데 필요한 항목이 빠졌으면 → 거절

**"못 읽었으니 0원으로 치자"는 길을 아예 없앴습니다.** 못 읽으면 값을 못
매기는 것이고, 값을 못 매기면 **시작하면 안 됩니다.**

이게 진짜 되는지 확인하려고, 저장소에 **실제로 들어 있는데 이 형식이 아닌
파일**을 지목해 봤습니다 (`agentic_sandbox_solver.yaml`). 가짜로 꾸민 상황이
아니라 **실제 파일**입니다. 정말 거절합니다.

반대로, **수리 반복이 꺼져 있으면 아무 말도 안 합니다.** 안 쓰는 문서를
못 읽는다고 멈추면, 지금 커밋된 설정이 이유 없이 막힙니다.

#### 어느 파일을 읽어야 하는지도 설정에서 봅니다

컨테이너 설정에 **어느 안내 파일을 쓸지 적는 칸**이 있고, 실행 코드가 그걸
그대로 씁니다. 그래서 값을 잴 때도 **그 칸을 봅니다.**

증거로, 다른 파일을 지목하면 **답이 달라집니다** — 3,922자가 아니라
3,056자가 나옵니다. 설정을 정말 보고 있다는 뜻입니다.

청구됩니다.

매기지 않기 위해서입니다.

#### 프롬프트 파일이 둘로 갈리면, **긴 쪽을 청구합니다**

컨테이너 설정에는 **어느 프롬프트 파일을 쓸지 적는 칸**이 있습니다. 그런데

실행기 자신의 기본 파일을 씁니다.

그래서 둘 중 **어느 쪽이 진짜냐를 추측하지 않습니다.** 둘 다 만들어 재고,
**긴 쪽을 청구합니다.** 추측하면 둘 중 한 번은 **싼 쪽으로 틀립니다.**

그 자리에 **등록된 실행기가 없거나**, 있어도 **기본 파일을 안 적어 두었으면**
어느 파일을 보내는지 이 저장소 어디에도 안 적혀 있다는 뜻이므로 **거절합니다.**

### 13.27 비용은 기록하되 실행을 막지 않습니다 (2026-08-28 소유자 결정)

#### 결정

저장소 소유자는 매월 제공되는 **Azure 크레딧을 이 벤치마크 작업에

모델은 지금도 가격과 실제 호출 크기를 모릅니다.

#### 코드와 계획 파일의 계약

`cost.policy`는 `record_cost_findings_only`입니다. 기본 정책은 여전히 비용 문제가

이 중 하나라도 빠지면 무료 검사가 다시 중단합니다. 비용 정책을 바꿔도 모델 고정,

#### 한 줄 요약

실행 줄 비교의 실험 설정 세 개는 계획서 옆 폴더에 함께 들어 있습니다.


실험을 실제로 돌리는 워크플로는 `.github/workflows/batch-run.yml` 하나뿐이고,
돌릴 설정을 `experiment_yaml`이라는 **확장자 없는 이름**으로 받습니다. 그 이름을

```ruby
valid_name = name.match?(/\A[A-Za-z0-9][A-Za-z0-9_.-]{0,99}\z/) && ...
```

**구분자 `/`가 글자 목록에 없습니다.** 그래서 위 세 개는 파일을 찾아보기도 전에
