# 334 — 개입한 갈래가 판정 대신 형식을 깨뜨렸다

**요약.** [`333`](./333-speech-prompt-ab-prereg.md)이 사전등록한 말소리 프롬프트 A/B를
**한 번, 120번 호출로** 실제로 샀다. 물어본 것은 하나였다 — *같은 소리·같은 문항에서
**지시문만** 바꾸면 판정이 달라지는가.*

* **설계는 깨끗하게 굴러갔다.** 클립 10개의 지문이 `330` 매니페스트와 **정확히 일치**했고,
  두 갈래가 문항마다 **같은 오디오 바이트**를 받았으며(오디오 토큰도 갈래당 1,848개로 동일),
  프롬프트는 **모든 문항에서 정확히 739자만** 달랐다. 그 739자가 관찰 머리말이다.
  갈래끼리 공유된 프롬프트는 **0개**다.
* **그런데 개입 갈래가 답을 못 냈다.** 관찰 갈래 60번 중 **51번이 읽기 실패**
  (`format_error:unparseable_json`)다. 응답률 **15%**. 대조 갈래는 같은 실행에서
  60번 중 59번 답했다(98.33%).
* **사전등록한 1차 검정은 "못 보였다"로 나왔다.** 문항 단위 20쌍 정확 McNemar,
  **p = 0.0654**. α = 0.05를 넘지 못한다.
* **그리고 그 p는 판정 차이를 잰 게 아니다.** 관찰 갈래가 진 이유의 대부분은
  "다르게 판정해서"가 아니라 **"읽을 수 있는 판정을 아예 안 내놔서"**다.
  20문항 중 **13문항이 세 번 다 안 읽혔다.**

> **결론: 원래 질문은 아직 답이 없다.** 이 실행은 "지시문이 '아니다' 쪽으로 미는가"를
> 재려다가 **그 전 단계에서 멈췄다.** 관찰 머리말을 붙이면 채점기가 못 박은 JSON을
> 안 내놓는다는 것 — 그게 이번에 산 것이다. 이건 실패한 실행이 아니라
> **다른 것을 알아낸 실행**이고, 알아낸 것을 그대로 적는다.

**고치지 않은 것.** [`331`](./331-it-said-no-to-almost-everything.md)의 60회,
`324`·`328`·`329`의 수치, 기존 185실행·31건 채점 원본 — **한 개도 안 건드렸다.**
`330`/`331` 문서와 그 결과 JSON도 그대로다. 이번 결과는 **새 번호(334)**로만 저장했다.

## 2. 1차 지표 — 문항 단위 20쌍 (사전등록 §4)

반복 3회를 문항마다 다수결 하나로 합치고, **문항으로 짝지어** 비교한다.

| | production (대조) | observation (개입) | 상수 `fail` 기계 |
|---|---|---|---|
| 판정이 정해진 문항 | **20 / 20** | **7 / 20** | 20 / 20 |
| 그중 정답 | 12 | 5 | 10 |
| 정확도 | 0.60 | 0.714 | **0.50** |
| 판별력 J | 0.20 | 0.50 | **0** |
| 못 정한 문항 | 0 | **13** (전부 "답이 아예 없음") | 0 |

**엇갈린 문항:** production만 맞힘 **9**, observation만 맞힘 **2**, 둘 다 맞힘 3, 둘 다 틀림 6.

> **정확 양측 McNemar, p = 0.0654.** α = 0.05를 못 넘는다.
> **큰 p는 "두 지시문이 같다"는 뜻이 아니다.** 엇갈린 문항이 11개뿐이라
> 아주 큰 차이만 보일 수 있는 설계였다(`333` §8).

`333` §4가 미리 못 박은 대로, **답이 없는 13문항은 정확도 분모에서 빠지고
McNemar의 엇갈림에는 들어간다.** 그래서 `p = 0.0654`가 잰 것은 대부분
"판정이 달랐다"가 아니라 **"한쪽이 판정을 안 냈다"**이다. 이 구분이 이 문서의 전부다.

### 부차 지표 — 호출 단위 60쌍 (1차 아님)

`333` §4가 "배달 차이가 가장 먼저 드러나는 자리"라며 부차로 남겨 둔 숫자다.
이번에 정확히 그 역할을 했다.

| | production | observation |
|---|---|---|
| 시도 | 60 | 60 |
| 답한 호출 | 59 (98.33%) | **9 (15.0%)** |
| 답한 것 중 정답 | 37 (0.627) | 7 (0.778) |
| 판별력 J | 0.243 | 0.60 |
| 미응답 내역 | 모델 거절 1 · 읽기 실패 0 · 공급자 실패 0 | 모델 거절 0 · **읽기 실패 51** · 공급자 실패 0 |

호출 단위 McNemar는 p = 6.94e-08이다. **이 숫자를 "관찰 지시가 나쁘다"로 읽으면 안 된다.**
엇갈림 32:2의 32는 대부분 *관찰 갈래가 아무 답도 안 낸 호출*이다.
읽히지 않은 답은 틀린 답이 아니다.

## 3. 관찰 갈래에 실제로 무슨 일이 있었나

읽기 실패 51번의 오류는 **전부 같은 것 하나**다: `format_error:unparseable_json`.
공급자 실패 0번, 모델이 스스로 거절한 것 0번, 어휘 밖 단어 0번.
**즉 모델은 응답을 돌려줬고, 그 응답이 못 박은 JSON이 아니었다.**

| | 답이 읽힌 호출 | 읽기 실패한 호출 |
|---|---|---|
| 출력 토큰 중앙값 | 71 | **32** |
| 최소 / 최대 | 64 / 99 | **18 / 68** |

**실패한 응답은 잘린 게 아니라 짧다.** 토큰이 모자라 JSON이 중간에 끊긴 모양이면
실패 쪽이 더 길어야 하는데, 반대다.

**여기서 멈춘다.** 보고서는 응답 본문을 저장하지 않는다(설계상 그렇다 — `330` §의
개인정보 규칙). 그래서 **모델이 무엇을 대신 적었는지는 이 원본으로 증명할 수 없다.**
토큰 길이와 아래 §5의 증거 필드는 "JSON 대신 들은 말을 산문으로 적었다"와
**들어맞지만**, 그건 정황이지 증거가 아니다. 정황을 결론처럼 쓰지 않는다.

### 응답 형식 계약은 개입에 들어 있지 않았다

혹시 계약을 빼먹어서 생긴 일인지부터 확인해야 한다. 아니다.
`AUDIO_RESPONSE_CONTRACT`는 core의 것이고 **두 갈래에 글자 그대로 똑같이** 붙는다.
두 갈래의 프롬프트 차이는 **모든 문항에서 정확히 739자**였고, 그게 관찰 머리말
(`b9bfaaa2…`) 하나다. 계약은 양쪽에 다 있었다.

## 5. 읽힌 9번이 말해 주는 것과, 말해 주지 않는 것

관찰 갈래에서 JSON으로 읽힌 9번은 **증거 필드에 들은 말을 받아 적고** 있었다.
머리말이 시킨 일을 한 것이다. 그중 정답 7개, J = 0.60.

**그런데 이 9번을 "관찰 지시가 더 낫다"로 읽으면 안 된다.**

* **n = 9다.** 20문항 중 7문항만 정해졌고, 그중 5개가 맞았다(이항 p = 0.227).
* **무작위 표본이 아니다.** 이 9번은 "JSON을 내놓는 데 성공한 호출"이라는
  **결과로 걸러진** 집단이다. 형식을 지킨 응답과 지키지 않은 응답이 판정 난이도에서
  다를 이유가 없다고 볼 근거가 없다.
* `333` §1이 미리 적어 둔 대로, **이 실행은 어느 프롬프트가 옳은지 고르지 않는다.**

그래서 이 9번은 결론이 아니라 **다음 실행을 설계할 단서**다.

## 6. 중단 규칙이 안 걸렸다 — 이건 결함이다

`333` §6은 `330` §3의 중단 규칙을 그대로 가져왔고, 그중 하나가
`zero_response_after = 10`이다. 그 규칙의 주석은 스스로 이렇게 적고 있다 —
*"이건 328의 관찰 갈래를 열 번 만에 끝냈을 규칙이다."*

**이번 관찰 갈래는 최대 27번 연속으로 안 읽혔는데도 안 멈췄다.** 왜인지 정확히 적는다.

1. **범위가 틀렸다.** 규칙은 `calls` 목록 **전체**에서 답한 호출을 센다. 그런데
   실행 순서는 문항마다 `production → observation`으로 **번갈아** 간다. 1번 호출이
   production이고 그게 답을 냈으므로, `answered == 0`은 **실행 내내 한 번도 참이 될 수 없었다.**
   두 번째 갈래를 추가한 건 [PR #445](https://github.com/hyeonsangjeon/gdpval-realworks/pull/445)
   — 즉 **이 결함은 이번 묶음이 만들었다.**
2. **범위만 고쳐도 안 걸렸다.** 규칙 모양이 "앞 N번에 답이 **하나도** 없으면"이다.
   관찰 갈래는 **자기 4번째 호출에서 한 번 답했다.** 그래서 갈래별로 셌더라도
   `answered == 0`이 거짓이라 안 멈춘다.

**두 가지를 다 적는 이유:** 1번만 고치고 "막았다"고 쓰면 그건 사실이 아니다.
15%씩 답하는 갈래를 멈추려면 **응답률 기준 규칙**이 필요하고, 그 임계값은
**결과를 보고 나서 고르면 안 된다.**

### 이번에 한 것과 안 한 것

* **한 것:** 범위를 갈래별로 고쳤다(`scripts/measure_audio_grading_accuracy.py`).
  두 갈래 실행에서 한 갈래의 침묵이 다른 갈래의 응답에 가려지지 않는다.
  회귀 테스트를 그 분기에만 붙였다.
* **안 한 것:** 응답률 기준 중단 규칙. 이건 **임계값을 미리 못 박은 별도 사전등록**이
  있어야 한다. 지금 숫자를 보고 임계값을 정하면 그건 사후 맞춤이다. 후속 목록에 남긴다.
* **이 수정은 `334`의 숫자를 하나도 바꾸지 않는다.** 이미 산 120번은 그대로 저장돼 있고,
  중단 규칙은 *수집*에만 영향을 준다. **다시 돌리지 않는다**(`333` §7).

## 7. 사전등록한 숫자 전부 (§5가 내라고 한 것)

결과를 보고 고른 지표는 없다. 갈래마다 전부 낸다.

| 지표 | production | observation |
|---|---|---|
| 응답률 | 59/60 = 0.9833 | 9/60 = **0.150** |
| 미응답 — 모델 거절 | 1 | 0 |
| 미응답 — 형식 오류(읽기 실패) | 0 | **51** |
| 미응답 — 공급자 실패 | 0 | 0 |
| 참 주장 정확도 | 8/29 = 0.276 (`false_fail` 20, 69.0%) | **3/5** (읽힌 것만, 25번 미응답) |
| 거짓 주장 정확도 | 29/30 = 0.967 (`false_pass` 1, 3.3%) | **4/4** (읽힌 것만, 26번 미응답) |
| 판별력 J (호출) | 0.243 | 0.60 |
| 문항 다수결 정확도 | 12/20 = 0.60 | 5/7 = 0.714 |
| 못 정한 문항 — 답 없음 | 0 | **13** |
| 못 정한 문항 — 다수결 없음 | 0 | 0 |
| 사전등록 이항 검정 | n=20, 12 정답, p = 0.2517 | n=7, 5 정답, p = 0.2266 |
| 짝 안 뒤섞기(순열) | J = 0.243, p = 0.03125 | J = 0.60, p = 0.078125 |
| 갈라낸 쌍 | 10쌍 중 **2쌍** (8쌍은 양쪽에 똑같이 `fail`) | 10쌍 중 0쌍 (**9쌍은 한쪽이 미완**) |
| 반복 흔들림 | 58쌍 중 8번 = 13.79% | 비교 가능한 쌍이 **2개**뿐 |
| **상수 `fail` 기준선** | **0.50 / J = 0** | **0.50 / J = 0** |

**production의 0.60을 기준선 0.50 옆에 놓고 읽어야 한다.** 20문항에서 12개는
동전보다 두 개 많은 것이고, 사전등록한 이항 검정이 **p = 0.2517**로 그렇게 말한다.

**observation의 `by_family` 칸은 대부분 비어 있다.** 6번 중 0번 읽힌 계열이 둘 있다.
계열별 비교는 이번 실행으로 못 한다.

> **원본에 있는 한 가지 이상한 값.** 관찰 갈래의 `stability.identical_across_repeats`가
> 13으로 찍혀 있는데, 이건 *세 번 다 안 읽힌 13문항*을 "반복끼리 같았다"로 센 것이다.
> 답이 없는 것을 일관성으로 세면 안 된다. `330` 때부터 있던 계산이고 **1차 지표에는
> 안 쓰인다.** 결과를 본 뒤에 계산을 고치지 않기 위해 **이번엔 안 고치고 여기 적어만 둔다.**

## 8. 이 실행이 답하지 못한 것

`333` §8의 한계가 전부 그대로 살아 있고, 하나가 늘었다.

* **원래 질문에 답 못 했다.** "지시문이 '아니다' 쪽으로 미는가"는 여전히 미해결이다.
  개입 갈래가 판정을 안 내놨기 때문이다.
* **관찰 지시가 도움이 되는지 안 되는지 모른다.** 읽힌 9번은 표본이 아니다(§5).
* **왜 형식이 깨졌는지 모른다.** 응답 본문을 저장하지 않으므로 정황뿐이다(§3).
* 목소리는 **eSpeak 포먼트 합성**이고 `en-us` 하나뿐이다. 사람이 아니다.
  잡음·화자 겹침·억양·다른 언어 없음.
* 문항 20개는 적다. **큰 p는 "차이 없음"이 아니라 "이 코퍼스로는 못 봤다"**이다.
* **`331`의 낮은 점수가 "소리를 못 알아듣는다"는 증명이 아니라는 것**도 그대로다.
  이번 실행은 그 질문을 **가르지 못했다.**
* 프롬프트·자료·모델 범위를 넘어 일반화하지 않는다.

## 9. 비용

| | 값 |
|---|---|
| 청구 대상 호출 | 120 |
| 입력 토큰 | 47,088 (production 18,924 / observation 28,164) |
| 출력 토큰 | 6,597 (production 4,180 / observation 2,417) |
| 오디오 토큰 | 3,696 (갈래당 1,848) |
| `pricing_complete` | **false** |
| 가격표에 없는 모델 | `gpt-audio-1.5` |
| **추정 비용** | **`null`** |

`gpt-audio-1.5`는 이 저장소 가격표에 **없다.** 그래서 이 실행의 비용은
**미확정이지 0달러가 아니다.** 안 잰 것과 0은 다르다.
가격표는 다른 작업자가 소유하고 있고, 이 문서는 그 파일을 건드리지 않았다.

**관찰 갈래는 입력 토큰을 49% 더 썼다**(머리말 739자). 읽히지도 않을 응답에
그만큼 더 냈다는 뜻이고, §6의 중단 규칙이 중요한 이유가 그거다.

## 10. 다음에 할 일 (여기서 하지 않은 것)

각각 **자기 사전등록**이 필요하다. 이 문서가 결과를 보고 임계값이나 설계를
정하지 않기 위해서다.

| | 무엇 | 왜 여기서 안 하나 |
|---|---|---|
| 1 | 관찰 갈래의 형식 실패 원인 규명 | 응답 본문을 남기는 진단이 따로 필요하다. 개인정보·전문 보존 규칙과 같이 설계해야 한다 |
| 2 | 응답률 기준 중단 규칙 | 임계값을 **결과를 보기 전에** 못 박아야 한다(§6) |
| 3 | 구조화 출력(`response_format`) | `input_audio`와 함께 지원된다는 **공식 근거나 별도 최소 호환성 검증** 없이는 안 켠다. 지금도 미확인이다(`332` §4) |
| 4 | 형식을 깨지 않는 관찰 머리말로 A/B 재시도 | **`334`의 재실행이 아니다.** 새 번호·새 사전등록이어야 한다. `333`은 1회로 끝났다(§7) |
| 5 | `stability`가 무응답을 일관성으로 세는 문제 | 계산 변경이므로 결과를 본 뒤에 하지 않는다(§7의 경고) |

**이 문서는 재실행을 요청하지 않는다.** `333` §7은 "p가 마음에 안 든다고 다시 돌리지
않는다"고 적었고, p = 0.0654는 정확히 그 유혹이 오는 자리다. 한 번 샀고, 그게 끝이다.
