# 329 — 답을 못 알아들은 건 모델이 아니라 우리 쪽이었다

**요약.** [`328`](./328-the-answer-that-was-not-in-the-vocabulary.md)이 산 120번의 응답을
**한 번도 다시 사지 않고** 로컬에서 다시 읽었다. 결과를 한 줄로 줄이면 이렇다.

> 처치 갈래(observation)의 "정확도 47.1%"는 **판정이 들어 있지 않은 답 17개로 계산한
> 숫자였다.** 새 검증을 적용하면 그 갈래는 60번 중 **0번** 답했다. 정확도가 낮은 게
> 아니라 **정확도라는 게 없다.**

무엇을 고쳤는지도 한 줄로 줄이면 이렇다.

> 두 갈래가 **서로 다른 말로** JSON을 요구하고 있었다. 이제 **글자 하나까지 같은 문장**을
> 쓴다. 그리고 답이 없을 때 그 이유를 **세 가지로 갈라서** 센다.

[`328`](./328-the-answer-that-was-not-in-the-vocabulary.md)과
[`324`](./324-the-speech-it-heard-in-silence.md)의 수치는 **한 개도 안 고쳤다.**
기존 185실행·31건 채점 원본도 손대지 않았다.

## 3. 수정 전과 후, 같은 응답을 두 가지로 읽으면

| | 발표된 숫자 (`328`) | 새 검증으로 다시 읽으면 |
|---|---|---|
| production 답한 횟수 | 51 | **50** |
| production 정확도 | 0.549 | 0.560 |
| observation 답한 횟수 | **17** | **0** |
| observation 정확도 | **0.471** | **없음** |
| observation 응답률 | 0.283 | **0.000** |

숫자가 딱 맞아떨어진다. 발표본이 "답했다"고 센 observation의 **17번**은
새 검증이 "판정 값이 어휘에 없음"으로 거른 **17번과 같은 것**이다.
production의 51 → 50도 마찬가지로 그 갈래의 어휘 밖 1번이다.

**즉, 기존 파이프라인은 `true`라는 글자를 판정으로 받아들이고 있었다.**
그리고 `pass`가 아니면 전부 "아니다"로 세니까, 모델이 "맞다"는 뜻으로 `true`를
쓸 때마다 **정반대로 채점됐다.** [`328`](./328-the-answer-that-was-not-in-the-vocabulary.md)이
"처치가 유의하게 나쁘다(p = 1.10 × 10⁻⁵)"고 본 게 이것이다.

> 이번에 새로 주장하는 건 **"처치가 사실은 좋았다"가 아니다.** 그 갈래는 아무것도
> 답하지 않았으므로 좋았는지 나빴는지 **알 수 없다.** 사후에 `true`를 `pass`로 바꿔
> 읽어서 새 결과인 척하지 않는다. 알 수 없는 것은 알 수 없다고 적는다.

## 4. 무엇을 고쳤나

### 4-1. 두 갈래가 이제 같은 문장으로 요구한다

문제는 단순했다. 대조 갈래와 처치 갈래가 **각자 다른 말로** "JSON으로 답하라"고
쓰고 있었다. 그러면 응답률 차이가 프롬프트 때문인지 요구 문구 때문인지 **가를 수가
없다.** 지금은 두 갈래 모두 `AUDIO_RESPONSE_CONTRACT`라는 **하나의 문장**으로 끝난다.
바이트 단위로 같다는 걸 테스트가 잡고 있다.

계약이 요구하는 건 이것뿐이다.

* JSON 객체 하나, 다른 말 없이
* `verdict`는 `pass` / `partial` / `fail` / `judge_error` 중 **문자열 하나**

### 4-2. 답이 없을 때, 이유를 세 가지로 가른다

전에는 답이 없으면 다 한 덩어리였다. 이제 갈라서 센다.

| 이름 | 뜻 | 누구 책임인가 |
|---|---|---|
| `declined_to_judge` | 모델이 "판정 못 하겠다"고 **말했다** | 모델의 정직한 기권 |
| `read_failure` | 답은 왔는데 **형식이 계약과 다르다** | 우리 요구 또는 모델의 형식 |
| `provider_failure` | **호출 자체가 실패**했다 | 인프라 |

세 가지 다 정확도 분모에서 **똑같이 빠진다.** 다른 건 진단이다. 60번이 전부
`read_failure`인 것과 60번이 전부 `provider_failure`인 것은 완전히 다른 이야기인데,
전에는 리포트에서 구분이 안 됐다.

이유가 안 붙은 미응답은 **`provider_failure`로 떨어진다.** 모델에 대해 가장 적게
주장하는 쪽을 기본값으로 뒀다. 모르는 걸 "모델이 기권했다"로 적으면 안 되기 때문이다.

### 4-3. 조용히 `fail`로 바뀌던 것들

엄격한 검증이 이제 다음을 전부 **거부**한다. 하나도 `fail`이 되지 않는다.

* `true` / `false` / `refuse` 같은 **어휘 밖 문자열**
* `verdict` 키 **누락**
* 문자열이 아닌 **잘못된 타입** (`{"verdict": 1}`)
* **깨진 JSON**
* `"partial_score": true` — 파이썬에서 `bool`은 `int`라서 검사 없이는 점수 1.0이 된다

### 4-3-1. 이건 설계가 아니라 빠뜨린 거였다

같은 검사를 **다른 두 채점기는 이미 갖고 있었다.**

| 채점기 | 어휘 밖 값이 오면 |
|---|---|
| 메인 판정 (`tool_calling_judge`) | 거부 |
| 그림 판정 (`core/perception/vision.py:175`) | 거부 (`InvalidVisionEnvelope`) |
| **소리 판정 (`core/perception/audio.py`)** | **`fail`로 받아들임** ← 여기만 |

소리만 빠져 있었다. "소리는 다르니까 느슨하게 두자"는 판단이 있었던 게 아니라
**그냥 안 들어간 것**이다. 그래서 이번 수정은 새 정책이 아니라 나머지 둘과
**줄을 맞추는 일**이다.

### 4-4. 성공률 분모와 미응답률을 같이 낸다

정확도는 **답한 것 중에서**, 응답률은 **시도 전체에서** 낸다. 두 숫자를 항상 나란히
적는다. 정확도 하나만 보면 "60번 중 0번 답했다"가 안 보인다.

### 4-5. 구조화 출력은 아직 안 켠다

API가 `input_audio`와 함께 `response_format`을 실제로 받는지 **확인되지 않았다.**
확인 전까지 안 켠다. 이것도 테스트로 고정해 뒀다
(`test_no_structured_output_is_requested_until_it_is_verified`).

## 6. 말소리 검증 세트 (아직 재보진 않았다)

지금까지 `gpt-audio-1.5`에 대해 잰 건 **전부 삑삑거리는 소리**였다. 클릭, 톤, 비프.
그걸로 "판정이 소리에 따라 달라지는가"는 답했다. 하지만 채점 대상 31건 중
**사인파는 하나도 없다.** 전부 사람 말이다. 그래서 물어야 할 건 따로 있다.

> **말을 알아듣는가?**

이건 다른 능력이고, 한쪽만 가질 수 있다. 삑 소리 세 번을 맞게 센 시스템은
"소리가 도착했다"를 보인 것이지 "말을 알아들었다"를 보인 게 아니다.

그래서 검증용 말소리 세트를 만들었다. 아직 모델에 물어보진 않았다.

| | |
|---|---|
| 합성기 | eSpeak NG (오프라인, 결정적) |
| 라이선스 | GPL-3.0-or-later — **이 저장소는 아무것도 재배포하지 않는다** |
| 고정하는 것 | 버전 문자열, 바이너리 SHA-256, 패키지 출처, **전체 명령줄**, 클립별 SHA-256 **두 개** |
| 문항 | 클립 10개, 주장 20개, **짝 10쌍** (참 10 / 거짓 10) |
| 찍으면 | **50%** |
| 개인정보 | 녹음 없음, 목소리 복제 없음, 사람·장소·날짜·식별자 없음 |
| 정답 유출 | 매니페스트에만 있고 **모델에는 안 간다** — 모델은 `criterion` 한 줄만 본다 |

### 왜 클립마다 지문이 두 개인가

처음엔 하나로 두려고 했다. "모델이 듣는 그 바이트를 고정한다"는 게 핵심이니까
16 kHz로 만들어서 지문 하나만 남기면 된다고 봤다. **그게 안 됐다.**

eSpeak NG에는 **표본율 옵션이 아예 없다.** 목소리 데이터에 붙어 있는 값이고
`en-us`는 22050 Hz로 나온다. 그런데 채점 경로(`_trim_audio_bytes`)는 **뭘 받든**
16 kHz 모노로 다시 인코딩해서 보낸다. 즉 eSpeak가 쓴 파일은 **아무도 안 듣는다.**

| 지문 | 무엇인가 | 재현하려면 |
|---|---|---|
| `source` | eSpeak가 쓴 것 (22050 Hz) | 같은 eSpeak 버전 |
| `sent` | **모델이 실제로 듣는 것** (16000 Hz) | 같은 eSpeak **+ 같은 ffmpeg** |

그래서 둘 다 적는다. 하나만 적으면 재현 실패가 났을 때 **합성기가 바뀐 건지
인코더가 바뀐 건지 구분이 안 된다.** 재현 비교도 두 지문을 **다른 문장으로**
따로 틀렸다고 알려 준다.

변환은 ffmpeg나 sox를 따로 부르지 않고 **채점기 자신의 함수**를 쓴다. 새 도구를
쓰면 그 도구의 버전도 고정해야 하는데, 채점기 함수를 쓰면 고정할 게 안 늘어난다.

각 쌍은 **같은 클립에 대해 같은 종류의 질문을 두 번** 한다. 하나는 참, 하나는 거짓.
예를 들어 "화자가 열일곱이라고 말한다" 대 "화자가 일흔이라고 말한다" — **들어야만**
갈린다. 종류는 헷갈리는 숫자, 방향, 순서, 부정, 결합 등이다.

`order` / `binding` / `negation` 세 종류는 **참 주장의 모든 단어가 클립 안에 들어
있고 배열만 다르다.** 단어만 주워담는 시스템은 이걸 못 푼다.

### 한계는 미리 적는다

eSpeak NG는 로봇 목소리다. 사람 목소리보다 **알아듣기 어렵다.** 그래서:

* **통과하면 강한 증거다.** 로봇 음성을 알아듣는 시스템이 같은 문장을 읽는 사람
  목소리를 못 알아들 가능성은 매우 낮다.
* **실패하면 약한 증거다.** "사람 말을 못 알아듣는다"가 아니라 "eSpeak를 못
  알아듣는다"까지만 말할 수 있다.

이 문장은 문서 구석이 아니라 **매니페스트의 필드**로 들어간다. 숫자 옆에 항상 붙게.

### 이 NAS에서는 못 만든다

커널이 3.10.102라 `espeak-ng`가 안 깔린다. `espeak` / `piper` / `flite`도 없다.
그래서 **GitHub Actions에서 만든다** — `.github/workflows/speech-verification-set.yml`.
클립은 커밋하지 않고 artifact로 올린다. 저장소에는 **지문만** 남는다.

다만 **문항이 공정한지 검토하는 일은 합성기 없이 된다.** 그게 사람이 봐야 하는
부분이고, 그건 이 NAS에서도 돌아간다.

```bash
python scripts/build_speech_verification_set.py --describe
```

### 실제로 만들어졌고, 지문도 대조했다

실행 [`34022771513`](https://github.com/hyeonsangjeon/gdpval-realworks/actions/runs/34022771513)에서
클립 10개가 만들어졌다. eSpeak NG 1.51, 총 재생 31.2350초. artifact를 받아
**NAS에서** 다시 대조했다. 새 API 호출은 **0번**이다.

| 확인 | 결과 |
|---|---|
| 합성 원본 digest = 파일 | 10/10 |
| 전달본 digest = 파일 | 10/10 |
| 전달본을 **NAS에서 다시 인코딩**해 비교 | **10/10 바이트 단위 일치** |

세 번째 줄이 이 설계가 값어치를 하는 지점이다. GitHub 러너가 만든 16 kHz 바이트가
**다른 기계에서 똑같이** 다시 나왔다. 그래서 `sent` 지문은 "그때 그 러너에서만
나오는 값"이 아니라 누구나 대조할 수 있는 값이다. 값 자체는
[`330`](./330-speech-diagnostic-prereg.md) §2에 있다.

매니페스트는 **저장소에 커밋했다** —
[`330-speech-verification-manifest.json`](./330-speech-verification-manifest.json).
음성 파일은 안 올린다(라이선스). 이렇게 하면 나중에 다시 만들었을 때 명령 한 줄로
대조된다.

```
workflow_dispatch → expect_manifest:
  tasks/rebuilding_grading_task/330-speech-verification-manifest.json
```

그리고 이걸 커밋한 덕분에 **문장을 고치고 다시 안 만드는 실수**를 테스트가 잡는다.
지문은 특정 문장에서 나온 값인데, 문장만 고치면 매니페스트는 **없어진 소리의 지문**을
계속 주장하게 된다. 이건 합성기 없이 NAS에서도 잡히고, 실제로 잡히는지 확인했다
(문구 수정·정답 뒤집기 둘 다 걸림).
