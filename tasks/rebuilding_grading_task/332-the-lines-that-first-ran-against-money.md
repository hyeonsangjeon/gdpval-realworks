# 332 — 돈을 쓴 다음에야 처음 돌아본 줄들

**요약.** [`331`](./331-it-said-no-to-almost-everything.md) §10의 후속 여섯 항목을 닫는다.
**이 PR은 돈을 한 푼도 쓰지 않는다.** 새 유료 실행도, 기존 결과의 수정도 없다.

* §10의 **1·2·4·5번은 코드와 시험으로 닫았다.** 유료 요약 페이지의 네 갈래(미응답 3종
  분할, 도착 사용량 행, 다중 갈래 안내, 지문 배너)를 **워크플로 자신의 `run:` 덩어리를
  실제로 실행해서** 확인했고, `pins.grader_source_sha256`을 요약에 찍게 했고,
  `classify()`의 어휘 밖 판정을 막았다.
* §10의 **3·6번은 원래 "문서화만 필요"한 항목이다.** 이 문서의 3절과 4절이 그것이다.
* 진단 시험 파일 **165개 → 171개** (+6). 새 시험 다섯 개는 전부 워크플로 YAML 안의
  파이썬을 꺼내 돌린 것이고, 여섯 번째는 `classify()`를 직접 부른다.
* 채점기 지문은 **안 움직였다.** `74e1f478…a558a90` — [`330`](./330-speech-diagnostic-prereg.md)이
  못 박은 값, `331`이 실제로 산 값과 **같다.** 저장소 자체 가드가
  `PASS: no grader-source file in this diff`.

> **한계부터.** 여기서 확인한 것은 **요약 페이지가 옳은 조건에서 옳은 줄을 찍는가**뿐이다.
> 이건 채점기가 소리를 알아듣는지와 아무 상관이 없다. `331`의 숫자는 한 개도 안 바뀌었고,
> 이 PR은 그 숫자를 다시 해석하지도 않는다.

## 1. 왜 이 줄들은 돈을 쓰고 나서야 처음 돌았나

같은 결함이 계속 나온다: **그 줄을 돌리는 유일한 입력이 유료 실행 자신인 것.**

예행(dry-run)은 조건을 **항상 거짓으로** 만든다. 미응답이 없고, 갈래가 하나고,
지문 충돌이 없다. 그래서 "뭔가 잘못됐을 때만 찍는" 줄은 **처음 실행되는 순간이 곧
돈이 나간 뒤**다. `331` 유료 실행에서 미응답 3분할이 실제로 찍혔지만, 그때까지
**그 줄이 옳은 라벨을 다는지 아무도 확인한 적이 없었다.**

`grep`으로는 이걸 못 잡는다. grep은 **문장이 파일에 있다**는 것만 증명하고,
**그 문장을 품은 갈래가 도는지**는 증명하지 않는다. 그래서 시험은 워크플로의
`run:` 블록에서 파이썬 heredoc을 **꺼내서 `exec`으로 돌리고**, `GITHUB_WORKSPACE`를
보고서 JSON이 들어 있는 임시 폴더로 돌려놓는다.

| §10 | 무엇 | 어떻게 닫았나 |
|---|---|---|
| 1 | `unanswered_by_kind` 3분할 (본문 L151) | 거절·읽기 실패·공급자 실패를 **일부러 다른 개수(5·9·16)** 로 만든 가짜 채점기. 라벨이 바뀌어 붙으면 숫자로 드러난다 |
| 2 | 도착 행 L133 · 다중 갈래 안내 L127 · 지문 배너 L252 · `if comparison:` L285 | 도착 행은 건네준 수를 그대로 싣는지, 갈래 안내와 짝표는 `--prompt-arm both`(무료 예행)에서만 나오는지, 지문이 둘인 클립은 배너가 비교표 **위**에 오는지 |
| 4 | `classify()` 어휘 밖 판정 | 5절 |
| 5 | 요약이 `pins.grader_source_sha256`을 안 찍음 | 값은 이미 보고서에 있었다. **읽는 줄만 없었다.** 사전등록 표의 64자 상수와 맞춰 보라고 잘라 쓰지 않고 통째로 찍는다 |

모델 신원 배너(본문 L277)는 이미
`test_a_foreign_model_answering_is_bannered_and_not_merely_listed`가 실행으로 덮고 있어
새로 만들지 않았다.

### 하마터면 — 시험이 없는 모양을 만들 뻔했다

지문 줄을 넣자 **기존 시험 다섯 개가 `KeyError: 'grader_source_sha256'`로 깨졌다.**
`pinned_identity()`는 지문을 안 들고 있고 `main()`이 나중에 찍어 넣기 때문이다.

**워크플로에 `.get()` 기본값을 넣지 않았다.** 그러면 지문 없이도 페이지가 렌더되고,
"어느 채점기로 돌았는지" 없이 초록불이 난다. 대신 **가짜 쪽을 진짜 모양에 맞췄다** —
`main`이 하는 것과 똑같이 지문을 찍는 `_stamped_identity()`를 만들고 12군데 호출을
그리로 돌렸다. 아무 실행도 만들지 않는 보고서 모양으로 시험을 통과시키면,
**결함이 아닌 자리에서 깨진다.**

## 2. 이 PR이 안 한 것

* **`batch-runner/core/` 아래를 한 글자도 안 건드렸다.** 그래서 채점기 지문이 안 움직인다.
  움직였으면 `330`의 사전등록이 `331`이 실제로 산 코드를 더 이상 가리키지 못한다.
* **새 유료 실행 없음.** `331`의 60회를 다시 사지 않았다.
* **기존 숫자 수정 없음.** `324`·`328`·`329`·`331`의 값, 185실행·31건 채점 원본 모두 그대로다.
* **새 추상화 없음.** 다중 갈래 갈림길은 이미 있는 `--prompt-arm both` 예행으로 닿는다.
* **전수 변형 검사 없음.** 시험은 §10이 이름을 댄 갈래에만 붙였다.

## 3. `--prompt-arm observation` + 말소리 세트는 왜 지금 exit 2인가 (§10-3)

**기전.** `argparse.ArgumentParser.error()`다. 이건 stderr에 사용법을 찍고
**상태 코드 2로 프로세스를 끝낸다** — 우리가 고른 숫자가 아니라 argparse의 규약이다.
`scripts/measure_audio_grading_accuracy.py:2959`:

```python
if args.prompt_arm != "production":
    # 330 pre-registers one arm. Two questions in one run is what made
    # 328 unable to answer either.
    parser.error(
        "the speech set is pre-registered as a single production arm; "
        "--prompt-arm would make it a different, unregistered run"
    )
```

**실제로 돌려서 확인한 값**(무료, 예행, 임시 매니페스트 2클립):

| 부른 방식 | 종료 코드 |
|---|---|
| `--prompt-arm observation` + 말소리 세트 | **2** |
| `--prompt-arm both` + 말소리 세트 | **2** |
| `--prompt-arm production` + 말소리 세트 | 0 |

**이유.** `330`은 말소리 진단을 **갈래 하나**로 사전등록했다. `328`이 두 질문을 한 실행에
섞어 넣는 바람에 **둘 다 답 못 하는 결과**가 나왔고, 이 차단은 그 재발 방지다.
그리고 이 자리는 **인자 검사 단계**라서, 클라이언트를 만들기 전에·한 번도 부르기 전에
막힌다. 즉 **돈 쓰기 전에 막히는 게 맞다.**

**이걸 그냥 없애서는 안 된다.** 프롬프트 A/B를 말소리로 하려면 차단을 걷어내는 게 아니라,
그 조합이 **올바른 음성과 질문·형식 계약을 실제로 만드는지** 모의 API로 증명하는
**진단 전용 지원**을 먼저 만들어야 한다. 그건 이 PR 범위가 아니다 — 별도 사전등록과
새 결과 ID로 간다.

## 4. 구조화 출력(`response_format`)은 여전히 꺼져 있다 (§10-6)

**현재 상태: 안 보낸다.** `core/audio_analyzer.py:108`이 그 자리에 주석으로 남아 있고,
`tests/test_audio_verdict_contract.py:521`의
`test_no_structured_output_is_requested_until_it_is_verified`가
`assert "response_format" not in client.calls[0]`로 그 결정을 못 박고 있다.
JSON 모양은 **API 플래그가 아니라 프롬프트 문장**으로 요구한다.

**왜 안 켜나.** `gpt-audio-1.5`가 `input_audio`와 **함께** 그 플래그를 받는지
**아무도 관찰한 적이 없다.** 거부하는 배포에 보내면 오디오 호출이 전부 400이 된다.
원 요구사항의 "API가 지원한다고 확인된 경우에만"이 그대로 적용된 보류다.

**켜려면 무엇이 필요한가 — 둘 중 하나.**

1. 그 API·모델 조합에 대한 **공식 근거**(제공자 문서에 `input_audio` + `response_format`
   동시 지원이 명시), 또는
2. **별도의 최소 호환성 검증** — 이 진단과 분리된 실행 단위에서, 호출 한 줌으로
   400이 나는지만 본다.

**하지 말아야 할 것.** 지원 여부를 알아보겠다고 **기존 비교의 입력을 몰래 바꾸는 것.**
`331`이 산 60회는 `response_format` 없이 나갔다. 그 조건을 바꾼 실행은 `331`과
같은 실행이 아니고, 섞어 쓰면 **형식 성공률이 왜 올랐는지 아무도 못 가른다** —
`328`에서 이미 한 번 겪은 실패다.

**지금 켜지 않아서 잃는 것은 거의 없다.** `331`은 읽기 실패 0번·어휘 밖 0번이었다.
서버가 강제해 줬으면 좋았을 문제가 **이번엔 안 일어났다.**

## 5. 어휘 밖 판정이 조용히 점수가 되던 자리 (§10-4)

`classify()`의 `fail` 갈래는 **그냥 `else`** 였다. `verdict == "pass"`가 거짓이면
끝. 그래서 `true`·`false`·`refuse`·`analyze_audio` — 실행 `34008840627`(`328`)이
실제로 뱉은 **어휘 밖 네 단어** — 가
**확신에 찬 `fail` 판정으로 점수화**되고, 거짓 주장에서는 전부 정답 처리됐다.

**새 규칙을 만들지 않았다.** `core.perception.audio`가 이미 어휘 밖 답을
`verdict_not_in_vocabulary`로 **전선에서** 거절한다. `classify()`는 같은 값의
**두 번째 독자**일 뿐이므로, 검사도 core의 것을 그대로 가져다 쓴다:

```python
if verdict not in AUDIO_VERDICT_VOCABULARY:
    raise ValueError(
        f"verdict outside the response contract's vocabulary: "
        f"{_offending_token(verdict)}"
    )
```

`AUDIO_VERDICT_VOCABULARY`와 `_offending_token` 둘 다 core에서 import한 것이고,
시험은 `probe.AUDIO_VERDICT_VOCABULARY is AUDIO_VERDICT_VOCABULARY`로 **사본이 아님**을
단언한다. 메시지도 core의 경계 있는 렌더러를 거치므로 모델이 준 문자열이 그대로
새어 나오지 않는다(`"the audio was ambiguous"` → `<non-token>`).

**오늘 이 갈래는 도달 불가다.** 앞단이 먼저 막기 때문이다. 그게 정확히 이 줄이
지금까지 조용했던 이유이기도 하다. 터뜨리는 쪽을 고른 건 `Tally.add`가 모르는 종류에
주는 답과 같고, **닫히는 쪽으로 실패한다** — 아무도 검증하지 않은 답에서 숫자가
발행되지 않는다.
