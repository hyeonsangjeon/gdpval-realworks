# 325 — 소리가 정말 모델까지 갔는가

**요약.** [`324`](./324-the-speech-it-heard-in-silence.md)가 낸 낮은 판별력에는
설명이 최소 셋 있다. 그중 하나 — **오디오가 요청에서 빠졌다** — 를 여기서 지운다.
새 호출은 한 번도 안 샀다. 이미 산 60번의 사용량이 답을 갖고 있었다.

* **보내는 모양은 공급자 규격 그대로다.** 코드가 만드는 조각과 공식 문서·SDK 타입이
  같다.
* **길이가 늘면 입력 토큰이 그만큼 늘어난다.** 클립 9개, 호출 60번에서 상관계수
  **0.9805**, 기울기 **초당 10.86토큰**. 오디오가 빠졌다면 있을 수 없는 관계다.
* **60번 모두 사용량이 붙어 왔다.** 하나도 비지 않았다.

그래서 남는 설명은 **프롬프트**와 **능력** 둘이고, 그 둘을 가르는 실험이
[`326`](./326-prompt-arm-prereg.md)이다.

---

## 1. 보내는 모양이 맞나

채점기가 오디오를 실어 보내는 자리는 `core/perception/audio.py`의 한 곳이다.

```python
{"type": "input_audio",
 "input_audio": {"data": b64, "format": fmt}}
```

공급자 쪽 규격 두 군데와 맞춰 봤다.

| 확인한 것 | 어디서 | 결과 |
|---|---|---|
| 조각 이름이 `input_audio`인가 | 공식 오디오 가이드의 curl 예제 | 같다 |
| `data`가 base64 문자열인가 | 같은 가이드 (`base64.b64encode`) | 같다 |
| `format`이 받는 값 | 설치된 `openai` 2.46.0의 생성 타입 `InputAudio` | `Literal["wav", "mp3"]` |
| 채점기가 보내는 값 | `_guess_format` → `wav` | 목록 안 |
| 모델이 이 경로를 받는가 | 가이드가 예로 드는 이름이 `gpt-audio-1.5`다 | 같은 이름 |

**모양 때문에 소리가 빠질 자리는 없다.** 형식이 목록 밖이면 코드는 보내지 않고
`unsupported_audio_format`으로 먼저 끊는다.

---

## 2. 보낸 것은 파일이 아니다

이게 이 문서에서 제일 놓치기 쉬운 줄이다.

`_trim_audio_bytes`는 압축 포맷(`mp3`)만 그대로 통과시키고, **`wav`는 언제나
다시 인코딩한다** — 16 kHz · 모노 · `pcm_s16le`. 즉

> **디스크의 파일 해시 ≠ 실제로 보낸 바이트의 해시.**

324 보고서에 적힌 `clip_sha256`은 *만든 파일*의 해시다. 그 파일이 모델에게 간
바이트와 같다는 보장은 지금까지 아무 데도 없었다. 이번 진단이 넣은 기록기는
**보내기 직전 조각에서** 해시를 뜬다. 파일이 아니라 전선을 잰다.

이 클립들은 원래 16 kHz 모노로 만들어졌으니 재인코딩이 내용을 바꾸지는 않는다.
하지만 "안 바뀐다"는 것도 재 봐야 아는 것이지 믿을 것이 아니다.

---

## 3. 공짜로 얻은 증거 — 토큰이 길이를 따라간다

오디오가 요청에서 빠졌다면 모델이 보는 것은 글자뿐이고, **클립이 길든 짧든 입력
토큰은 같아야 한다.** 실제로는 이렇다.

| 클립 | 길이 | 호출 | 입력 토큰(최소~최대) |
|---|---:|---:|---|
| `major_triad` | 3.0초 | 6 | 150~150 |
| `buzzy_bass` | 3.0초 | 6 | 152~157 |
| `g_major_scale` | 3.4초 | 6 | 153~154 |
| `three_beeps` | 5.0초 | 6 | 173~173 |
| `low_then_high` | 5.0초 | 6 | 175~175 |
| `modulating_arpeggio` | 5.0초 | 6 | 177~178 |
| `pure_silence` | 6.0초 | 6 | 177~183 |
| `tone_stops_early` | 6.0초 | 6 | 187~195 |
| `clicks_120bpm` | 8.0초 | 12 | 203~208 |

* 호출 60번 전체: **r = 0.9805**, 기울기 **초당 10.86토큰**, 절편 약 119.6.
* 클립별 평균 9점으로 봐도: **r = 0.9821**, 기울기 초당 11.01토큰.
* 기준 문장 길이(46~140자)도 토큰에 조금 섞인다(r = 0.4249). **토큰에서 길이의
  몫을 회귀로 빼낸 잔차**를 클립 길이와 다시 재도 **r = 0.9678**, 초당 9.71토큰이
  남는다. (길이와 클립 길이 **양쪽**에서 몫을 빼는 편상관으로 보면 r = 0.9984,
  초당 10.33토큰으로 오히려 더 강해진다. **약한 쪽을 본문 숫자로 쓴다.**)

**초당 11토큰 언저리는 고정 프레임 오디오 토크나이저의 모양이다.** 글자만 갔다면
이 기울기가 나올 이유가 없다. `pure_silence`처럼 **모든 표본이 0인 파일도 6초치
토큰을 썼다** — 내용이 없어도 길이만큼은 확실히 실려 갔다는 뜻이다.

호출 60번 전부 `usage_complete`가 참이다. 사용량이 없어서 못 본 칸은 없다.

## 4. 그래도 남는 구멍과, 이번에 메운 것

토큰-길이 관계는 **간접 증거**다. 소리가 갔다는 것까지는 말해도, 간 바이트가
우리가 만든 그 바이트인지, 답한 모델이 우리가 부른 그 모델인지는 말하지 않는다.
그래서 기록기를 붙였다. 다음 실행부터 호출마다 이만큼이 남는다.

| 기록 | 답하는 질문 |
|---|---|
| `audio_part_present`, `audio_parts` | 조각이 실렸는가, 몇 개인가 |
| `audio_sha256`, `audio_b64_chars` | **보낸** 바이트가 무엇인가 |
| `audio_format` | `wav`인가 |
| `sent_wav` (RIFF·채널·표본율·길이) | 헤더가 실제로 그렇게 말하는가 |
| `response_model` | **답한** 모델 이름 (요청이 아니라 응답에서) |
| `audio_tokens` | 공급자가 오디오 토큰을 따로 세어 주는가 |
| `prompt_sha256`, `prompt_chars` | 어느 프롬프트로 물었는가 |
| `transport_error` | 호출이 던졌는가 |

이 기록에서 보고서가 만드는 요약이 `delivery`다. 여기서 걸리는 것들:

* 조각이 하나도 없는 호출 수(`calls_without_audio`)
* **같은 클립인데 보낸 해시가 둘 이상인 경우** — 두 프롬프트 갈래가 같은 바이트를
  들었는지는 이걸로 확인한다
* 헤더가 말하는 길이와 원본 길이가 0.05초 넘게 어긋나는 클립 — 잘림 탐지
* 응답에 찍힌 모델 이름 목록
* 오디오 토큰 보고 여부

`response_model`은 이미 저장소에 있던 `resolved_model_of`를 쓴다. 있는데 오디오
쪽에서 한 번도 안 부르고 있었다.

### 안 남기는 것

**원본 오디오도, 프롬프트 전문도, 모델의 내부 추론도 기록하지 않는다.** 남는 건
해시·개수·헤더 값뿐이고, 시험 하나가 기록의 모든 값이 128자를 넘지 않는지와
base64·프롬프트 문자열·`reasoning`이 산출물 어디에도 안 나오는지를 확인한다.

### 빠진 payload는 모의 호출로 잡는다

값을 치르지 않고 잡아야 하므로, 새 시험은 **일부러 망가진 가짜 클라이언트**를
쓴다. 오디오를 버리는 것, 빈 base64를 넣는 것, 형식을 바꿔치기하는 것, 바이트를
잘라 보내는 것, 요청 모델 이름을 응답인 척 돌려주는 것 — 각각이 시험 하나로
걸린다. 새 시험 **45개**를 붙였고, 코드에 결함 **24개**를 일부러 심어
**24개 모두**가 걸리는 것까지 확인했다.

## 5. 이 문서가 말하지 않는 것

1. **이미 산 60번에는 위 기록이 없다.** 기록기는 그 실행 뒤에 붙었다. 60번에 대해
   말할 수 있는 건 토큰-길이 관계와 사용량이 다 있다는 것까지다.
2. **`audio_tokens`가 실제로 오는지는 아직 모른다.** 공식 usage 스키마에는
   `prompt_tokens_details.audio_tokens` 자리가 있지만, 이 배포가 채워 주는지는
   다음 실행이 알려 준다. 값이 없으면 **`null`로 남긴다. 0으로 적지 않는다.**
3. **전달이 맞다고 판정이 맞는 건 아니다.** 이 문서가 지운 건 설명 셋 중 하나뿐이다.
4. **운영 채점기는 한 줄도 안 고쳤다.** 기록기는 진단 스크립트 안에만 있다.
   `core/perception/**`와 `core/tool_calling_judge.py`, 채점 설정은 그대로다.

## 6. 다시 세는 법

값 없이:

```bash
cd batch-runner
python scripts/measure_audio_grading_accuracy.py --dry-run --delivery-out /tmp/delivery.json
```

§3의 토큰-길이 관계는 이미 저장소에 있는 파일만으로 다시 나온다.

```bash
cd batch-runner
python - <<'PY'
import json
d = json.load(open("../tasks/rebuilding_grading_task/324-audio-accuracy-measured.json"))
dur = {c["clip_id"]: c["duration_s"] for c in d["clips"]}
crit = {c["claim_id"]: c["criterion"] for c in d["claims"]}


def fit(xs, ys):
    n = len(xs); mx = sum(xs)/n; my = sum(ys)/n
    sxy = sum((a-mx)*(b-my) for a, b in zip(xs, ys))
    sxx = sum((a-mx)**2 for a in xs); syy = sum((b-my)**2 for b in ys)
    slope = sxy/sxx
    return sxy/(sxx*syy)**0.5, slope, my - slope*mx


xs = [dur[c["clip_id"]] for c in d["calls"]]
ys = [c["input_tokens"] for c in d["calls"]]
ls = [len(crit[c["claim_id"]]) for c in d["calls"]]
print("all       n=%d r=%.4f slope=%.2f intercept=%.1f" % (len(xs), *fit(xs, ys)))
print("crit len       r=%.4f" % fit(ls, ys)[0])
_, s, i = fit(ls, ys)                      # 토큰에서 문장 길이의 몫을 빼고
res = [y - (s*l + i) for y, l in zip(ys, ls)]
print("residual       r=%.4f slope=%.2f" % fit(xs, res)[:2])
PY
```
