# 317 · 185과제 채점에 얼마가 들었나 — 값을 못 정한 채로 범위를 좁히다

> 이 문서는 **가격을 정하지 않는다.** 정할 수 없기 때문이다.
> 대신 "얼마인지 모른다"를 "이 범위 안이다"로 바꾼다.
> 여기 적힌 모든 숫자는 `main`에 커밋된 장부에서 다시 계산된다.

---

## 1. 한 줄 요약

이 프로젝트의 대표 실행인 **185과제 gold-ceiling 채점**에는 **금액이 아예 없었다.**
토큰은 한 톨까지 다 세어 놓고, 달러만 비어 있었다.

| | 값 |
|---|---|
| 모델 호출 | **22,528회** |
| 입력 토큰 | **119,799,621** |
| 출력 토큰 | **7,879,272** |
| 금액 | **없음** (`estimated_cost_usd: null`) |

이번 작업으로 금액이 생긴 건 **아니다.** 대신 이렇게 됐다.

| | 이전 | 이후 |
|---|---|---|
| 185과제 채점 값 | 알 수 없음, 상한 없음 | **$549.50 ~ $980.84** |
| 과제당 | 알 수 없음 | **$2.97 ~ $5.30** |
| 모델 가격 | 미정 | **여전히 미정** |

---

## 2. 왜 금액이 없었나 — 실패가 아니다

채점 모델 `gpt-5.6-sol`은 **일부러** 가격표에 없다.

Azure가 가격을 안 밝혀서가 아니다. 오히려 **24개나** 밝혀 놨다.
문제는 그중 **어느 것이 우리 실행에 해당하는지** 아무도 말해주지 않는다는 것이다.

이 저장소의 규칙은 단순하다.

> 가격은 **정확히 일치**해야 한다. 커밋된 표에 그 모델의 키가 있으면 가격이 있는 것이고,
> 없으면 없는 것이다. 앞자리가 같다고, 가장 비슷하다고, 같은 계열의 대표 모델이라고
> 대신 쓰지 않는다.

그래서 장부의 모든 행이 `model_cost_usd: null`이다. **`0`이 아니라 `null`이다.**
이 차이가 전부다. `0`은 "공짜였다"는 뜻이고, `null`은 "아무도 얼마인지 말할 수 없다"는 뜻이다.
공짜가 아니었던 걸 공짜로 적는 것이 이 시스템이 막으려는 유일한 거짓말이다.

---

## 3. 막고 있던 이유 하나가 이미 사라져 있었다

가격표에는 "무엇이 해결되면 값을 매길 수 있나"가 적혀 있었다. 두 가지였다.

1. **채점 쪽 호출별 비용 장부를 공개할 것** — "결과 파일 옆에 쓰였다가 실행이 끝나면 같이 사라진다"
2. 5.6-sol의 context 경계값이 밝혀질 것

**1번은 이미 참이 아니었다.** PR #272와 #327이 장부를 결과 파일 옆에 같이 커밋하도록 바꿔 놨다.
지금 `main`에는 장부가 **29개** 들어 있다. 사라지지 않는다.

가격표만 그 사실을 모른 채 옛 문장을 그대로 들고 있었다. 이번에 그 문장을 고쳤다.

---

## 4. 옛 근거 하나는 애초에 틀린 추론이었다

가격표는 tier(context 구간)를 못 정하는 이유로 이렇게 적고 있었다.

> 86개 과제의 영수증을 보니 과제당 입력이 76,600 토큰(32회 호출)에서
> 6,150,162 토큰(177회 호출)까지 **80배** 벌어졌다. 그러니 하나로 정할 수 없다.

**이 근거는 성립하지 않는다.**

tier는 **요청 한 건**의 입력 크기로 갈린다. 과제당 합계는 **여러 요청을 더한 값**이다.
80배로 벌어진 건 "한 과제에서 몇 번을 물어봤나"이지 "한 번에 얼마나 크게 물어봤나"가 아니다.
합계를 아무리 쌓아도 tier는 움직이지 않는다.

정작 봐야 할 건 **호출 하나짜리 최대값**이었고, 그건 장부가 커밋되기 전에는 볼 수 없었다.

---

## 5. 장부를 실제로 읽어보니

커밋된 장부 29개 전부를 읽었다.

| | 값 |
|---|---|
| 5.6-sol 호출 (중복 제거) | **44,875회** |
| **한 요청 최대 입력** | **226,701 토큰** |
| 128,000 초과 | 26회 |
| 200,000 초과 | 3회 |
| **272,000 초과** | **0회** |

272,000은 형제 모델 `gpt-5.4`에 Azure가 **공개한** 경계값이다.
5.6-sol에는 공개된 경계값이 없어서, 비교할 수 있는 가장 가까운 숫자가 이것뿐이다.

**커밋된 44,875회 중 단 한 번도 272,000에 닿지 않는다.** 44,849회는 128,000 아래다.

---

## 6. 그래서 무엇이 정해졌고, 무엇이 안 정해졌나

**정해진 것: 없다.** Azure가 5.6-sol 경계값을 안 밝힌 이상, 226,701이라는 숫자는
여전히 **비교할 대상이 없다.** 모델은 계속 미정이다.

**좁혀진 것: tier가 금액을 얼마나 흔들 수 있는가.**

185과제 실행을 두 tier로 각각 계산하면 이렇다 (standard global 기준, cache write 제외).

| tier | 총액 | 과제당 |
|---|---|---|
| short context | **$549.50** | **$2.97** |
| long context | **$980.84** | **$5.30** |

이 범위는 그 실행의 **5.6-sol 호출 22,503회만** 계산한 것이다.
같은 실행에는 `gpt-audio-1.5` 호출이 **25회** 더 있는데, 그 모델도 따로 미정이라
이 범위 **안에 들어 있지 않다.** 즉 위 금액은 실행 전체가 아니라 채점 모델 몫이고,
실행 전체는 저 범위보다 조금 더 든다.

이전에는 tier가 "몇 배가 될지 모르는 축"이었다. 이제 **1.79배짜리 축**이다.

### 아직 열려 있는 축 셋

1. **tier** — 위 범위까지만 좁혀졌다. 경계값이 나와야 닫힌다.
2. **zone** — global인지 data zone인지. 이 표의 모든 모델이 같은 처지다. (약 1.1배)
3. **cache write** — 5.6-sol은 캐시 **쓰기**에도 과금하는데 5.4는 안 한다.
   영수증은 캐시에서 **읽은** 토큰만 기록하고 **쓴** 토큰은 기록하지 않는다.
   앞의 둘이 다 정해져도 이 미터는 적용할 수가 없다.

세 번째의 크기만 따로 재보면, 캐시에 없던 입력 56,284,648 토큰이 **전부** 캐시에 쓰였다고
가정한 최악의 경우 **$351.78**이 더 붙는다. 실제로 얼마가 쓰였는지는 기록이 없어서 모른다.

**축 셋이 열린 채로 값을 매기는 것이 바로 이 표가 거부하려고 존재하는 그 추측이다.**

## 7. 하마터면 두 배로 셀 뻔했다

장부 29개의 행을 다 더하면 **67,571행**이다. 그런데 호출은 **45,043회**다.

11개 조각(shard) 장부와, 그것들을 합쳐 만든 병합 장부가 **둘 다** 커밋돼 있기 때문이다.
병합 실행의 모든 호출은 디스크에 **두 번** 있다. 행을 세면 호출 수가 절반쯤 부풀려진다.

처음 계산에서 실제로 이 함정에 빠져 5.6-sol 호출을 67,378회로 셌다.
`call_id`로 중복을 제거해서 44,875회로 고쳤다.

그런데 이 중복이 뜻밖의 검증이 됐다.

```
중복 행 수 = 22,528
병합 장부 행 수 = 22,528   ← 정확히 일치
```

병합 장부의 **모든** 행이 조각 장부의 어떤 행과 `call_id`로 짝이 맞는다는 뜻이다.
병합 과정이 **없는 호출을 만들지도, 있는 호출을 빠뜨리지도 않았다.**
이 일치를 시험으로 고정해 뒀다.

## 8. n=1로 곱하면 안 되는 이유가 숫자로 나왔다

카드에는 채점 값이 **과제 하나**에서 잰 `$0.753121`로 적혀 있다.
그때 같이 적어 둔 경고가 "n=1이니 220개에 곱하지 말 것"이었다.

185과제 실행의 **하한**은 과제당 **$2.97**이다.

| | 과제당 | |
|---|---|---|
| n=1 실측 | $0.753121 | 산출물이 488자짜리 작은 엑셀 하나였던 과제 |
| n=185 하한 | **$2.97** | **약 3.9배** |
| n=185 상한 | $5.30 | 약 7.0배 |

경고가 맞았다. 그것도 **적게 잡은 쪽으로** 맞았다.
작은 과제 하나로 잰 값을 곱했다면 실제의 1/4 밑으로 예산을 잡았을 것이다.

## 9. 시험이 정말 잡는지 (되돌리기 7회)

새 시험 9개를 하나씩 일부러 깨뜨렸다. 일곱 번 모두 걸렸다.

| 바꾼 것 | 결과 |
|---|---|
| `max_single_request_input_tokens` 226701 → 226700 | 걸림 |
| `duplicate_rows` 22528 → 22527 | 걸림 |
| "이제 해결됐다" → 옛 "실행과 함께 사라진다" 문장 복원 | 걸림 |
| `$549.50` → `$549.51` | 걸림 |
| `calls_over_272k` 0 → 1 | 걸림 (시험 2개) |
| 여는 문장 "축 셋이 열려 있다" → "축 하나" | 걸림 |
| 닫는 문장 쪽 축 개수 | 걸림 |
| cache write 축 문장 삭제 | 걸림 |

**여섯 번째가 처음엔 안 걸렸다.** 축 개수는 문단의 처음과 끝에 두 번 적혀 있는데,
시험이 끝쪽만 보고 있었다. 앞을 "축 하나"로 고쳐도 뒤가 그대로라 통과했다.
양쪽 다 확인하도록 고치고, 왜 그렇게 했는지 시험 안에 적어 뒀다.

가장 중요한 시험은 이것이다.

```python
assert table.lookup("azure", "gpt-5.6-sol") is None
```

**범위를 좁힌 것이 값을 정한 것으로 둔갑하면 여기서 깨진다.**
숫자를 적어 두는 일의 유일한 위험은, 나중에 읽는 사람이 좁은 범위를 보고
"이 정도면 하나 골라도 되겠네"라고 여기는 것이다. 그 순간 실패하도록 해 놨다.

## 10. 채점기 지문에 영향 없음

`model_price_table.json`은 채점기 지문(`grader_source_hash`) 계산에 **들어가지 않는다.**
지문은 `step8_grade.py`, `core/**/*.py`, 스키마, `requirements.txt`, 프롬프트,
채점 설정 파일을 해싱한다. 가격표는 그중 어디에도 없다.

따라서 이 변경은 **어떤 채점 실행의 지문도 움직이지 않는다.** 병합 동결도 해당 없다.
(확인: 실행 중인 채점 없음, 가장 최근 실행은 08:22:14Z 완료.)

## 12. 남은 일

경계값이 공개되거나, zone이 확정되거나, 영수증이 cache write 토큰을 기록하기 시작하면
그때 다시 좁힐 수 있다. 셋 다 이 저장소 밖의 일이다.

그때까지 185과제 채점 값은 **$549.50에서 $980.84 사이**이고,
여기에 최대 **$351.78**의 cache write가 얹힐 수 있으며, **정확한 값은 없다.**
없는 값을 있는 척 적지 않는 것이 이 문서의 결론이다.
