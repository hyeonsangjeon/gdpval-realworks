# 306 — 재실행 조건: 무엇을 확인했고, 무엇을 아직 사지 않았는가

> 이 문서는 **재실행 준비 상태**를 적는다. 재실행 자체는 하지 않았고, 유료 채점도 한 번도 돌리지 않았다.
> 앞 문서: 부분 결과는 `304-B-partial-blocked.md`, 재개 단위 설계는 `305-resume-granularity.md`.
> 검사기는 `batch-runner/tests/test_the_audio_smoke_covers_what_the_defect_damaged.py` (10건).

## 한 문단 요약

174개를 채점한 뒤 채점기 결함 하나를 찾았다 — 영상 답안의 소리를 못 듣는 판정자에게 소리 항목을 넘기고 있었다. PR #276이 그걸 고쳤는데, **고치는 순간 채점기 지문이 바뀌어서 이미 채점된 174개는 고칠 수 없다.** 다시 사야만 교정된다. 그래서 이번에는 **아무것도 사지 않고**, 다시 살 때 잘못될 수 있는 자리들을 미리 다 막아뒀다. 막았다고 주장만 한 게 아니라 하나씩 실제로 돌려서 확인했다.

## 지문 두 개 — 절대 섞지 않는다

| | 지문 | 무엇 |
|---|---|---|
| 옛것 | `955be41edc4aff19…` | **이미 채점된 174개.** 소리를 못 듣던 채점기 |
| 새것 | `450aee03cf6cb840…` | 고쳐진 채점기. **아직 아무것도 채점하지 않았다** |

지문이 다르면 **다른 측정**이다. 같은 과제를 두 지문으로 매긴 점수는 평균 낼 수 없다. 항목 단위로 어느 채점기가 매겼는지 구분할 방법이 없기 때문이다.

## smoke를 두 과제로 늘렸다 — 추측을 실측으로 바꿈

전에는 `75401f7c` 하나였다. 이유는 *"`.mp3`·`.mp4`·`.wav`가 다 들어 있는 답안이니 소리 경로를 제일 싸게 건드려볼 수 있겠다"* 는 **짐작**이었다.

174개를 돌리고 나니 그 짐작이 겨누던 결함이 실제로 잡혔고, **피해 범위도 정확히 나왔다 — 딱 두 개.**

| 과제 | 강등된 항목 | 못 받은 배점 |
|---|---|---|
| `75401f7c` | 14 | 18.0 / 56 |
| `e222075d` | 7 | 10.3 / 60 |

둘 중 하나만 덮는 smoke는 **비용은 거의 그대로면서 나머지 하나는 증명하지 못한다.** 그래서 pin을 짐작한 집합에서 **잰 집합**으로 바꿨다.

중요한 건 이 목록을 config에 **베껴 적지 않았다**는 것이다. 검사기가 `stage3_partial_inventory.json`의 결함 블록을 매번 다시 읽어서 config의 목록과 대조하고, 둘이 어긋나면 실패한다. **나중에 세 번째 피해 과제가 발견되면 smoke를 사기 전에 CI가 먼저 빨개진다.**

순서도 취향이 아니다. `step8_grade.py`는 corpus 순서를 안 지킨 pin을 거부하므로 `e222075d`(46번)가 `75401f7c`(47번)보다 먼저다. 둘 다 Film and Video Editors인데, 이건 우연이 아니라 **연속된 행이 같은 직업을 공유**하기 때문이다.

## 재실행은 run ordinal 1이다 — 2가 아니다

`--run-ordinal N`은 **지문이 그대로인 채로 같은 run을 반복**할 때 쓰는 것이고, `_repeats/run-00N/`으로 결과를 빼돌려서 그 사실을 표시한다.

지금은 지문이 **이미 움직였다.** 그래서 새 지문에서의 ordinal 1은 아직 아무도 안 쓴 자리다. 여기서 2를 붙이면 *"한 번도 채점된 적 없는 지문에서의 두 번째 run"* 이라는 거짓말이 된다. 게다가 `_repeats/`로 빠지면 대시보드가 읽는 `data/grades/*.json` glob에서도 빠진다.

**손으로 아무것도 안 올려도 되는 상태가, 분리가 제대로 작동하고 있다는 증거다.**

## 새 run이 옛 174개를 건드릴 수 없는 세 갈래

셋 다 실제로 돌려서 확인했다. 하나만 있어도 될 것 같지만, 셋이 각각 다른 사고를 막는다.

| | 무엇이 갈라지나 | 막는 사고 |
|---|---|---|
| **출력 경로** | 파일명에 `src_<지문 앞 16자>`가 들어감 | 옛 결과 **덮어쓰기** |
| **비용 원장** | run id가 `실험\|config\|지문` | 새 지출이 옛 run 합계에 **얹히는 것** |
| **병합 계약** | `grader_source_hash`가 동일성 필드 | 두 채점기 결과가 **한 payload로 섞이는 것** |

셋째가 제일 중요하다. 앞의 둘은 파일을 따로 둘 뿐이지만, 셋째는 **한 결과 안에 섞이는 것**을 막는다. 이게 없으면 185개를 채우는 제일 싼 방법이 *"빠진 11개만 새 채점기로 사서 옛 174개에 붙이기"* 가 되는데, 그건 **완전한 corpus처럼 보이면서 속은 채점기 두 개**다.

병합 거부는 **필드 목록을 읽어서 확인하지 않고 실제로 병합을 시켜봤다.** 커밋된 shard 0과, 지문만 새것으로 바꾼 shard 1 사본을 같이 넣으면 rc=1로 거부하고 출력 파일을 만들지 않는다. 목록만 봤다면 필드가 계약에 **놓여만 있고 안 쓰이는 상태**여도 통과했을 텐데, 지금 막으려는 사고가 바로 그 소리 없는 종류다.

## 지문은 고정돼 있지 않다 — 이번에 새로 찾은 것

`450aee03cf6cb840`은 **오늘 main 기준**이다. 열려 있는 PR들을 실제로 병합해보고 다시 계산했다.

| 병합하면 | 전체 run 지문 |
|---|---|
| main 그대로 | `450aee03cf6cb840` |
| \+ #278 (cost-call-identity) | `4cdacb582b00bc54` **바뀜** |
| \+ #284 (cost-rollup-status) | `3abdb81dce7585e2` **바뀜** |
| \+ #288 (gpt-5.4 cost smoke) | `450aee03cf6cb840` 그대로 |
| \+ #292 (envelope phase 0) | `003310ec408d165e` **바뀜** |

#288만 안 움직이는 이유는 **지문이 config별로 계산되기 때문**이다. 넘겨받은 config 하나만 넣고, 옆에 있는 다른 config 파일은 쳐다보지 않는다. #288은 새 grading config만 추가하므로 우리 config의 지문에 안 보인다.

**여기서 나오는 실무 규칙 하나.** smoke와 전체 run은 **같은 커밋에서 띄워야 한다.** smoke를 돌린 뒤에 `core/`를 건드리는 PR이 하나라도 병합되면, 전체 run은 **어떤 smoke도 확인한 적 없는 지문**에서 돌게 된다. 그리고 그 사실이 드러나는 시점은 유료 채점 60시간쯤 지난 뒤다.

이건 검사기에 넣어뒀다. `core/` 파일을 건드리면 **두 지문이 같이 움직이고**(그래서 smoke가 전체 run에 대한 증거가 된다), config만 건드리면 **한쪽만 움직인다.** 양쪽 다 실제로 파일을 고쳤다 되돌리면서 확인했다.

절차: **smoke가 통과한 순간의 전체 run 지문을 적어두고, 전체 run을 띄우기 직전에 다시 계산해서 달라졌으면 멈춘다.**

## 좁혀서 싸게 사려는 시도는 막혀 있다 — 실제로 시켜봄

전체 config는 185개를 pin하고 있다. 이걸 CLI로 줄일 수 있으면 pin이 무의미해지므로, 줄이려는 시도는 전부 거부된다.

| 해보면 | 결과 |
|---|---|
| smoke pin 중 **한 개만** `--tasks`로 지정 | 거부 — *"conflicts with config pinned task selection"* |
| `--limit 1` | 거부 — *"--limit conflicts"* |
| pin에 없는 과제 지정 | 같은 이유로 거부 |
| pin과 **똑같이** 지정 | 통과 (중복이지만, 그래서 config가 딴 데를 가리키면 그때 걸린다) |

"한 개만" 을 굳이 시험한 이유: 이게 **돈을 반으로 줄이려 할 때 실제로 칠 법한 명령**이고, 통과했다면 *한 과제에 대해서만 소리 경로를 증명한 smoke*가 **그럴듯한 결과를 내놓았을** 것이기 때문이다.

그리고 smoke는 corpus의 일부만 pin하므로 scope가 `subset`으로 분류돼 `_diagnostic/<scope_sha>/`로 빠진다. **smoke가 실패해도 전체 run의 디렉터리에는 닿지 않는다.**

## 비용은 이번에도 미확정이다

재실행에 쓰이는 두 모델 — 판정자 `gpt-5.6-sol`, 소리 `gpt-audio-1.5` — 은 **둘 다 가격표에 없다.** 가격표에는 `gpt-5.4` 계열 넷뿐이다.

값이 없으면 **가까운 모델로 대신 매기지 않고 그냥 "가격 없음"으로 기록한다**(`runtime_cost_unpriced`). 사용량은 다 남는다.

**`known_usd: 0.0`을 `$0`으로 렌더링하지 말 것.** 공짜라는 뜻이 아니라 **가격표가 없다**는 뜻이다.

## 아직 안 한 것

- **유료 채점을 한 번도 돌리지 않았다.** 이 문서의 모든 지문·숫자는 커밋된 파일에서 다시 계산한 것이다.
- **shard 4의 다섯 번째 재시도를 하지 않았다.** 같은 조건의 반복은 결론을 못 바꾸고 약 6시간을 다시 쓴다.
- 기존 `expected_task_count`·`task_ids`·최종 병합 경로 검사를 **완화하지 않았다.**
- `core/`·schema·rubric·prompt·judge를 건드리지 않았다. smoke config **하나만** 넓혔고, 그게 전체 run 지문을 안 움직인다는 것을 다시 계산해서 확인했다(`450aee03cf6cb840` 그대로).

## 실제로 사려면 남은 것

**smoke를 띄우는 것도 전체 run을 띄우는 것도 소유자 결정이다.** 여기서는 준비만 했다.

순서는 이렇다.

1. **2과제 smoke** — 소리 경로가 실제로 고쳐졌는지 확인. 이 시점의 전체 run 지문을 적어둔다.
2. 지문 재계산 — 1번 이후 `core/`를 건드린 병합이 있었으면 **여기서 멈춘다.**
3. **전체 185개 재실행** — 새 지문, run ordinal 1.

다만 3번은 `304-B`의 차단 해제 조건이 먼저 풀려야 한다. **`9e39df84`는 여전히 한 청크 안에 안 들어간다** — 고쳐진 채점기라고 더 빨라지지 않는다. 그래서 재실행은 (a) 360분 넘는 검증된 러너나 (b) 과제 내부 체크포인트 중 하나를 필요로 하고, 설계는 `305-resume-granularity.md`에 있다.

`305`가 적어둔 판단이 지금 그대로 들어맞는다 — **지문이 어차피 움직이는 시점에 (b)를 같이 묶는 것이 옳다. 그때는 어차피 전체를 다시 사야 하므로 (b)의 추가 비용이 0이 된다.** 지문은 이미 움직였다.
