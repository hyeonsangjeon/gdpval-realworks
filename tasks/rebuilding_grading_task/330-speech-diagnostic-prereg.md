# 330 — 말소리 진단 사전등록 (아직 안 샀다)

**상태: 사전등록 초안. 아직 한 푼도 안 썼다.**

이 문서는 **돈을 쓰기 전에** 적는다. 실행 후에 조건을 바꾸면 그건 사전등록이 아니다.
[`328`](./328-the-answer-that-was-not-in-the-vocabulary.md)이 실패한 이유의 절반이
"무엇을 재는지 실행 전에 못 박지 않은 것"이었다.

---

## 0. 실행 조건 (이게 안 맞으면 안 산다)

| 조건 | 상태 |
|---|---|
| 응답 형식 계약 PR이 **green으로 병합** | ✅ [#435](https://github.com/hyeonsangjeon/gdpval-realworks/pull/435) (2026-09-06, squash `e3c87d3`) |
| 말소리 세트가 **CI에서 실제로 만들어짐** | ✅ 실행 [`34022771513`](https://github.com/hyeonsangjeon/gdpval-realworks/actions/runs/34022771513) |

네 개 다 채워지기 전에는 실행하지 않는다. **⬜ 가 하나라도 남아 있으면 이 문서는
사전등록이 아니라 계획서다.**

### 실행할 때 넣을 값 (실행 전에 못 박는다)

`.github/workflows/audio-accuracy-probe.yml`을 `workflow_dispatch`로 부른다.
**아래 다섯 개 말고 다른 조합은 이 사전등록이 아니다.**

| 입력 | 값 | 기본값과 다른가 |
|---|---|---|
| `dry_run` | `false` | ✅ 다름 |
| `paid_approval` | `true` | ✅ 다름 |
| `repeats` | `3` | 같음 |
| `prompt_arm` | `production` | 같음 |
| `corpus` | `speech` | ✅ 다름 |

`prompt_arm`이 `production`인 게 핵심이다. §1에서 적었듯 이번엔 프롬프트 A/B가
아니다. `both`를 넣으면 호출이 120번이 되고 두 질문이 섞인다. 측정기가
`--speech-set`과 함께 온 두 번째 갈래를 **거절**하도록 돼 있어서, 실수로 넣으면
돈을 쓰기 전에 멈춘다.

`corpus: speech`면 두 작업(무료·유료) 모두 eSpeak를 깔아 클립을 **다시 만들고**
커밋된 매니페스트와 대조한다. 러너의 eSpeak가 움직였으면 바이트가 달라지고,
대조가 실패하고, **돈 쓰기 전에** 멈춘다.

네 번째 줄이 나중에 붙었다. 앞의 세 개가 다 ✅가 된 뒤에야 **측정기가 톤 코퍼스만
돌릴 수 있다**는 게 드러났다. 조건을 지우는 대신 줄을 늘렸다. 못 돌리는 걸
"돌릴 수 있다"로 치고 실행하면 사전등록이 아니다.

## 1. 무엇을 묻는가

> **`gpt-audio-1.5`가 말소리를 알아듣는가?**

지금까지 잰 건 전부 톤·클릭·비프였다. 그걸로 "판정이 소리에 따라 달라지는가"는
답했다. 하지만 채점 대상 31건 중 **사인파는 하나도 없다.** 전부 사람 말이다.

이건 [`324`](./324-the-speech-it-heard-in-silence.md)나
[`328`](./328-the-answer-that-was-not-in-the-vocabulary.md)이 물은 것과 **다른 질문**이고,
한쪽만 가질 수 있는 능력이다.

### 이번에 안 묻는 것

* **프롬프트 A/B 아님.** 갈래는 **하나**다(운영 헤더). 두 질문을 한 실행에 섞으면
  둘 다 흐려진다. [`328`](./328-the-answer-that-was-not-in-the-vocabulary.md)이 그랬다.
* **기존 실험 재채점 아님.** 185실행·31건은 건드리지 않는다.
* **음악·신호 재측정 아님.** 톤 코퍼스 결과와 **따로** 보고한다. 섞지 않는다.

## 2. 고정하는 것

### 모델·설정

| | 값 |
|---|---|
| 모델 | `gpt-audio-1.5` (Azure OpenAI) |
| 설정 파일 | `gold_audio_repeat_v2_sol_max.yaml` |
| 채점기 지문 | `8bb8360a5da68fc532b3d7392f726b284e1940417170563079a1550d0458c8a8` |
| 구조화 출력 | **끔** — API가 `input_audio`와 함께 받는지 미확인 |

### 프롬프트

운영 헤더 + `AUDIO_RESPONSE_CONTRACT`. **손으로 고쳐 쓰지 않는다.**
[`329`](./329-the-verdict-that-was-never-a-verdict.md)에서 두 갈래를 바이트 단위로
맞춘 그 문장 그대로다.

모델이 보는 건 `criterion` **한 줄**이다. 대본도, 정답도, 짝의 반대쪽도 안 간다.

#### 정답이 같은 프로세스 안에 있다

매니페스트에는 eSpeak에 넘긴 **문장 전체**(`clips[].command`)와 각 주장이 왜
성립하는지(`claims[].because`)가 들어 있다. 재현하려면 있어야 하는 값들이다.
그래서 측정하는 내내 **정답이 속성 하나 거리에** 있다.

이게 새면 실행이 죽지 않는다. **정답을 받은 판정기는 20문항을 다 맞히고**,
리포트는 "말소리를 알아듣는다"고 적는다. 지금까지 잡은 결함들과 같은 모양이다 —
숫자는 멀쩡해 보이고 측정만 의미가 없다.

그래서 판정기에 넘어가는 **인자 목록 자체**를 테스트로 박았다. `criterion`과
`audio_path` 둘뿐이고, 하나라도 늘면 깨진다
(`test_the_judge_is_handed_the_criterion_and_nothing_else`). 프롬프트 전문은
§6대로 기록하지 않으므로(지문만 남는다) 검사할 수 있는 경계가 여기다.

문항 자체도 확인했다. 20개 중 **자기 답을 말하는 criterion은 없고**, 대본을
그대로 인용하는 것도 없다. 짝의 두 문항은 같은 클립·같은 종류에 **헷갈리는 단어
하나만** 다르다(`seventeen`/`seventy`, `left`/`right`). 소리를 안 듣고 글자만
읽으면 찍는 것과 같다
(`test_the_published_criteria_do_not_answer_themselves`).

#### 이 지문이 진짜 재현되는지 확인했다

artifact를 받아 **다른 기계(NAS)에서** 대조했다. 돈은 안 들었다.

| 확인 | 결과 |
|---|---|
| 합성 원본 10개 digest = 파일 | **10/10** |
| 전달본 10개 digest = 파일 | **10/10** |
| 전달본을 NAS에서 **다시 만들어** 비교 | **10/10 바이트 단위 일치** |

세 번째 줄이 핵심이다. GitHub 러너에서 만든 16 kHz 바이트가 NAS에서 **똑같이**
다시 나왔다. 재인코딩이 기계를 안 탄다는 뜻이고, 그래서 `sent` 지문은 "그때 그
러너에서만 나오는 값"이 아니라 **누구나 대조할 수 있는 값**이다.

eSpeak 자체는 이 NAS에서 못 돈다(커널 3.10.102). 그래서 `source` 쪽 재현은
CI에서만 확인 가능하고, 여기서 확인한 건 **인코더 단계까지**다.

매니페스트 원본은 [`330-speech-verification-manifest.json`](./330-speech-verification-manifest.json)에
있다. 다시 만들었을 때 대조하려면 워크플로를 `expect_manifest`에 이 경로를 넣고
돌리면 된다. 어긋나면 **합성기가 움직였는지 인코더가 움직였는지 갈라서** 알려 준다.

#### 측정기가 이 세트를 실제로 끝까지 돌리는지도 확인했다

지문 대조와 별개로, **측정 경로 전체**를 이 NAS에서 한 번 돌렸다. 모델 자리에는
정답을 아는 스텁이 들어가므로 정확도는 의미가 없다(`measured: false`). 보는 건
**소리가 제대로 실려 나가는가**다. 새 API 호출은 **0번**이다.

```bash
cd batch-runner
python scripts/measure_audio_grading_accuracy.py --dry-run --repeats 3 \
  --speech-set ../tasks/rebuilding_grading_task/330-speech-verification-manifest.json \
  --speech-clips <클립 디렉터리> --out /tmp/speech_real_dry.json
```

| 확인 | 결과 |
|---|---|
| 계획 호출 수 / 실제 | **60 / 60**, 중간 중단 없음 (`stopped: null`) |
| 문항·클립·반복 | 20 / 10 / 3 — §2와 동일 |
| 실제로 실려 나간 소리의 지문 | **10/10 매니페스트 `sent`와 일치** |
| 표본율·채널 | 전부 16000 Hz mono |
| 총 재생 길이 | **31.235 초** → 예상 오디오 토큰 **937** |
| 오디오 토큰 합계 | `null` (스텁은 이 필드를 안 보낸다. **`0`이 아니다**) |

마지막 두 줄이 이번에 잡은 결함 두 개다. 고치기 전에는 **길이가 안 맞는 클립**이
10개 전부로 나왔고(삑소리 길이표로 대조하고 있었다), **토큰↔길이 상관**의 표본이
`0`건이었다. 지금은 각각 **0개**와 **60건, r = 0.99992**다.

멀쩡한 실행이 저 두 칸 때문에 "소리가 안 갔다"로 읽힐 뻔했다. 그 두 칸은 정확도를
믿기 **전에** 먼저 보라고 적어 둔 자리다.

**빈칸을 채우지 않은 채로 실행하면 안 된다.** 어떤 소리를 들려줬는지 나중에
증명할 수 없는 측정은 측정이 아니다.

### 문항·반복·호출

| | 값 |
|---|---|
| 클립 | 10 |
| 주장 | **20** (짝 10쌍, 참 10 / 거짓 10) |
| 갈래 | 1 (운영) |
| 반복 | **3** — 이전 실행들과 같게. 안정성을 비교하려면 같아야 한다 |
| **총 호출** | **20 × 3 × 1 = 60** |
| 찍으면 | **50%** |

### 토큰 예상

[`328`](./328-the-answer-that-was-not-in-the-vocabulary.md)에서 공급자가 보고한 값은
**클립 1초당 정확히 10.00 오디오 토큰**이었다. 그 비율을 그대로 적용하면:

```
예상 오디오 토큰 = 10 × (총 재생 길이 초) × 3
```

총 재생 길이가 **31.2350 초**로 확정됐으므로:

```
10 × 31.2350 × 3 ≈ 937 오디오 토큰
```

실제 값이 이 식에서 **10% 넘게 벗어나면**(즉 843 미만 또는 1,031 초과) **그 자체가
보고 대상**이다. 소리가 다르게 전달됐거나 과금 방식이 바뀐 것이므로.

### 비용

`gpt-audio-1.5`는 **가격표에 없다.** 따라서:

* `pricing_complete: false`
* `estimated_cost_usd: null`

**`$0`이 아니다.** 모르는 것은 모른다고 적는다. 실제 청구액은 나중에 대조한다.

## 3. 시간·중단 규칙

실행 전에 정한다. 중간에 "조금만 더"는 없다.

| 상황 | 조치 |
|---|---|
| 벽시계 **20분** 초과 | 중단, 그때까지 나온 것만 보고 |
| 처음 **10번** 중 **응답률 0** | **즉시 중단.** 형식이 또 깨진 것이므로 나머지 50번은 낭비 |
| `provider_failure` 누적 **10번** | 중단. 인프라 문제지 모델 능력 문제가 아니다 |
| 소리 미전달(오디오 토큰 0) 감지 | **즉시 중단.** 안 들려준 걸로 능력을 재면 안 된다 |
| 그 외 | 60번 다 채운다 |

중단해도 **결과는 그대로 보고한다.** 중단은 실패가 아니라 절약이다.

### 이 규칙은 코드가 지킨다

문서에만 있는 중단 규칙은 **지키면 손해 보는 그 순간에** 다시 검토된다. 그래서
표의 네 줄을 `measure_audio_grading_accuracy.py`의 `SPEECH_STOP_RULES`에 그대로
넣었고, 두 값이 어긋나면 테스트가 깨진다
(`test_the_pre_registered_rules_are_the_ones_the_document_names`).

두 번째 줄이 핵심이다. [`328`](./328-the-answer-that-was-not-in-the-vocabulary.md)의
처치 갈래는 **60번을 다 사고** 나서 한 번도 안 읽혔다는 게 밝혀졌다. 이 규칙이
있었으면 **10번에서 끝났다.**

세부 사항 두 가지를 미리 적는다.

* **중단해도 산 건 안 버린다.** 규칙을 발동시킨 그 호출까지 기록에 남긴다. 버리면
  규칙을 지키는 게 손해가 되고, 그러면 안 지키게 된다.
* **오디오 토큰이 "없다"와 "0이다"는 다르다.** 필드 자체를 안 보내는 공급자는
  중단시키지 않고, **0이라고 보고한** 공급자만 중단시킨다. 앞은 모르는 것이고
  뒤는 "소리를 안 셌다"는 주장이다.
* 리포트에 `stopped`(끝까지 갔으면 `null`)와 `calls_planned`가 같이 들어간다.
  중간에 멈춘 실행을 끝까지 간 실행과 나란히 놓고 비교하면 안 되기 때문이다.

**톤 코퍼스에는 이 규칙을 안 건다.** 그 숫자는 이미 발표됐고, 지금 규칙을 붙이면
발표된 결과가 나온 조건을 사후에 바꾸는 게 된다.

## 4. 미리 정하는 지표

### 1차 지표

> **쓸 수 있는 판정 중 정확도**, 그리고 그 옆에 **시도 전체 대비 응답률**.

두 숫자를 항상 같이 낸다. 하나만 내면 "0번 답했다"가 안 보인다.

### 판정 규칙

| 결과 | 읽는 법 |
|---|---|
| 정확도가 50%를 **유의하게 넘음** | 말소리를 어느 정도 알아듣는다는 **증거** |
| 정확도가 50% 근처 | 이 세트로는 **말소리 이해를 못 보였다** |
| 응답률이 낮음 | 능력이 아니라 **형식** 문제. 능력 판정 안 함 |

유의성은 20개 주장 각각에 대해 3회 중 다수결로 하나의 판정을 정한 뒤,
**이항검정(n = 20, p = 0.5)**으로 본다. 반복 3회를 독립 시행으로 세면 분모가
부풀어서 없는 유의성이 생긴다.

**검정은 두 개를 항상 같이 낸다. 어느 쪽이 1차인지도 지금 정한다.**

| | 검정 | 단위 | 리포트 필드 |
|---|---|---|---|
| **1차** | 이항검정 (n = 20, p = 0.5) | 주장당 다수결 판정 1개 | `accuracy.pre_registered_binomial` |
| 2차 | 짝 안 순열검정 (10쌍, 1024가지) | 짝 안에서 라벨을 뒤섞음 | `accuracy.permutation` |

둘 다 **숫자가 나오기 전에** 이름을 적어 뒀다. 하나만 계산해 놓고 나중에 "이게
1차였다"고 고르는 게 이 문서가 막으려는 바로 그것이다. 두 개를 다 내고 어느 쪽이
1차인지 미리 박아 두면 **나중에 고를 수가 없다.**

순열검정이 낼 수 있는 가장 작은 값은 **1/1024 ≈ 0.00098**이다(10쌍). 이항검정
쪽은 20개가 다 맞아야 1/2²⁰이다. **설계가 못 내는 값을 기대하지 않는다.**

다수결이 `partial`로 나온 주장은 이항검정의 분모에서 **뺀다.** 맞다고도 틀렸다고도
셀 수 없기 때문이다. 그래서 n이 20보다 작아질 수 있고, 그 경우 `n`과
`hedged_majorities_excluded`가 리포트에 같이 찍힌다.

### 부차 지표

* 짝 안에서의 **일관성** — 같은 클립, 참/거짓 한 쌍에 대해 서로 다른 답을 하는가.
  둘 다 `pass`면 안 듣고 찍은 것이다.

#### 짝 일관성은 세어서 낸다

`accuracy.pair_consistency`에 **10쌍 중 몇 쌍을 갈랐는지** 그대로 찍힌다.

| 필드 | 뜻 |
|---|---|
| `answered_differently` | 참/거짓에 **다르게** 답한 쌍. 들었다면 여기가 커야 한다 |
| `answered_identically` | 양쪽에 **같게** 답한 쌍 = 못 가른 쌍 |
| `identical_by_verdict` | 그 같은 답이 무엇이었나 (`pass` 10쌍이면 안 듣고 찍은 것) |
| `incomplete` | 한쪽에 다수결이 안 선 쌍. 가른 것도 못 가른 것도 아니다 |

Youden's J는 이걸 **비율 차이**로 요약한다. 몇 쌍이 안 갈렸는지는 J가 못 말한다.
그래서 개수를 따로 센다. 10쌍 전부 `pass`여도 이 코퍼스에서는 **정확도가 50%로
나온다.** 정확도만 보면 "아깝게 못 넘었다"로 읽히는 자리다.

* 종류별 정확도 — `order` / `binding` / `negation`은 단어만 주워담아선 못 푼다.
  다른 종류는 되는데 이 셋만 안 되면 **"단어는 듣지만 문장은 못 듣는다"**는 뜻이다.
* 반복 3회 사이의 **불일치율** — 이전 실행의 19.35%와 비교 가능하다.

#### 불일치율은 분모를 못 박아야 비교가 된다

19.35%는 **"반복 쌍" 분모**로 나온 값이다. 3회 반복이면 문항마다 쌍이 3개(1-2,
1-3, 2-3)이므로 20문항 = 60쌍이다.

리포트의 `stability`에는 **다른 분모**도 있다. `identical_across_repeats`로
계산하면 "한 번이라도 흔들린 문항의 비율"이 나온다. 3회 중 한 번 흔들린 문항은
쌍 분모로 33%, 문항 분모로 100%다. **두 숫자를 나란히 놓으면 있지도 않은 변화가
보인다.**

그래서 비교 대상은 `accuracy.stability.repeat_flips.flip_rate_pct` **하나로
고정한다.** 문항 분모 값(`claims_that_ever_flipped`)도 같이 찍지만 **19.35%와
비교하지 않는다.** 요약표에도 그렇게 표시된다.

한쪽이라도 답이 안 온 쌍은 **분모에서 뺀다.** 안 온 답은 일치도 불일치도 아니다.
뺀 개수는 `pairs_dropped_for_a_missing_answer`로 같이 적는다. 비교할 쌍이 하나도
없으면 `flip_rate_pct`는 `null`이다 — **0%가 아니다.** 0%는 "반복이 일치했다"는
주장이다.

## 5. 결과가 말할 수 있는 것과 없는 것

**미리** 적는다. 숫자를 본 뒤에 정하면 갖다 붙이는 게 된다.

| | |
|---|---|
| ✅ 통과하면 | 합성 음성을 알아듣는다. 사람 목소리도 알아들을 **가능성이 높다** |
| ❌ 실패하면 | **eSpeak를** 못 알아듣는다. "사람 말을 못 알아듣는다"는 **말할 수 없다** |
| ❌ 어떤 경우든 | 오디오 토큰이 청구됐다는 건 **전달의 증거**이지 이해의 증명이 아니다 |
| ❌ 어떤 경우든 | 이 결과는 **말소리**에 대한 것이다. 톤·클릭·비프 결과와 섞지 않는다 |
| ❌ 어떤 경우든 | 20문항은 **적다.** 좁은 신뢰구간을 주장하지 않는다 |

eSpeak NG는 로봇 목소리라 사람 목소리보다 **알아듣기 어렵다.** 그래서 통과는 강한
증거이고 실패는 약한 증거다. 이 비대칭은 매니페스트의 필드로도 들어간다.
