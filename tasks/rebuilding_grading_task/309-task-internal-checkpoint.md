# 309 · 청크보다 긴 과제 — 과제 내부 체크포인트

`307-audio-smoke-result.md`의 남은 일 목록 중 **3번(과제 내부 체크포인트)** 에 대한 답이다.
`305-resume-granularity.md`가 선택지 두 개와 함정 네 개를 정리해 뒀고, 이 문서는 **그중 B를 골라 실제로 만든 기록**이다.

결론부터: **끝낸 항목을 파일 하나에 남기고, 다음 조각이 거기서 잇는다.** 모델은 한 번도 부르지 않았다.

---

## 1. 무엇이 문제였나

채점은 과제를 하나씩 돈다. 시간이 다 되면 **하던 과제를 통째로 버리고** 나머지는 지킨다.
과제 하나보다 시간이 짧은 경우가 없다고 보고 만든 규칙이다.

`9e39df84` 과제 하나가 그 가정을 깬다.

| | |
|---|---|
| 채점 항목 수 | **57개** |
| 관측 속도로 다 도는 데 | 약 **360분** |
| GitHub가 한 판에 내주는 최대 | **351.7분** |

**8분이 모자란다.** 그래서 네 번을 샀는데 네 번 다 이렇게 끝났다.

```
1번째 시도 → 45개 하고 버려짐 → 다음 판은 1번 항목부터
2번째 시도 → 54개 하고 버려짐 → 다음 판은 1번 항목부터
3번째 시도 → 54개 하고 버려짐 → 다음 판은 1번 항목부터
4번째 시도 → 55개 하고 버려짐 → 다음 판은 1번 항목부터
```

**돈은 매번 다 냈고 남은 것은 매번 0개다.** 시간을 더 준다고 풀리지 않는다 — 상한이 우리 설정이 아니라 플랫폼 것이라서, 예산을 올리면 **돈을 잃는 위치만 과제 안쪽으로 옮겨간다.**

---

## 2. 왜 지금 이걸 하나

`305`는 이렇게 권고했다.

> A(긴 러너)를 먼저, B(체크포인트)는 A와 무관하게. … B는 **지문이 어차피 움직이는 시점에 묶어서 하는 것이 옳다.** 그때는 어차피 전체를 다시 사야 하므로 B의 추가 비용이 0이 된다.

**그 시점이 지금이다.** 소리 판정 버그를 고친 PR #298이 채점기 코드를 바꿨고, 채점기 코드가 바뀌면 지문이 움직이고, 지문이 움직이면 기존 174개는 어차피 다시 사야 한다.

| | 그때(305 작성 시점) | 지금 |
|---|---|---|
| 이미 값 치른 174개 | 유효 — B를 하면 무효가 됨 | **PR #298이 이미 무효로 만듦** |
| B의 추가 비용 | 60시간어치 재채점 | **0** |

같은 작업인데 지금 하면 공짜다. 미루면 다음에 청크보다 긴 과제가 나올 때 같은 자리에 다시 선다.

---

## 3. 어떻게 동작하나

시간이 다 돼서 과제를 버릴 때, **끝낸 항목만 파일 하나에 적는다.**

```
data/grades/_shards/<이름>/_progress/<partial 이름>__9e39df84___.json
```

다음 조각이 같은 과제를 시작할 때 그 파일을 읽고, **이미 끝난 항목은 건너뛰고 그다음부터 채점한다.**

```
1번째 조각 → 45개 끝냄 → 45개를 파일에 적음
2번째 조각 → 파일에서 45개 읽음 → 46번부터 채점 → 57개 완료
```

파일은 과제가 완전히 끝나면 지운다. 부분 결과가 남아서 "안 끝난 과제"처럼 보이지 않게.

**저장 위치가 partial 파일 옆인 이유**: 그 경로에 이미 실험·설정·지문·shard 번호·실행 회차가 다 들어 있다. 다른 shard의 체크포인트를 잘못 읽을 방법이 없다.

---

## 4. 안전장치 네 가지

`305`가 미리 짚어 둔 함정 B-1~B-4다. 넷 다 처리했다.

### B-1 · 공정성 — 재개할 때마다 듣기·보기 한도가 되살아나는 문제

채점기는 과제 하나당 **소리 3번, 그림 5번**까지만 쓴다. 이 한도는 과제가 바뀔 때 초기화된다.

그대로 두면 **세 조각에 걸쳐 끝난 과제는 소리를 9번 듣는다.** 한 판에 끝난 옆 과제는 3번 듣는다.
같은 rubric을 다른 자로 잰 셈이 된다.

→ **쓴 횟수도 같이 저장하고, 이어받을 때 되돌려 놓는다.** 실패 횟수 예산도 마찬가지다.
→ 저장된 숫자로 한도 자체를 늘릴 수는 없다. 999를 적어 넣어도 한도까지만 인정하고, 음수는 0으로 본다.

### B-2 · 출처 — 한 과제 안에서 채점기 버전이 섞이는 문제

**이게 넷 중 제일 위험하다.** shard끼리 섞이면 병합이 시끄럽게 거부한다. 그런데 **과제 안쪽에는 그 방어가 없었다.**

항목 1–30을 옛 채점기로, 그사이 코드가 바뀌고, 항목 31–57을 새 채점기로 채점하면 —
완성된 과제는 **마지막 채점기의 지문 하나만** 달고 나온다. 병합은 통과시킨다. **아무도 모른다.**

→ **체크포인트에 자기를 쓴 채점기 지문을 박는다.** 지금 지문과 다르면 **이어받기를 거부하고 그 과제를 처음부터 다시 채점한다.**
→ 거부할 때는 두 지문을 다 찍어서 로그에 남긴다. "체크포인트가 없었다"와 "있었는데 거부했다"는 완전히 다른 사실이고, 로그에서 구분돼야 한다.

### B-3 · 절반의 rubric은 점수가 아니다

57개 중 45개로 점수를 내면 숫자로는 그럴듯하고 뜻으로는 거짓이다.

→ **체크포인트 타입에 점수 필드를 아예 만들지 않았다.** `pct`, `critical_fail`, 합계 — 없다.
모양이 성적표와 같으면 언젠가 누가 성적표로 읽는다. 구조적으로 못 읽게 했다.
→ 저장 단계에서도 거부한다. 항목을 전부 담은 체크포인트는 **쓰지도 않고 읽지도 않는다.** 그건 끝난 과제고, 끝난 과제는 성적표에 들어가야 한다.

### B-4 · 비용 귀속 — 확인 결과 문제 없음

과제 하나가 두 조각에 걸치면 원장에 조각이 둘 생긴다. "과제당 얼마"를 볼 때 합쳐지는지 확인했다.

`cost_receipts.py`의 `receipt_for(task_id, bucket)`는 **과제 번호로 거르고 조각/회차로는 거르지 않는다.** 두 조각이 남아도 영수증은 하나로 합산돼 나온다. **고칠 것 없음.**

## 5. 추가로 막은 것 — 돈이 새는 두 자리

`305`에 없던 것인데, 만들면서 발견했다.

**가) 아무것도 못 한 조각이 다음 조각을 사면 안 된다.**
기존 규칙은 "이번 판에 과제를 하나도 못 끝냈으면 더 사지 않는다"였다. 체크포인트가 생기면 **과제는 못 끝냈어도 항목은 나아갈 수 있다** — 그때는 사도 된다. 다만 **항목도 안 나아갔으면** 다음 판이 똑같은 자리에서 똑같이 멈춘다. 그래서 두 조건을 다 본다.

**나) 저장했는데 커밋이 안 되면 저장 안 한 것이다.**
조각마다 러너가 새로 뜬다. 파일을 완벽하게 써도 **커밋되지 않으면 다음 조각이 볼 수 없다.**
그래서 워크플로가 이 파일도 커밋하게 붙였고 — 원장을 커밋하는 것과 정확히 같은 이유다 — 커밋용 경로를 못 알려준 경우에는 **"나아갔다"로 치지 않는다.**

경로 검사는 두 패턴을 다 받는다. shard로 돌면 `_shards/<이름>/` 밑, 아니면 `data/grades/` 바로 밑에 생기기 때문이다. **한쪽만 받는 검사는 맞게 쓴 파일 때문에 유료 판 전체를 죽인다.**

## 6. 검증

모델은 한 번도 부르지 않았다. 전부 가짜 응답으로 돌렸다.

| | |
|---|---|
| 새 테스트 | **46개** (`test_a_task_longer_than_a_chunk_keeps_its_finished_items.py`) |
| 음성 대조(가드를 하나씩 부숴 보기) | **16개 전부 테스트가 잡아냄** |
| 백엔드 전체 | 회귀 없음 |

**음성 대조가 이 작업의 핵심 증거다.** 테스트가 통과한다는 사실만으로는 그 테스트가 무언가를 지키고 있다는 뜻이 못 된다. 그래서 가드를 하나씩 실제로 망가뜨린 뒤 해당 테스트가 **실패하는지** 확인했다. 16개 전부 실패했다 — 즉 16개 가드가 전부 실제로 일하고 있다.

부순 것들: 지문 검사 없애기, 한도 되돌리기 안 하기, 실패 예산 리필하기, 한도를 넘겨 복원하기, 이어받고도 전 항목 다시 채점하기, 절반 rubric을 성적표로 쓰기, 판정문 원문을 파일에 남기기, 워크플로에서 커밋 지우기 등.

발견한 실수 하나: 음성 대조 장치 자체가 처음에 **엉뚱한 줄을 고치고 있었다.** 같은 코드가 파일에 다섯 번 나오는데 첫 번째를 바꿨다. 장치가 "이 앵커는 한 군데에서만 맞아야 한다"를 강제하도록 고쳤다. 안 고쳤으면 "테스트가 안 잡네" 하고 멀쩡한 가드를 의심할 뻔했다.

## 7. 만들면서 지운 것

처음에는 체크포인트에 **판정 호출 수·토큰·지연시간**까지 실었다. 테스트를 써 보니 **그 숫자들이 읽히자마자 덮어써지고 있었다.**

`Grader._aggregate_tool_instrumentation`이 항목별 계측을 과제 단위 진실로 삼아 다시 합산하기 때문이다. 그리고 그 항목별 숫자들은 이미 저장한 항목 안에 같이 들어 있다. **한 번 더 들고 다닐 이유가 없었다.**

남긴 건 `precheck_count` 하나다. 사전검사로 해결된 항목은 판정을 부르지 않아서 **항목별로 세어지는 데가 없다.** 이것만 잃는다.

지운 이유를 코드 양쪽에 적어 뒀다. **아무것도 안 하는데 뭔가 지키는 것처럼 보이는 코드**가 제일 위험하다.

## 8. 아직 안 한 것

* `9e39df84`가 **실제로** 두 조각에 걸쳐 끝나는지는 유료 실행에서만 확인된다. 여기까지는 전부 가짜 응답 위에서의 증명이다.
* 이 변경은 지문을 움직인다. **PR #298과 함께 하나의 지문으로 묶어서** 2과제 smoke를 한 번 더 돌린 뒤에 전체 185개로 간다.
* 순서는 `307`의 목록 그대로다.

```
1. 소리 400 고치기            → 끝 (PR #298)
2. 시각 렌더 대상 판단        → 끝 (문서 308, 코드 변경 없음)
3. 과제 내부 체크포인트       → 이 문서
4. 2과제 smoke 한 번 더       → 다음
5. 통과하면 전체 185개
```

**4번이 통과하기 전에는 185개를 사지 않는다.**
